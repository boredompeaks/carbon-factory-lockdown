## Findings (severity order)

### Q02-01 | P2 / MEDIUM | CODE | `backend/cart/views.py:64`
**A cart bound to a pending order stays fully mutable, and capture then deletes every line in it — including lines added after the order was created.**

`cart/views.py:64` resolves the cart and `:71-142` adds to it with no reference to `cart.order_id` (grep for `order` in `backend/cart/views.py`: zero hits). `orders/views/checkout.py:820-821` binds `cart.order = order` and leaves the items in place ("Inventory, coupon usage, and cart cleanup occur…" — `:850`). `orders/inventory.py:291-295` then deletes **all** items of the linked cart at capture: `linked_cart.items.all().delete()`, justified by the comment at `:71-72` "the linked cart's contents ARE the order's".

That premise only holds at the instant of checkout. Reachable sequence: add A → checkout (order1 for A, `cart.order=order1`, A still in the cart) → customer keeps shopping and adds B → pays order1 → capture deletes A **and** B. B was never ordered and is silently lost from the basket. The same wipe applies to lines merged in from a second device's guest cart at login, since merge targets the account cart regardless of `order_id` (`services.py:119-134`).

Not reachable for guests: `checkout.py:100-128` refuses anonymous checkout with 403, so every order-linked cart is account-keyed. That closes the worse variant I first suspected (a merged guest cart carrying an `order` FK) — it cannot exist. Confidence in the mechanism as written: **H**.

Fix route: NEXT-BUILD. Guard cart mutations on `cart.order_id` (reject, or start a new cart), or snapshot-and-detach the order's lines at checkout, or clear at order creation rather than capture.

### Q02-02 | P2 / MEDIUM | CODE | `backend/cart/views.py:125`
**Quantity increment is an unlocked read-modify-write, and the stock gate is check-then-act — two concurrent adds lose one, and `conventions.md:16` is not satisfied.**

`views.py:125-127` `get_or_create`, then `:129-138` reads `cart_item.quantity`, adds, re-checks `> product.stock`, assigns and `save()`. `views.py:199-200` (PATCH) and `:120-123` (stock gate) are the same unlocked shape. There is no `transaction.atomic()` and no `select_for_update()` anywhere in the add/update paths — grep over `backend/cart/*.py` shows `select_for_update` only at `services.py:111,119` and `views.py:239,267` (coupon paths), i.e. the *documented* convention is applied to coupon writes and not to the quantity/stock write. Two tabs adding 1 each against a line at 1 converge on 2 instead of 3; the stock re-check is also a stale read, so the "impossible line" the code claims to keep out (`:117-119`) can be created by a race.

Blast radius bounded (cart state only; `inventory.py:159-181` re-checks summed demand under locks at capture), so not money. Fix route: NEXT-BUILD — `F("quantity") + delta` inside `transaction.atomic()` with the stock read re-done under `select_for_update()` on the cart row.

### Q02-03 | P3 / LOW | CODE | `backend/cart/views.py:103`
**`int(quantity)` silently truncates a non-integer quantity instead of rejecting it: `{"quantity": 2.9}` is accepted as 2, `{"quantity": true}` as 1.**

`views.py:102-109` (add) and `:177-184` (patch) coerce with bare `int()`, which succeeds on floats and bools; only `ValueError`/`TypeError` produce the 400. The axis-1 invariant "quantity is an integer" is therefore enforced against `"abc"` and `-1` (tested, `tests.py:108-135`, `:149-165`) but not against `2.9`. No test drives a float/bool body.

Fix route: FOLD-INTO-NEXT.

### Q02-04 | P3 / LOW | CODE | `backend/cart/views.py:64`
**The unthrottled boot GET mints a Django session row *and* a cart row for every cookie-less caller, so one anonymous origin can insert unbounded rows at an unbounded rate.**

`CartMutationRateThrottle.allow_request` returns `True` for `GET`/`HEAD`/`OPTIONS` (`views.py:29-32`), `cart_detail` is the only throttle class on that view (`:57`), and `resolve_cart` calls `request.session.create()` + `Cart.objects.get_or_create(...)` on the anonymous branch (`services.py:41-53`). `DEFAULT_THROTTLE_CLASSES` is only `ScopedRateThrottle` (`settings.py:1283`), so nothing else bounds it. Each cookie-less `GET /api/cart/` therefore writes 2 rows. Reclamation depends entirely on `prune_carts`, which nothing schedules (see Q02-07).

Both behaviours are individually documented (SPA boot call, `views.py:47-52`), so this is a cost-of-contract observation with a real availability edge, not a broken invariant. Fix route: FOLD-INTO-NEXT (an anon-scope throttle on the create path, or cache the empty-cart response for a cookie-less GET).

### Q02-05 | P3 / LOW | CODE | `backend/cart/views.py:14`
**`from orders.views import validate_redeemable_coupon` couples the cart app to the orders app's view module and is the stated cause of a duplicated helper.**

`cart/views.py:14` imports from `orders.views`; the cycle it creates is acknowledged in `orders/views/checkout.py:77-79`, where `_object_body` is copy-pasted from `cart.views._object_body` (`cart/views.py:35-44`) "because cart.views imports orders.views". Two byte-identical body-coercion helpers now exist, each with its own docstring — the classic duplication `conventions.md` asks to avoid, and the F7-B1 fix must be applied twice to stay correct.

Fix route: FOLD-INTO-NEXT — move coupon validation to a service (`orders/services.py` or similar) and the body helper to `common/`.

### Q02-06 | P3 / LOW | CODE | `backend/cart/models.py:62`
**`Cart.updated_at` is not bumped by item mutations, so the field the serializer publishes as the cart's activity time is stale after any add/patch/delete.**

`models.py:62` is `auto_now=True`, which only fires when the `Cart` row itself is saved. `views.py:125-142` (add), `:199-200` (patch) and `:209` (delete) write only `CartItem` rows. Consequences: `CartSerializer.updated_at` (`serializers.py:36`) reports the cart's creation time forever; `CartAdmin.ordering = ("-updated_at",)` (`admin.py:30`) sorts on a value that never moves; and `prune_carts`'s documented basis — "Age is measured on `updated_at` (the last write)" (`prune_carts.py:15-16`) — is false for item writes. No data loss results (the prune query also requires `items__isnull=True`), so this is hygiene, not integrity.

Fix route: FOLD-INTO-NEXT (touch `cart.updated_at` on item writes, or stop publishing the field).

### Q02-08 | P3 / LOW | CODE | `backend/cart/models.py:67`
**The "exactly one owner key" invariant has no database constraint and the reader does not defend itself.**

`models.py:67-79` constrains only `user` (partial unique). Nothing forbids a row with both `user` and `session_id` set, or neither. `resolve_cart`'s anonymous read is `Cart.objects.filter(session_id=session_key).first()` (`services.py:50-53`) with **no** `user__isnull=True` filter, while the merge path *does* filter (`services.py:112`). Today only `merge_session_cart_into_user_cart` writes `user` and it clears `session_id` in the same `save(update_fields=[...])` (`services.py:129-131`), so the invariant holds — but it holds by writer discipline alone, and a single future write that stamps `user` without clearing `session_id` turns a stale browser cookie into a read path onto an account basket. The long comment at `models.py:9-16` states the invariant; nothing enforces it.

Fix route: FOLD-INTO-NEXT (`CheckConstraint` `Q(user__isnull=True) | Q(session_id__isnull=True)`, plus the filter in `services.py:51`).

### Q02-10 | P4 / INFO | CODE | `backend/cart/serializers.py:31`
**The cart payload carries no money at all — no subtotal, no line prices beyond the nested live product — so the "recompute the total on every read" invariant is vacuous here rather than satisfied.**

`serializers.py:31-37` exposes `id, items, coupon_code, created_at, updated_at`; `CartItemSerializer` (`:8-18`) exposes the nested `ProductSerializer` (live `price`), `quantity`, timestamps. The client derives a subtotal from live prices; the server derives its own at checkout (`checkout.py:477-495`) and for the coupon preview (`:1013-1016`). There is therefore nothing cached to go stale — and also no server-side figure a client can display authoritatively. Worth stating because the brief asks whether totals are recomputed on read: they are never stored, so display drift (never money drift) can only come from a price change between render and checkout.

### Q02-11 | P4 / INFO | CODE | `backend/cart/models.py:87`
**`CartItem.quantity` has no lower bound at the model layer while the API refuses 0, so the schema admits a state the code defends against.**

`models.py:87` is a bare `PositiveIntegerField(default=1)`, which permits 0 (and any value above stock). `views.py:111-115`/`:186-190` reject `<= 0`; `services.py:70-73` exists as a separate "drop a zero-cap line" branch precisely because the column cannot say no. No constraint links `quantity` to the product's stock either, which is correct (stock is advisory) but leaves the only quantity invariant in the DB layer being "not negative".

## Axis coverage

1. **Invariants.** Quantity positive/integer: bound yes (P3 gaps: Q02-03, Q02-11), `<= stock` advisory-by-design and re-checked at capture. One cart per identity: partial unique on `user`, enforced and tested. Session-vs-JWT ownership: single resolver, correctly branched, tested both ways. Merge-on-login: no lost lines, no duplicate lines, quantities summed and stock-capped, account coupon wins, no price resurrection possible (no stored price), **but** an order-linked cart is merged without regard to `order_id` (Q02-01 corollary). Price snapshot: none exists — deliberately, checkout prices live under lock. Total recomputation: no stored total (Q02-10). Session id never returned: confirmed (Q02-KNOWN V-09). CSRF on session mutations: enforced at the authentication layer and proven by a dedicated `enforce_csrf_checks=True` suite. Stock re-check at cart-add: present, locked nowhere (Q02-02).
2. **Correctness.** Status codes consistent (201 on add even when it updated an existing line at `views.py:142` — defensible add-to-basket semantics, pinned by `tests.py:84-91`). `get_or_create` races: handled by Django's retry and the DB constraint; the *increment* race is not (Q02-02). Decimal vs float: no money in this flow. Empty cart: uniform 400/"Cart is empty" at checkout, uniform 404 at coupon apply. Stale accumulation: command correct, unscheduled (Q02-07).
3. **SAST.** No missing `permission_classes` (four `AllowAny` sites are all session-scoped and documented); no IDOR (`item_id` scoped to `cart=resolved cart`, `views.py:162`, tested cross-session and cross-identity); no session id in any response body; no CSRF exemption on the cart views; no unbounded query params; no mass assignment (views read explicit keys, no writable serializer); no internals in error bodies (uniform `{"error", "code", "details"}` and uniform 404/400 families).
4. **Architecture.** Business logic is in services (`resolve_cart`, merge) — good — but the views module holds 272 lines of inline validation and the coupon domain leaks in from `orders.views` (Q02-05). `cart → orders` coupling is one-directional but forced a duplicated helper. No dead code found (F-19's `cart/views.py:117` dead block is gone; ruff is clean). Naming matches conventions except that `cart_detail` is a multi-method function view, which `conventions.md:13` says to prefer moving to a CBV (P4, not filed as its own row).
5. **Test side.** See Q02-09. Isolation is sound (fresh client per identity, `cache.clear()` around throttle pins, `tag("cart")`), no ordering dependence found, no network.
