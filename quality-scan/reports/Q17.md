## Findings

### Q17-01 — P2 MEDIUM — no test proves either money endpoint requires authentication; deleting `IsAuthenticated` leaves the suite green
`tests.py:948–1037` (`CreatePaymentTests`), `tests.py:1181–1690` (`VerifyPaymentTests`); guard at
`orders/views/payment.py:84` and `:189`.

`OrderTestBase.setUp` (`51–57`) authenticates the default client with a bearer token, and every
`/api/orders/payment…` request in scope is authenticated — including the one that uses a second client
(`1468–1470`, which sets the bearer explicitly). The only `401` assertions in the whole
1,200-line range are the two customer-read cases (`1779`, `1847`). So the whole authz story for the two
endpoints that mint and confirm charges — 20+ tests — rests on a decorator no test would notice the removal
of.

Impact is bounded, and the row is graded on that: with `request.user` being `AnonymousUser`, the owner
filters at `payment.py:98` / `:306` raise `ValueError` ("Cannot query AnonymousUser"), i.e. removing the
guard today yields a **500, not a leak** — the owner binding is what actually protects. What is untested is
that the endpoints are refused at the auth layer at all, and that the refusal is the house 401, not a
traceback. The same is true of the throttle scopes: both are pinned by inspecting `view_class`
(`451–454`, `1045–1050`), and the rate tests patch `THROTTLE_RATES` on the class (`463`, `475`, `1062`) —
which is the documented hermetic pattern, not a defect.

Fix: one subTest per endpoint (`{}` body, no credentials → 401 in the uniform envelope), plus one
anonymous request carrying a *well-formed* payload so the 401 cannot be confused with a validation 400.

### Q17-02 — P2 MEDIUM — the payment-intent money field is asserted on `.data` with a comparison a float passes; on the wire it is a float
`tests.py:960–970` (assert at `962–963`), production `orders/views/payment.py:175–185`.

```python
self.assertEqual(res.data["amount"], 100000)
self.assertEqual(res.data["amount_in_rupees"], Decimal("1000.00"))
```

`amount_in_rupees` is `order.total_amount`, a `Decimal`, placed in a plain `Response` dict — the exact shape
`orders/serializers.py:8–18` says must never leave the API ("DRF's JSON renderer encodes a bare ``Decimal``
as a float, dropping the trailing zero"). Probe result: `json.dumps({"amount_in_rupees":
Decimal("1000.00")}, cls=JSONEncoder)` → `{"amount_in_rupees": 1000.0}`. Two independent blind spots:

1. `.data` is pre-render, so a wire float is invisible (`MoneyWireFormatTests` exists precisely because of
   this, `488–490`, and does not cover this endpoint).
2. Even on `.data`, `Decimal("1000.00") == 1000.0` is `True`, so the assertion cannot distinguish a `Decimal`
   from a `float` at all.

So `R-9.3.24` is unproven for the one money response that is not built by a serializer, and the float is
live, not hypothetical. Also in the same block: `amount` (paise) is only ever pinned at a round `100000`
(`962`, `968–970`, `141–143`); no payment test uses a fractional total (the only non-round product in scope,
`1999.99` at `603`, never reaches `/payment/`), so a float regression in the paise conversion would pass every
test here. The risk is measured, not theoretical: across 2-dp values from 500.00 to 1000.00, **2,294** of the
50,000 differ between `int(float(d)*100)` and `int(d*Decimal("100"))` — e.g. `512.05` → `51204` vs `51205`.
(`1999.99` is *not* one of them: `float(1999.99)*100` is exactly `199999.0`, which is why picking an example
by feel is unsafe — the pin must be an amount from the measured set.)

Fix: render and parse the payment response in `MoneyWireFormatTests` style (`assertIsInstance(str)`,
`assertRegex(TWO_DP)`, `assertIn('"amount_in_rupees":"1000.00"')`), and add a line priced `512.05`
asserting `amount == 51205` — an amount from the measured mismatch set, so a float path fails.
Handoff: the wire float itself is a money-flow defect, not a test defect — see OUT-OF-SCOPE below.

### Q17-03 — P2 MEDIUM — every lock in the flow is either uncontended or unreferenced; all four `select_for_update` sites have no test that fails on removal
`checkout.py:627` (cart serialization for keyless dedup), `checkout.py:662` (user row for keyed replay),
`payment.py:306` (order row at verify), `payment.py:383–388` (products, ascending id, at capture).

The test file contains no thread, no second connection, and no `TransactionTestCase` except the migration test
(`177`). The three "race" scenarios are all sequential:

- `test_double_click_resubmission_replays_the_same_order` (`834–852`) — one client, two POSTs; the second
  sees a committed order. Remove `select_for_update` at `checkout.py:627` and this still passes: the dedup
  probe (`checkout.py:629`) runs after the (unlocked) cart read and finds the same row.
- `test_second_verify_rejected_idempotent` (`1478–1495`) — the second request is sent after the first
  returned 200. The guard it pins is the already-processed check (`payment.py:327–350`), not the lock at
  `:306`.
- `test_insufficient_stock_at_verify_returns_409` (`1497–1528`) — stock is moved with
  `products.objects.filter(...).update(stock=1)` before a single verify request, so the sufficiency re-check
  is exercised with zero contention.

Same for the lock-order claim the production comments lean on — `checkout.py:624–626` ("The cart row is
locked only on this path … so no new lock-order cycle is introduced") and `payment.py:377–382` ("One total
order closes the cycle"). Nothing in this file ever holds two paths' locks at once, so the deadlock-avoidance
argument is prose. (The keyed `Idempotency-Key` path is owned elsewhere — `orders/test_idempotency.py`, whose
"race authority" test at `:230–241` is also constraint-only, not concurrent.)

Fix (one test buys the whole invariant family): a `TransactionTestCase` with two threads, `connections.close_all`
in each, one performing checkout while the other sleeps inside a `mock.patch` hook — assert exactly one
`Order` row and one `PAYMENT_INITIATED`. If threads are not viable on the SQLite engine, say so in the class
docstring and add a `captureOnCommitCallbacks`-free structural pin (`assertIn("select_for_update", source)`)
rather than leaving the claim untested.
Reproduce evidence: sequential passes are already in the file; the removal argument is source-read.

### Q17-04 — P3 LOW — the "loser adopts the winner" test patches the locking primitive itself and ignores its arguments
`tests.py:1149–1177` (patch at `1163`, stub row built at `1158–1162`).

```python
locked = mock.MagicMock(); locked.get.return_value = winner
with mock.patch.object(Order.objects, "select_for_update", return_value=locked):
```

This does prove the code *calls* `select_for_update` (delete the call and the response would carry
`order_LOSER`, so the test fails) — but it proves nothing about locking, and because `locked.get` is a
`MagicMock` it accepts any arguments, so the `pk=order.pk` scope at `payment.py:151` is unverified: change it
to an `all()` or a wrong filter and the test still passes. The "winner" row is also in-memory only
(`winner.razorpay_order_id = "order_WINNER"` at `1159`, never saved), so the test's own premise — that the
winner's id is **committed** — is not true of anything the database can see. Its sibling
`test_persist_race_adopts…` therefore documents a contract it cannot observe.

Fix: keep it as a call-site pin, but name it that; add `locked.get.assert_called_once_with(pk=order.pk)`, and
move the real contention case to Q17-03's threaded test.

### Q17-05 — P3 LOW — signature verification is mocked to "accept anything", so only the raising branch is pinned and the verifier's arguments are never checked

### Q17-06 — P3 LOW — the currency-freeze test is vacuous: no code path under test can change a stored column on refresh
`tests.py:145–152`.

```python
order = self.create_order()                      # minted under the current config
with override_settings(DEFAULT_CURRENCY="USD"):
    order.refresh_from_db()
self.assertEqual(order.currency, "INR")
```

There is no write between the two lines, so the assertion is a property of `refresh_from_db`, not of any
freezing logic: the test passes against an implementation with **zero** freeze behaviour, as long as the
column exists and `create_order` set it. The comment ("Existing rows keep the currency they were minted
with") states an intent the test cannot contradict. `233–235`/`248–249` (read-only fields) and `98–128` are
the tests that carry the real invariant.

Fix: attempt the mutation the guard is supposed to refuse — `Order.objects.filter(pk=…).update(currency="USD")`
via the admin/serializer, or a full `save()` under the override — and assert the value survives; or assert
the field has no writer (`currency` in `read_only_fields` *and* no view/serializer path assigns it).

### Q17-07 — P3 LOW — the retry test raises `IntegrityError` from patched Python before any SQL, so the DB's post-violation transaction state is never exercised
`tests.py:1082–1097` (`_flaky_save`), used at `1107` and `1133`.

`flaky_save` raises before delegating to `real_save`, i.e. before a single statement reaches the database, and
`assertEqual(len(calls), 2)` (`1114`) asserts on the mock's own counter. So the test proves "an
`IntegrityError` raised inside the loop body is caught and retried once" — which is worth pinning — but not
the thing the flow depends on: that a **real** unique violation on `razorpay_order_id` can be recovered from,
which is engine-dependent (an aborted transaction is not re-usable without a savepoint; the production
comment at `payment.py:167–170` relies on the `transaction.atomic()` savepoint, not on the raise). On the
SQLite test engine the real violation cannot be produced at all (no concurrent writer), so this test is the
best available — but it is mislabelled and should say so.

Fix: rename to `test_persist_retries_a_unique_violation_raised_in_the_write`, or make the retry real by
pre-creating another order holding the same `razorpay_order_id` and asserting the 200 adopts it.

### Q17-08 — P3 LOW — "marks nothing without a matching order" only inspects status events; writes to any other table are invisible

```python
self.assertFalse(order.status_events.exclude(trigger=order_state.TRIGGER_ORDER_CREATE).exists())
```

The path under test does write on this branch — `AuditEvent.record(PAYMENT_SIGNATURE_REJECTED, …)`

### Q17-09 — P3 LOW — the admin seam's whole permission matrix runs on `force_authenticate`, so the 403s prove the capability classes and nothing about how a real privileged caller reaches the endpoint
`tests.py:2242–2506` (first use `2297`; the class never calls `api_login`; `setUp` at `2253–2255` creates a
plain buyer).

Every non-anonymous request in the class replaces `request.user` outright, bypassing the JWT/session stack
and the privileged-login path (`common/testing.py:173–209` exists exactly for that path and is unused here).
Consequence: an endpoint mounted behind a broken/absent authentication backend, or a capability resolver that
never runs, would keep all 20 tests green — only the anonymous case (`2287–2294`) touches the real stack at
all, and it asserts a 403 that DRF produces before any user is known. The 403/200 matrix itself is genuinely
strong (`2296–2300` unprivileged, `2302–2311` finance-scoped-unscoped, `2331–2347` read-only-role write plus
`LogEntry.objects.count() == 0`), so this is a wiring gap, not a coverage hole in the permission logic.

Fix: one end-to-end case using `api_login` with the TOTP-bearing helper + `ROLE_FINANCE` on `GET
/api/admin/orders/` → 200, and `ROLE_FINANCE` on `POST …/cancel/` → 403, to prove the class is reachable by
the real auth chain it will serve in production.

### Q17-10 — P3 LOW — the backfill test down-migrates the shared test database mid-run with no `try/finally`; a failure anywhere in the body leaves every later test on a 0007 schema
`tests.py:177–224` (`TransactionTestCase`), down-leg `182`, restore `218`.

The class's own comment (`204–217`) records that the previous shape of this test stripped later migrations
from **other apps** and "detonated the moment 0013 added a column — every test that ran after this one
inserted into a `products_products` whose schema predated the model." The fix was to make the forward leg a
full `migrate`; the failure mode was not removed, only made less likely. If anything between `182` and `218`
raises — the raw `INSERT` (`188–202`), a `migrate` error, an `Order.DoesNotExist` that never gets to run —
the restore never executes, there is no `tearDown`/`tearDownClass`, and the rest of the run inherits the
down-migrated schema. The test is also order-dependent (`TransactionTestCase` truncates, but the schema it
leaves behind is global).

Fix: wrap the body in `try: … finally: call_command("migrate", verbosity=0, interactive=False)`, or isolate it
in a dedicated test database (`databases` + a settings override) so a failure cannot leak past the class.

## What these tests *do* prove (so the findings above are not over-read)

- Money wire: preview, checkout and item bodies are bytes-checked against the 2-dp string form **and** the
  float form is asserted absent (`508–589`) — the only class in scope that renders.
- Coupon: uniform rejection body by exact dict equality for six reasons (`307–347`), case-insensitivity
  (`369–373`), cap (`376–387`), clamp (`390–400`), free-shipping composition (`403–430`), and the same math
  reaching persisted totals (`1738–1752`); preview/checkout parity on a value that needs quantizing (`597–622`).
- Checkout: client amounts, `status` and `user` are ignored (`636–658`), every cart line snapshotted
  (`660–671`), six required-field rejections (`674–687`), guest refusal precedes cart lookup (`689–719`).
- Stock gate at creation is genuinely read-only (`737–760` — cart line, stock and row counts all pinned).
- Idempotency predicate: seven distinct cases including per-user keying and window expiry (`834–945`).
- Verify: failure keeps the order payable (`1219–1235`), retry then captures (`1237–1259`), replay is
  rejected without double-booking stock, coupon and ledger (`1478–1495`), owner scoping (`1594–1617`),
  mismatched gateway ref (`1555–1565`), one SALE movement per product with `stock_after` (`1396–1440`),
  cart clearing via the order link with no cookie (`1442–1475`), notification enqueued not sent (`1621–1671`)
  and outbox failure not breaking the capture (`1673–1690`).
- Admin: capability matrix and no-side-effect on the denied write (`2331–2347`), one-step fulfilment walk
  (`2395–2410`), terminal-state 409s (`2412–2423`, `2455–2476`), cancel idempotence with a single `LogEntry`
  (`2478–2492`), uniform envelope codes on every error (`2287–2430`).
