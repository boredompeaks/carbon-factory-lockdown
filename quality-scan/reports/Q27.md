## Direct answers to the six focus questions

1. **Does the error envelope swallow a 500 or leak a stack/DB message?** No, on both counts.
   `common/errors.py:91-97` returns `None` for any non-`APIException`, so the exception keeps
   propagating; `_envelope` (100-119) copies only the message and never raises. A 500 reaches
   the client as Django's own page because `config/urls.py` defines no `handler500` (grep: zero
   hits), so the 500 body is HTML and `_json_dict_body` bails on content type. The status code is
   never rewritten. The three `{"error": str(exc)}` sites in the tree (`orders/views/checkout.py:915`,
   `products/views.py:372`, `shipping/views.py:87`) all wrap *domain* exceptions
   (`ShippingUnavailable`, `ValueError` from the stock guard), not `IntegrityError`/`DatabaseError`,
   so no DB text rides through the envelope today.
2. **Is `audit.log_api_action` fail-open or fail-closed on a logging error?** **Fail-closed on the
   record, fail-open on the log line.** The record is a `LogEntry` insert inside the caller's
   `transaction.atomic()` (`products/views.py:139-141`, `orders/views/admin.py:233`,
   `orders/refunds.py:338`), so an insert failure rolls the privileged mutation back. The
   `audit_logger.info` line (`common/models.py:246`) is deliberately outside any gate — logging
   handlers swallow their own errors — which is the right direction, but see Q27-02 for what that
   line lets an attacker put into the log.
   **Secrets/PII:** no leak found. The key denylist (`audit.py:47-89`) covers this project's real
   material (`TOTPDevice.secret`, `User.password`, the Razorpay secret) and every `detail=` payload
   in `orders/webhooks.py`, `orders/views/checkout.py` and `accounts/views.py` carries identifiers,
   amounts or a status word — no credential value under an innocent key. Usernames are retained in
   the log line by an explicit documented decision (`common/models.py:239-245`); email/phone/address
   are not written.
3. **Are roles/capabilities deny-by-default (any truthy path for an unknown role)?**
   Capabilities: **yes, deny**. `CAPABILITY_ROLES` is a closed dict and every lookup uses
   `.get(capability, frozenset())` (`permissions.py:83`, `common/admin.py:176-182`), so an unknown
   or misspelled capability grants nobody; `roles.py` itself has no truthy fallback for an unknown
   role — `get_user_roles` intersects group names with `STAFF_ROLES` (`permissions.py:71`).
   The one allow-by-default path is `user_may_assign_role` (unknown role → `True`,
   `permissions.py:228-230`); it is harmless only because that intersection exists, and it lives in
   Q06's file, so it is not re-reported here.
4. **Does the CSRF/session class correctly exempt bearer requests and enforce session ones?** Yes.
   The exemption is by chain order, not by an `if` — `JWTAuthentication` is first
   (`settings.py:1261-1271`) and DRF stops at the first authenticator that returns a tuple
   (`rest_framework/views.py::_authenticate`), so a bearer request never reaches the CSRF gate.
   Everything else is held to `enforce_csrf`: an active session user (`authentication.py:43-48`)
   and any anonymous request carrying `sessionid` (`49-57`); `CSRFCheck` itself accepts
   GET/HEAD/OPTIONS. The gate cannot be silently lost: the only `authentication_classes([])`
   override in the tree is the signature-verified webhook (`orders/webhooks.py:563`), and the
   class returns `None` so it never changes the resolved identity. Verified sound; no finding.
5. **Does `common/totp.py` verify with a replay-safe step and a constant-time compare?** Yes —
   `last_used_counter` is a monotonic watermark (`totp.py:104`), the caller persists the matched
   counter (`accounts/serializers.py:137-139`, `accounts/views.py:864-868`) and
   `hmac.compare_digest` is used (`106`). The defect is in the *normalization* that runs before
   both: see Q27-01.
6. **Are middleware-added headers/correlation ids attacker-influenced?** The echoed
   `X-Request-ID` is attacker-*chosen* but charset- and length-bounded
   (`middleware.py:47`, `[A-Za-z0-9._:-]{1,64}`), so no CR/LF splitting, no SQL/JSON boundary
   break, and the value is re-validated before it can reach the `AuditEvent.request_id` column.
   One documented-contract deviation in the sanitizer: Q27-07.

## Axis coverage

**1. Invariants.**
- *Money as Decimal, no float on the wire* — held where this flow touches it. The envelope
  re-serialises with DRF's `JSONEncoder`, which would turn a `Decimal` into a float; the one
  scalar context that carries money is already coerced to a 2-dp string
  (`orders/views/checkout.py:592-597`, `money_string`), and `orders/tests.py:519-522` pins both the
  string form and the absence of `5000.0`. `AuditEvent` stores money as `str(...)` at every call
  site. No breach.
- *Audit trail commits or rolls back with the effect* — enforced by transaction placement at each
  write site (`products/views.py:139-146`, `orders/views/admin.py:222-236`,
  `orders/refunds.py:334-342`, `orders/views/checkout.py:889-910`); `AuditEvent.save/delete` refuse
  updates and deletes (`common/models.py:257-268`), so append-only is a model-level invariant, not
  a convention. Holds.
- *Deny-by-default authorization* — holds for capabilities (`frozenset()` defaults) and for the
  admin chrome (`capability_required`/`_any` re-check `is_staff` + capability + superuser bypass);
  `has_view_permission` in `admin_search` denies a model before the query is issued (90-91), which
  is the ordering the "no existence leak" property needs.
- *TOTP replay* — held (`last_used_counter` watermark, see Q5 answer); the *normalisation* before
  it is the hole (Q27-01).
- *Correlation id provenance* — held: bounded charset, length, re-generated on any mismatch, stored
  in a `max_length=REQUEST_ID_MAX_LENGTH` column, reset in `finally` so it cannot bleed across
  requests on a worker thread.
- *One error shape* — held for dict bodies from both producers, with the idempotence guard
  (`_is_envelope`) preventing double wrapping. Not universal for list bodies (`ValidationError([...])`),
  but no view in the tree raises one (grep: zero hits), so it is not reported as a live defect.

**2. Correctness.** Status codes are never rewritten by the envelope; `_envelope` never raises.
The 500 path is sound. Two real defects: the `isdigit`/`int` mismatch (Q27-01) and the
rendered-vs-`.data` mismatch (Q27-04). Timezone: `totp.now()` is one patchable time source
(`totp.py:35-38`), `STEP`/`DIGITS`/`DRIFT_WINDOW` are constants so server and enrollment URI cannot
drift. `update_fields` is present at every `last_used_counter` write. No check-then-act race in
scope: the lock in `test_isolation` is an OS-level byte-range lock, and `admin_search` is read-only.

**3. SAST.** No missing `permission_classes` in scope (all four chrome routes carry a decorator;
`staff_only` covers onboarding). No secrets in code or logs (question 2 above). No raw SQL, no
deserialisation, no SSRF, no unbounded loops (`RESULTS_PER_MODEL`, `MAX_TERM_LENGTH`,
`AUDIT_VALUE_MAX_LENGTH` all bound their loops/values). The two integrity findings are log
injection (Q27-02) and log-adjacent input handling (Q27-07). `onboarding`/`admin_search` render only
labels, URLs and `str(obj)`, each behind that model's own view capability, so no IDOR and no PII to a
third party.

**4. Architecture / smells.** `admin_search.py:71-74` and `onboarding.py:71` read the private
`admin.site._registry`, which is the documented derivation strategy here (a handwritten table would
be a fourth authority) — accepted, not a finding. `common/audit.py` is a proper single gate;
`errors.py` keeps one `_envelope` builder shared by both producers, which is why the shape cannot
drift. Dead code: the middleware except branch (Q27-03). No import cycles — `audit.py` defers
`common.models` to call time precisely to avoid the one that would exist (197-199). `tasks.py` is a
pure `call_command` shim with no policy of its own; its beat entries, task names and command names
agree (`settings.py:778-832` vs `tasks.py:60/72/91`), and none of the three commands can exit
non-zero except by raising a normal exception, so the docstring's "raises on a non-zero command
exit" claim is inert rather than wrong-in-practice. `roles.py` is a table + one idempotent
`get_or_create` loop, called only from the two data migrations; no truthy default anywhere.

**5. Test side.** Which tests would fail if the guard were deleted?
- `tests/test_csrf_security.py` — yes (session and guest-cart mutation without `X-CSRFToken` must
  403); `cart/test_csrf.py` pins the boot GET issuing the cookie.
- `tests/test_test_isolation.py` — yes, including a **real second process** refused through a
  subprocess (`:339-370`), which is the only way to prove an OS lock.
- `tests/test_error_envelope.py` — yes, and it asserts rendered bytes rather than `.data`, which is
  the correct discipline; `tests/test_audit_structured.py` pins the denylist against the real model
  fields rather than a typed-out list.
- `tests/test_correlation_ids.py` — yes for the header on the real chain (`:102-106`), but
  `:108-118` covers an impossible path (Q27-03).
- No test would fail if the audit log line were dropped, if `clean_audit_value` stopped escaping
  (it never escaped), if `held_by_user` were removed from the onboarding page, or if the search
  count were removed — i.e. Q27-02/05/06 sit in the "no test names the property" band.
- Axis-1 invariants with **no** test: (a) an attacker-chosen string cannot break one audit log line
  per event; (b) the onboarding page's query count is bounded; (c) the global search's scan cost is
  bounded. (Money-as-string, audit-transaction coupling, replay watermark and deny-by-default all
  have real pins.)
