The head-line answers to the brief:

- **Is a backup a verified, restorable artifact?** No. Nothing verifies the
  bytes: `size` is read and printed, never asserted; no `fsync`, no checksum, no
  `pg_restore --list`. The only integrity signal is `pg_dump`'s exit code, and
  Q25-01 defeats even that. The one verification the success message names
  (`restore_drill`) cannot read the artifact at all.
- **Path/credential handling in the dump?** Good, and deliberately so: no shell
  (`subprocess.run` with a list argv, no `shell=True`), no path built from user
  text (`--output-dir` is a path the operator typed, not data), connection
  identity only in the child's `PG*` env, argv carries flags only
  (`postgres identity in argv` is genuinely closed). No traversal and no shell
  injection found.
- **`purge_notification_outbox` and live rows?** It does NOT exclude a leased
  row (Q25-04), and it is unbounded (Q25-05).
- **`restore_drill` on a scratch DB?** Yes — genuinely structural: the scratch
  alias is registered on `connections` only, never in `settings.DATABASES`
  (`restore_drill.py:214-238`), `mode=ro`/refusal rules hold, and the teardown
  is in `finally`. Its *refusal* correctness is sound; its *verification* is
  weak (Q25-10) and mis-advertised (Q25-03).
- **Ops views: capability + POST-only + CSRF?** There is no mutating ops view in
  this flow — every route is `GET` (`health`, `health_detail`, `api_settings`,
  `dashboard`, `audit_log`), so CSRF/POST-only is N/A by construction, not
  skipped. Capability enforcement is correct and tested: `dashboard` and
  `audit_log` use `@capability_required` (a plain-view decorator doing
  superuser-OR-(is_staff AND capability), `permissions.py:141-142`),
  `health_detail` uses `[HasReportsRead]`. No inline `is_staff`.
- **Commands guarded only by a docstring?** `purge_notification_outbox` is
  scheduled (beat entry `settings.py:819-821`), so not docstring-only; but
  `backup_db` has no scheduler in-tree and its docstring (29-33, 43-44) is the
  only place the retention/failure contract is stated besides the runbook — and
  the runbook's verification claim is false (Q25-03).

## Q25-01 | P2 HIGH | CODE | `backup_db.py:472-474` (+188-193, 476-492)

**Two backups in the same second write the same `.partial` path, so they corrupt
each other's dump and both report success.**

`unique_path` is a check-then-act:

```
181 def unique_path(directory, name):
188     candidate = Path(directory) / name
190     while candidate.exists():
191         candidate = ... f"{Path(name).stem}-{index}{Path(name).suffix}"
```

and the stamp is second-resolution (`utc_stamp`, `%Y%m%dT%H%M%SZ`). The pg path
computes `destination` *before* dumping (472) and derives the partial from it
(474): `partial = f"{destination}.partial"`. Two runs in the same second — cron
firing on the boundary plus the manual run the docstring explicitly names at
184-187 — both get the identical `destination` and therefore the identical
`partial` path, and both `open(partial, "wb")` (476), i.e. two independent fds at
offset 0 on one inode with `O_TRUNC`.

On Linux (production, docker) each child writes from its own offset, so the two
`pg_dump` streams overwrite each other from byte 0: the surviving file is a
patchwork of two custom-format archives — corrupt, not merely truncated. Both
children exit 0, so both `os.replace` (492) and both print
`Backup written: … (N bytes)` (361-365). The first run's artifact is destroyed
by the second run's fd, which keeps writing into the inode after the first
`replace` renamed it. Retention then counts a single file (prune, 239-265), so
the operator is left with one backup, zero valid ones, and two success lines.

Windows would fail loudly instead (`os.replace`/`open` sharing violation), which
is why the test suite cannot see it: `test_two_backups_in_the_same_second_do_not_overwrite_each_other`
(`tests/test_backup_db.py:425-434`) runs the two invocations **sequentially**, so
the second call's `unique_path` already sees the first file and appends `-1`.
The concurrency invariant the docstring claims ("a backup can never overwrite an
existing dump", 34-36) has no test that exercises concurrency.

Fix direction: `os.open(..., O_CREAT|O_EXCL)` on the partial (or `mkstemp` in the
directory) so the reservation is atomic, and derive the partial from the
exclusive handle rather than from `unique_path`'s answer.

## Q25-02 | P2 MEDIUM | CODE | `backup_db.py:359` (+361-365, 492, 579)

**The dump is never verified after it is written; the byte count is decorative.**

```
357  directory.mkdir(parents=True, exist_ok=True)
358  destination = self._dump(...)
359  size = destination.stat().st_size
361  self.stdout.write(f"Backup written: {destination.name} ({size} bytes, ...")
```

`size` is printed and nothing else. There is no `size > 0` assert, no
`pg_restore --list` / `sqlite3 PRAGMA integrity_check` on the finished artifact,
no checksum recorded anywhere (the runbook does not ask for one either), and no
`fsync` of the file or of the directory before `os.replace` (492) — so the
success line can be printed for a file whose bytes are still only in the page
cache and are lost to a power cut at 02:30:01. The sqlite branch has the same
shape (`579` replace, no integrity check; `517-518` catches the *copy* failing,
not the copy being wrong).

The absence is honest about itself — it does not claim a checksum — but the
brief's question is answerable: nothing here establishes "restorable". The
fabricated-integer hazard is real too: `size` is the only number the operator
sees, and it is never a gate.

**Test side:** the fake child always writes a valid `DUMP_BODY`
(`tests/test_backup_db.py:146-148`), so no test supplies `returncode=0` with an
empty or truncated body. Deleting a hypothetical `if size == 0: raise` guard
would not turn any test red — the invariant "a file in BACKUP_DIR is a
restorable archive" has no test.

I am explicitly NOT claiming that an exit-0 `pg_dump` produces a truncated
archive by itself (source-read only; on that path the exit code is a real
signal). The reachable corruption is Q25-01.

## Q25-03 | P2 MEDIUM | CODE | `backup_db.py:371-377` (+`restore_drill.py:180,206,249`, runbook 546-548, 685-687)

**The operator is told to verify the dump with `restore_drill`, which cannot
read the dump.**

```
371  self.stdout.write(self.style.SUCCESS(
373      "Backup complete. To restore, follow docs/runbook-incident-recovery.md
375       section 3a - a dump is only useful once it has been restored into a
376       FRESH database and verified with manage.py restore_drill."))
```

`restore_drill` rehearses a `dumpdata` JSON fixture (206-207) into a **sqlite**
scratch database built by `migrate` (243-249). It has no flag, no branch and no
import that opens a `.dump` file: `HANDLE` takes `--database`, `--dry-run`,
`--simulate-failure` and nothing else (126-146). So the artefact `backup_db`
just wrote — custom-format pg_dump, or a `.sqlite3` page copy — is never the
thing being verified. A truncated `.dump` and a healthy one produce identical
`restore_drill` output.

The runbook repeats the claim twice: "the dump it rehearses is this command's
output" (546-548) and "`manage.py restore_drill` proves the *format*
round-trips ... run it on every release" (685-687). An operator who follows the
backup command's own success message concludes the security-critical property
("we can restore") was just tested. It was not.

Fix direction: either `restore_drill` gains a `--artifact <path>` mode that
`pg_restore -l` / restores into a scratch DB, or the message and the runbook stop
naming it as dump verification and say plainly that nothing in-tree verifies a
dump.

## Q25-04 | P2 MEDIUM | CODE | `purge_notification_outbox.py:83` (+`common/notifications.py:757-762, 1042-1044`)

**The purge deletes a row that is claimed and leased by a live worker, silently
dropping a notification the outbox exists to guarantee.**

```
82  cutoff = timezone.now() - timedelta(seconds=grace)
83  spent = NotificationOutbox.objects.filter(expires_at__lte=cutoff)
90  doomed, _ = spent.delete()
```

The predicate is `expires_at` only. It does not consult `status` and it does not
consult the lease (`next_attempt_at`), which is the column that says "a worker
owns this row right now" (`models.py:395-408`). The claim predicate
(`notifications.py:757-762`) is `status IN claimable AND next_attempt_at <= now
AND expires_at > now`; a worker can claim a row at `expires_at - 1s` with the
default 60s lease, and the purge can then delete it a second later.

Downstream, `_deliver` re-reads the row after the claim:

```
1042  row = NotificationOutbox.objects.filter(pk=pk).first()
1043  if row is None:
1044      return DrainOutcome.VANISHED
1045  try: context = resolve_context(row.payload)
```

so the send is skipped, nothing raises, the outcome is logged at INFO
(`879`), and there is no retry — the row that was supposed to be delivered is
gone. The docstring's justification (18-24) covers exactly two cases, "drained"
and "stranded"; a row **in flight** is neither, and it is the one case where
deletion loses mail rather than a spent payload.

The window is narrow (TTL default 3 days, lease 60s), so frequency is low; the
mechanism is certain from source. A `--dry-run` cannot reveal it and no test
covers it: `test_the_purge_command_deletes_expired_rows_and_keeps_live_ones`
(`tests/test_notification_outbox.py:450-465`) only distinguishes expired from
inside-window, never claimed-from-unclaimed.

Fix direction: exclude `next_attempt_at__gt=now` (a live lease) and/or restrict
to `status__in=(SENT, DEAD)` plus pending rows whose lease has lapsed.

## Q25-05 | P2 MEDIUM | CODE | `purge_notification_outbox.py:90` (+29-34, `settings.py:620-621`)

**The delete is unbounded: one statement, no batch, no limit, on a table the
docstring says accumulates.**

`.delete()` on the filtered queryset issues a single `DELETE ... WHERE
expires_at <= cutoff` (the model has no foreign keys — `notifications.py:752-755`
says so — so there is no collector batching to bound it). Every other sweep in
this substrate is bounded by an explicit knob: `NOTIFICATION_OUTBOX_DRAIN_BATCH_SIZE`
(100, `settings.py:620-621`), `NOTIFICATION_OUTBOX_LEASE_SECONDS`,
`_MAX_ATTEMPTS`, retry caps. The purge has none, and the command has no
`--batch`/`--limit` flag (57-75).

This is not theoretical: the same docstring states "nothing in this repository
schedules it" (29-34) — an operator runs it by hand, so the first run is exactly
the run against a table that has been accumulating since the last manual run.
On PostgreSQL a multi-million-row single-statement delete means one long
transaction, WAL amplification and lock retention on the table the drain worker
is trying to claim from, i.e. the compensating control can stall the thing it
compensates for. (Scheduling was added later — `settings.py:819-821` beat entry,
`common/tasks.py:91-100` — so the docstring is now itself stale, and the
unboundedness becomes a periodic risk rather than a one-off.)

## Q25-06 | P2 MEDIUM | CODE | `views.py:87-91` (+`alerts.py:107-118`, `settings.py:580`, `docker-compose.yml:206-208`)

**The public health probe performs a blocking synchronous SMTP send per
recipient, so during an incident it occupies a gunicorn worker for up to
N × EMAIL_TIMEOUT on every poll — the monitor becomes the outage the docstring
says it cannot.**

```
87   checks = health.get("checks") or {}
89   alerts.notify_integration_outage(f"status=... {checks_text}".rstrip())
```

`notify_integration_outage` → `_send`, which loops the recipients and calls
`notifications.send_email` **inline** (`alerts.py:107-118`), with
`fail_silently=False` (`notifications.py:98`) and `EMAIL_TIMEOUT = 10`
(`settings.py:580`). The view's comment at 75-79 promises the opposite: "the
dispatch ... cannot alter the response — the monitor must never become the
outage it reports". It cannot alter the *body*; it does hold the worker and the
response for up to `len(ALERT_RECIPIENTS) × 10s`.

Concretely, with 2+ staff mailboxes and an SMTP host that is unreachable while
the DB is degraded (the exact simultaneous-failure case the alert exists for),
`/health/` takes ≥20s while the compose healthcheck allows 10s
(`docker-compose.yml:206-208`), and gunicorn runs 3 workers
(`backend/Dockerfile:134`) — sustained external polling of a public,
unauthenticated URL is enough to hold all three. The alert's own dedupe does not
bound the *latency*: the 300s cooldown suppresses sends, but the cooldown state
is a `FileBasedCache` under `BASE_DIR/alert_cache` (`settings.py:1070-1077`)
with no compose volume (`docker-compose.yml:169-172` mounts only `media_data`),
so a container restart mid-incident clears it and the next degraded poll sends
again.

Confidence is M, not H: the latency chain is source-read, the worker count and
timeouts are read from the repo, but I did not run a container. The class of
defect is real regardless of the numbers — a network send on the release-time
waiter's path.

Fix direction: hand the alert to a thread/task, or gate it on a cheap
pre-check that is not inside the probe's response path.

## Axis notes (explicit, per contract)

**1. INVARIANTS.** Enumerated and checked: (a) *a file in BACKUP_DIR is a
restorable archive* — NOT held (Q25-01, Q25-02), no test. (b) *retention deletes
only this command's dumps* — HELD and well tested: stamped-glob + content
signature + `keep >= 1` refusal, and the prune loop leaves unreadable files alone
(`is_own_dump` 213-236, tests 525-640). (c) *the backup source is only read* —
HELD: `mode=ro` URI (573), client-side dump, no DDL path. (d) *connection
identity never reaches argv/logs* — HELD: `_pg_argv` 506-522 is flags only,
`PG*` env 524-541, `scrub` redacts by value and by shape (154-165), tested
(250-345). (e) *purge never deletes a notification still owed* — PARTIALLY held:
inside-window rows are safe (tested), a leased in-flight row is not (Q25-04).
(f) *the drill never touches a live DB* — HELD, structurally and tested
(`tests/test_restore_drill.py`). (g) *money stays Decimal* — HELD in
`seed_shipping_methods` (`quantize_money`, `is_finite`, `>= 0`); no float
anywhere in the flow. (h) *authz = capability, not inline staff* — HELD and
tested for all five ops routes. (i) *state machines have one owner* — the outbox
status vocabulary has one writer per transition (`_claim`/`_record_*`); the purge
is the one deleter and is named in the model docstring (321-322).

**2. CORRECTNESS.** Checked for wrong status codes, swallowed exceptions,
`update_fields` omissions, tz, pagination order. `health`'s 200/503 contract is
correct and tested; `audit_log` uses `Paginator.get_page` (bad `?page=` degrades to
page 1) with `-action_time` ordering, so pagination is stable. `_seeded` amounts
are quantized. `email_send_probe` aborts on the first failing recipient (partial
send), which is the honest failure direction. The one shared-state tz question —
`cutoff` vs model-written `expires_at` — is consistent (`timezone.now()` both
sides).

**3. SAST.** No shell injection (no `shell=True`; argv is a list of constants);
no path traversal (paths come from `--output-dir`/`BACKUP_DIR`, never from data);
no secret in argv; secrets scrubbed from third-party stderr; no raw SQL; no
unsafe deserialization (`loaddata` reads a file this command just wrote to its
own temp dir); no IDOR (no object pk in any ops route); `api_settings` explicitly
whitelists its keys instead of dumping the model (132-156). Error leakage: the
alerts/file paths log exceptions with tracebacks at ERROR (self-hosted logs,
acceptable). The one unauthenticated side effect is Q25-06.

**4. ARCHITECTURE.** Layering is good — views delegate to `ops/services`, alerts
to `ops/alerts`, mail to `common.notifications.send_email` (single send path,
which `email_send_probe` correctly uses). Real smells: Q25-09 (duplicate
aggregates), the `BACKUP_DIR`/`BACKUP_RETENTION` knobs read by raw `os.getenv`
inside the command (`backup_db.py:414, 322`) with **no `BACKUP_*` key in
`config/settings.py` at all** (grep: zero matches) while every sibling knob
(`NOTIFICATION_OUTBOX_*`, `ALERT_*`, `EMAIL_TIMEOUT`) is a settings value — so
these two cannot be validated, defaulted or overridden the way every other knob
is, in a module whose own docstring (389-392) argues settings is the single
parser. P4 INFO, no row.

**5. TEST SIDE.** Named gaps, each tied to an axis-1 invariant with no test:
(i) dump integrity under concurrency — `test_two_backups_in_the_same_second...`
(`test_backup_db.py:425-434`) is sequential; (ii) dump integrity at all — the
fake child always writes `DUMP_BODY` (146-148), so no test drives `returncode=0`
+ empty bytes and no test asserts the artifact's signature/size; (iii) purge vs
a leased row — `test_notification_outbox.py:450-465` never sets `attempts`/
`next_attempt_at`; (iv) restore value corruption — `_corrupt_restored_copy` only
deletes (Q25-10); (v) the tag's duplicate queries (Q25-09). Positive: the
credential-redaction, retention-safety, refusal-path and capability-gate tests
are hand-written literals, not recomputed oracles, and would fail if the guards
were deleted.
