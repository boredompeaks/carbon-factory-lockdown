## Direct answers to the four brief questions

1. **Does the scheduling test pin the beat schedule *and* that each entry's task exists?** **The schedule/registration half: yes, and it is the strongest pin in the four files.** Key set is compared against a hand-written literal tuple (`:93-97, 103-110`) so an oracle cannot agree with a wrong constant; each entry's `task` string is compared to `f"common.tasks.{command}"` (`:112-121`); and registration is checked against the app's own registry with **function identity** — `assertIs(registered[dotted].run, getattr(tasks, command).run)` (`:141-144`) — which is the same lookup a worker's `NotRegistered` failure comes from. Deleting an entry, renaming a task, or scheduling an unregistered dotted path all fail. **The cadence half: no.** All three `CELERY_BEAT_*` knobs are bounded, never wired: the drain is asserted `remaining <= configured` (`:801-806`), so a hard-coded 60 s interval passes with the setting at any value ≥ 60; `CELERY_BEAT_EXPIRE_EVERY_MINUTES` is never read by any test on any line; `CELERY_BEAT_PURGE_HOUR` is never read either — the off-hour pin reads `fire.minute` only (`:874-876`). The knob-documentation test (`:909-941`) greps `settings.py` for the key **as a quoted string**, which a dead `X = _env_positive_int("KEY", 60)` assignment satisfies on its own. The file's own docstring records that this exact defect already shipped once ("`CELERY_BEAT_DRAIN_OUTBOX_SECONDS` was documented in `.env.example` … while the schedule read a literal, and it was found by checking rather than by a test", `:913-917`) — the pin added for it cannot catch the recurrence. See `Q13-01`.
2. **Does the outbox test drive two workers concurrently or sequentially?** **Sequentially — there is no threaded or multi-process test anywhere in `test_notification_outbox.py`, and no `claim_next_notification`/lease/`select_for_update` assertion at all.** That is *correct for this file's subject* (enqueue-side storage, transaction join, dedup identity, retention), and the dedup test legitimately relies on the DB unique constraint rather than on a race (`:284-294`). The two-worker proof exists, but in `tests/test_notification_outbox_worker.py:848-1063` (`OutboxTwoWorkerTests`, `threading.Barrier(2)`, `close_old_connections` per worker) — outside this flow. One defect noticed there while confirming: on the SQLite gate that test's mutual-exclusion assertion is `row.attempts <= 1` (`:945-949`), which is satisfied when **both** racing claims are refused (`:917-919` tolerates any `OperationalError` mentioning "lock"), and the `assertEqual(row.attempts, 1)` half is gated on `connection.features.has_select_for_update` (`:950-955`). Logged as an out-of-scope handoff, not counted here.
3. **Does `test_sentry.py` prove scrubbing (secrets/PII absent from the event) or only that `init()` was called with options?** **Only that options were passed.** `test_the_reporting_shape_is_pinned` asserts `send_default_pii is False`, `max_breadcrumbs == 20`, `attach_stacktrace is False`, `traces_sample_rate == 0.0` (`:196-198`) — kwargs handed to the SDK. `common/sentry.py` contains **no redaction at all**: `before_send` returns the event object unmodified on the allowed path (`sentry.py:334`), and `test_a_normal_path_and_exception_pass` asserts exactly that identity (`:312`). So an exception whose *message* embeds a token, or a breadcrumb whose text embeds an email, is forwarded verbatim and there is no test that would fail. The one mechanism that could prove the absence of secrets from a real serialized payload exists and is used only as a counter: `RealSdkTransportTests` captures real envelopes in `self.transport.envelopes` (`:586-592`) and asserts `len(...) == 1` (`:624`) — the envelope bodies are never inspected. That is a new mechanism (not QC-025, which is the init-options gap); see `Q13-06`.
4. **Are staff-role tests asserting capability enforcement or role assignment only?** **Both, and they are the best-built of the four files.** Enforcement is exercised through the real admin view (403 from the change gate at `:253, 269, 624`), through `save_model` off-flow (`:649-667`), and through `_apply_staff_roles` directly (`:669-686`); least privilege is pinned on the rendered `fieldsets`, not on intent (`:160-173`). What is *not* asserted is the third leg of the chain: **no test proves that a role granted through this surface actually confers its capability** — the `user_has_capability` call at `:255` only re-states the static support-role map, and the role→capability matrix is pinned elsewhere (`test_superadmin_tier.py:245-269`) against fixtures, not against a grant made here. Also, the confirm step's *own inputs* are never replayed by the tests (`Q13-08`), and one test's stated invariant is never asserted (`Q13-09`).

### Q13-04 | P3 / LOW | CODE | `backend/tests/test_notification_outbox.py:177-179`
**`test_a_repeated_element_in_a_set_is_described_once` is a tautology: `{"alpha", "alpha"}` is already `{"alpha"}` before `serialize_context` is called, so the assertion never reaches the behaviour it names and no plausible implementation can fail it.**
