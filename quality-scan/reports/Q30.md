## FINDINGS

### Q30-01 · P2 HIGH · CODE · Confidence H · NEXT-BUILD
`backend/accounts/views.py:450` (mint), `:759` (accept) — **a verification token is a valid password-reset token.**

`_send_verification_email` (`:448-460`) and `request_password_reset` (`:720-721`) both call the *same object*, `default_token_generator` (`from django.contrib.auth.tokens import default_token_generator`, `:7`), and `verify_email` (`:630`) and `reset_password` (`:759`) both accept it with the same `check_token`. Django's token is `timestamp + hash(pk, password, last_login, email, timestamp)` — there is **no purpose/salt component**, so the two flows are cryptographically interchangeable.

Consequence: a registration or `resend-verification` link, delivered to an inbox and therefore living in browser history, `Referer` headers, mail-provider logs and the user's mail archive, is a working **password-reset** credential for the account that owns it, for `PASSWORD_RESET_TIMEOUT` (Django default 3 days, unset in `settings.py`). Every `make_token` call in the interval yields another independently valid token, and a successful `verify_email` does **not** consume any of them (activation writes `is_active`, which is not in the hash). Only a password change or a first successful login (`update_last_login` mutates `last_login`, invalidating the hash) retires them — so the highest-risk population is exactly the accounts that registered, received the link and never logged in.

Reproduction (source-read, no execution): register → read `token` from the verification email → `POST /api/accounts/password-reset/confirm/ {"uid": <encoded pk>, "token": <that token>, "password": "<new>"}` → 200 and the password changes. `tests.py:253-262` already drives the reset endpoint with `default_token_generator.make_token(reset_user)` for an arbitrary user, which is the same token the verify flow mints.

Not V-17. V-17 records "verification tokens remain valid after activation" (replay into `verify-email`, a no-op). This is a different mechanism with a different outcome: replay into a **credential-changing** endpoint. `backend/docs/vulnerabilities.md:36` claims "Password reset / username lookup flows are enumeration-safe (uniform responses)" and no doc claims purpose separation exists.

Fix shape: give the verification flow its own `PasswordResetTokenGenerator` subclass with `key_salt = "accounts.verification"` (or `signing.Signer` salt), and make `verify_email`/`reset_password` reject the other class's tokens. One `_send_link_email(purpose, user, path)` helper would also remove the duplicated context-building that let the two mints drift.

### Q30-02 · P2 MEDIUM · CODE · Confidence M · NEXT-BUILD
`backend/accounts/views.py:418-431` + `:773-796` — **a session created during a password reset survives the reset.**

`_blacklist_user_refresh_tokens` iterates `OutstandingToken.objects.filter(user=user)`, a snapshot of committed rows, and the docstring at `:419-428` claims "the sessions die exactly when the change lands". No row is locked. A concurrent `POST /login/` (the reset endpoint and the login endpoint are different transactions on different connections) executes `RefreshToken.for_user` → inserts its own `OutstandingToken`, commits **after** the reset's snapshot but **before** its commit, and is therefore never blacklisted. The reset then commits its password change and reports success.

The attacker population that matters is the one that *holds the old password* — the reason a victim resets at all. That session keeps minting access tokens for the full `REFRESH_TOKEN_LIFETIME` (7 days) while the victim believes every session was killed. [R-17.10] as implemented is "sessions that existed when the reset read the table", not "no window where old sessions outlive new credentials".

The repo already owns both halves of the fix: `_lock_user_addresses` (`:50-61`) takes the owner-row lock as the single serialization point for exactly this "nothing to lock yet" shape, and `orders` takes the user-row lock for idempotency-key collisions (`changes.md:369`). Adding `User.objects.select_for_update().get(pk=user.pk)` at the top of the reset transaction closes it, with lock order User→(token rows), matching every other writer.

Secondary: the loop is an unbounded per-row `get_or_create` (N queries + N inserts) inside the credential-change transaction; a `bulk_create(..., ignore_conflicts=True)` keeps the lock hold short.

Test: sequential only; see axis-5 table. Marked Confidence M because the interleaving is source-read reasoning, not an executed probe (suite execution is forbidden to this flow).

### Q30-03 · P2 MEDIUM · CODE · Confidence H · NEXT-BUILD
`backend/accounts/views.py:670-673`, `:700-703`, `:734-739` — **the "uniform response" recovery endpoints are a three-way account oracle.**

Each endpoint answers a pinned uniform 200 for every input — but only when nothing is sent. When an account **does** exist, `notifications.send_email` runs synchronously inside the request (`common/notifications.py:92-100`: `render_to_string` → `send_mail(fail_silently=False)` → `logger.info`), and its failure is converted into a **503 carrying a distinct message**:

- `password-reset/` → 503 only if an **active** account exists.
- `resend-verification/` → 503 only if an **inactive** account exists.
- `forgot-username/` → 503 if **any** account exists.

During any SMTP degradation an anonymous attacker classifies an address into absent / active / inactive from the status code alone. With SMTP healthy, the same three endpoints still leak the same bit through **time**: an existing account pays a full SMTP round trip (bounded by `EMAIL_TIMEOUT`) that a nonexistent one does not — a difference measured in tens to hundreds of milliseconds against a zero-I/O baseline, statistically separable with a handful of samples. Neither the status nor the timing side-channel is covered by `test_uniform_response_regardless_of_account_state` (`tests.py:518-532`), which compares only two 200 bodies.

The uniform body is the control that is supposed to prevent exactly this, and it is defeated by a branch three lines below it. Fix: move the send off the response path (`notifications.enqueue`, already the substrate at `common/notifications.py:563` and already used by the payment path) and return the uniform 200 unconditionally, letting the outbox report failures to operators instead of to anonymous callers.

### Q30-04 · P2 MEDIUM · CODE · Confidence M · NEXT-BUILD
`backend/accounts/views.py:853-868` and `backend/accounts/serializers.py:126-136` — **the TOTP replay watermark is check-then-act; one code can be spent twice under contention.**

Both sites do the same three steps with no concurrency control: read `device.last_used_counter` off a plain (unlocked) `TOTPDevice` instance, `totp.verify_code(...)` against it, then `device.save(update_fields=["last_used_counter"])` — an unconditional `UPDATE` of the whole column. Two requests in flight with the same code both read the old watermark, both verify (the code is inside the ±1-step window), and both write. Both then proceed to their side effect: the login serializer mints a token pair, `_consume_code`'s callers (`MFAConfirmView:984-998`, `MFADisableView:1025`, `MFATrustDeviceView:1067`) flip state.

The replay guard is the *entire* anti-replay story for a 30-second credential ("`last_used_counter` is the replay guard … a code already consumed for this device can never verify again", `docs/conventions` aside, `common/totp.py:88-93`). Its purpose is defeated by concurrency, and the existing test (`test_mfa.py:749-758`) is sequential so it cannot see it.

This is the same class the repo has already solved twice: `_lock_presented_refresh` (`:304-328`) locks the `OutstandingToken` row inside the rotation transaction for exactly this "check-then-write on a one-time credential" shape, and `_lock_user_addresses` locks the owner row. The TOTP half was left out. Fix: `TOTPDevice.objects.select_for_update().get(pk=device.pk)` (or reload under lock) before `verify_code`, or a conditional `filter(pk=..., last_used_counter=old).update(...)` and treat 0 rows as a replay loss. Marked M: inferred from the absence of any lock or conditional write, not from an executed two-thread probe.

### Q30-05 · P2 MEDIUM · CODE · Confidence H · NEXT-BUILD
`backend/accounts/views.py:823-834` — **the MFA enrollment surface authenticates credentials and writes no audit event, on success or failure.**

`_authorize_enrollment` calls `authenticate(request=..., username=..., password=...)` for any anonymous caller and returns a 401 on failure (`:831-834`) or an authenticated user for the bootstrap path. Neither outcome reaches `AuditEvent`: `AuditEvent.EventType.AUTH_LOGIN_FAILED` and `AUTH_LOGIN` are written only by `LoginView._record_login` (`:156-170`), on the login doors.

[R-7.20] as implemented by `LoginView` is "successful (200) and rejected (400/401) attempts each land an audit event". `mfa/setup/` and `mfa/confirm/` are two more doors that accept a username+password over `AllowAny` + `permission_classes = []` (`:913`, `:969`) and refuse with 401 — so password guessing against a privileged account leaves zero forensic record at either door, while the identical guessing against `login/` leaves two rows per attempt. The `AUTH_REGISTERED`/`AUTH_EMAIL_VERIFIED`/`AUTH_PASSWORD_RESET` trail shows the module's own standard: every other credential event is recorded.

The successful bootstrap is the more serious omission: it is an authentication that then mints (or rotates) a second factor and can re-open login for the account, yet it is invisible to the abuse stream that `ops.alerts` and the audit log page are built from.

Fix: mirror `_record_login` inside `_authorize_enrollment` (failure → `AUTH_LOGIN_FAILED`, success → `AUTH_LOGIN` or a dedicated `AUTH_MFA_BOOTSTRAP` event type) with `detail={"username": ...}`.

### Q30-07 · P3 · CODE · Confidence H · FOLD-INTO-NEXT
`backend/accounts/views.py:758` + `:764-769` — **a non-string `password` returns a 500 on the public reset endpoint.**

`password = payload.get("password", "")` reads the field straight out of parsed JSON; this endpoint has no serializer, so nothing coerces it. `validate_password(password, user)` (`:765`) loops the configured validators and re-raises anything that is not `ValidationError` (`venv/Lib/site-packages/django/contrib/auth/password_validation.py:41-57`); the first validators call `len(password)` / `password.lower()` (`:108`, `:157`). `POST {"uid": <valid>, "token": <valid>, "password": 12345}` therefore raises `TypeError: object of type 'int' has no len()` → 500.

Reachability is bounded by needing a valid token, and DRF's `CharField` coercion protects the registration path (`serializers.py:32`), which is why this is P3 rather than P2 — but a 500 on a public endpoint from a shape-only body is still a defect, and the file's own defensive posture elsewhere (`:627,663,688,716,755,812` — every one of them handles a non-object body) shows the non-string *value* case was simply not considered. Fix: `password = payload.get("password") or ""` plus `if not isinstance(password, str): return 400`, or put a `Serializer` in front of the endpoint.

### Q30-08 · P3 · CODE (test) · Confidence H · FOLD-INTO-NEXT
`backend/accounts/tests.py:1861-1868` vs `backend/accounts/views.py:60` — **the address-lock test asserts the wrong lock, so the only lock that serializes the *first* default can be deleted green.**

`_lock_user_addresses` deliberately takes two locks in order: the owner row (`User.objects.select_for_update().get(pk=user.pk)`) and then the owner's `is_default` rows. The docstring explains why the row lock alone is insufficient: "there is nothing to lock yet, so two concurrent creates would both win."

The test patches **`Address.objects.select_for_update`** only and asserts `assert_called_once()`. Deleting line 60 removes the serialization point and the test still passes — under a name ("`test_default_flip_locks_the_owners_rows`") that reads as coverage of exactly the guard it does not touch. This is the recorded "a test that cannot fail against the code it guards is worse than no coverage" trap (`spec-run-state.md:197`), surviving in the accounts suite.

Fix: assert both locks, and prefer driving the lock order rather than the call count — e.g. patch `User.objects.select_for_update` too and assert it was entered *before* the `Address` queryset, or assert the guard's real effect (two concurrent creates ⇒ exactly one `is_default=True`) on Postgres.

### Q30-09 · P3 · CODE · Confidence H · FOLD-INTO-NEXT
`backend/accounts/views.py:600-603` vs `backend/accounts/serializers.py:53-56` — **the username rule the probe publishes is not the rule registration enforces.**

`username_available` answers `{"available": False, "message": "Username must be at least 3 characters."}` for anything shorter than 3 after `strip()`. `RegisterSerializer` imposes exactly one username rule — `username__iexact` uniqueness — and Django's `User.username` carries no `MinLengthValidator`. So `POST /register/ {"username": "x", ...}` succeeds with 201 for a value the availability probe calls unavailable, and the storefront form that consumes the probe (`/username-available/`) and the form that consumes the registration endpoint disagree about the same field.

This is a functional inconsistency on the sign-up path, not a style nit: a user is told a name is unusable and can register it anyway, and short names become permanent public identifiers (they appear in `str(Address)`-style references and in the audit stream). Fix: one shared `USERNAME_MIN_LENGTH` constant consumed by both, or a `validate_username` length check in the serializer.

### Q30-10 · P3 · CODE · Confidence H · FOLD-INTO-NEXT
`backend/accounts/views.py:140-145` + `:554` — **the guest-cart merge runs after the account/token is committed and after the success audit row, so its failure 500s a successful login/registration.**

Login: `:127` mints the token pair (writing an `OutstandingToken`), `:135` writes `AuditEvent.AUTH_LOGIN`, then `:142` calls `merge_session_cart_into_user_cart` with no surrounding transaction. Register: the user row and `AUTH_REGISTERED` commit inside `:543-549`, then `:554` merges.

If the merge raises, the client gets a 500 with no `Set-Cookie` and no tokens it can use (the minted refresh token exists in the DB and is never delivered), while the audit trail records a successful authentication that the client never received; a retried login works, a retried registration now 400s "username already taken" for an account the client believes failed. The response contract (`201`/`200` with an optional `cart_id` added additively, per the `:553` comment) is what makes the failure silent.

Fix: either wrap the merge in `transaction.atomic()` with the account creation (making "user + cart attached" one unit), or catch and log the merge failure and still return the token/201 — the `cart_id` key is already optional, so degrading to its absence is contract-legal. Note `apps.merge` is a cart-service call, so the fix belongs at the call site, not in `cart/services.py`.

3. `backend/common/notifications.py:100` → **owning notification/async flow**. `logger.info("email sent template=%s to=%s", template_name, recipient)` writes the customer's email address to the application log on **every** transactional send, including all three Q30 recovery flows.
