## Direct answers to the brief's questions

1. **Can `changelog_figures.py check` pass with no artifact behind a figure?** For a figure with *no* artifact named after its task: no, it flags. For the far more useful attack — an artifact that carries **nothing**: yes. `artifact_for` (`:765-783`) returns `floor.exists()` for every kind except `mutation`; the file is never opened, so its `task`, `engines`, `run` and `coverage` are never compared to the figure. Probed: a row reading `Ran 9999 tests, cov 12.34%, xf 99` with the sole backing file `{"task":"T-EMPTY","kind":"floor"}` (no `engines`, no counts) exits **0** (`Q05-01`).
2. **…or accept an artifact from another task/engine?** Yes to both. The artifact's own `"task"` field is never read, so a copy of another task's artifact under this task's name passes (probed, `Q05-01`). And `pair_complete` — the flag `floor` writes into every artifact (`:426`) and prints a `SINGLE-ENGINE` warning about (`:446`) — is read by **no consumer anywhere in the repo** (grep: only its two writers). Four committed artifacts are single-engine today (`MUT-1`, `PRISTINE-00`, `PRISTINE-01`, `VIEWS-SPLIT`, all `pair_complete:false`); the gate gives them exactly the same standing as a measured pair.
3. **Does `floor` / `mutation --task` print a figure that was actually measured in that run?** `floor`: yes — every number is parsed out of the subprocess it just ran (`:347-372`), the engine is probed in a child carrying the same env (`:320-345`), and a red engine is carried with its exit code rather than smoothed over. `mutation`: **not reliably.** The pairing is by `test_scope` *label equality* (`:550-563`), so when two mutations share a scope and the first aborts before running, the first consumes the second's run and the second prints `NO RUN` — probed: M1 (never ran) printed `FAILED (failures=7), Ran 41 tests` stolen from M2, M2 printed `NO RUN -- held`, the tally line printed `0/2 mutations killed`, and the process exited 0 (`Q05-05`).
4. **Can `pg_gate.py` report green while the suite short-circuited (skips counted as passes)?** Yes. `parse_summary` (`:111-135`) matches only `failures`/`errors`, so `OK (skipped=1836)` and a `Ran 0 tests` / bare `OK` both yield `problems=0`; the anti-vacuous cross-check (`:337`) then compares 0 headers to 0 problems and passes; the whole baseline becomes "no longer failing" warnings and the run exits **0** with the line `pg_gate: every failure is in the certified baseline.` Probed with a 6-id PostgreSQL baseline and `Ran 0 tests` → exit 0 (`Q05-06`). In `backend-tests.yml` this is backstopped by the separate partial-data step (`:386-417`, `tests_baseline=2468`), but `pg_gate` is invoked as a standalone CI step (`:419-422`) and carries no such guard itself, and the backstop lives in one workflow only.
5. **Does `run_races.py` mutate a real DB/host by default, or have a guard?** It mutates by default and has **no target guard**: `--phase all` is the default (`:1073`), and with env alone the runner fires real cart adds, real checkouts, real gateway intent mints (`create_payment`, capped at 20 by `LOAD_MAX_INTENTS`) and real captures at whatever `LOAD_BASE_URL` says — no `--dry-run`, no confirmation, no allowlist/`"test" in base` assertion, no localhost-vs-prod discrimination. The only rails are environmental (base URL must be set, `LOAD_BUYER_LOGINS` must parse, a DB mode or explicit `--skip-db`/`--emit-sql` must be chosen) plus the intent budget and login pacing. The DB itself is never mutated *by the script* — all DB writing is the application's, driven over HTTP — but the box under `LOAD_BASE_URL` is (`Q05-09`).
6. **Any secret/DSN printed or written to an artifact?** No secret is printed, and the DSN is redacted before it reaches a file (`_redact`, `:375-384`; the committed `scripts/figures/GATE-7.json` carries `postgres://perfume:***@localhost:5432/perfume_store`). Two residual disclosures, both P4 and not worth a row: (a) `_redact` returns the URL **unchanged** when there is no `@` in the authority, so any credential carried another way (`?password=…`, token in path) would land verbatim in a committed artifact; (b) every artifact commits the builder's absolute venv path (`C:\Users\Admin\Downloads\backend\backend\venv\Scripts\python.exe`) inside its `commands` array — 90 committed files of local-path disclosure. `run_races` writes no DSN at all, prints only the HMAC signature (`:909-914`), and its results JSON carries no passwords (buyer logins enter `results` nowhere).

## Findings (severity order)

### Q05-01 | P2 / HIGH | INFRA | `scripts/changelog_figures.py:765-783` (and `:729-762`)
**The figure gate checks that a file exists, not that the file records the figure: every `tests`/`coverage`/`stmts`/`xf` figure is "backed" by any JSON at `scripts/figures/<task>.json`, whatever it contains, whichever task it belongs to, and on whichever engine it was measured.**

`artifact_for` ends in `return floor, floor.exists()` for all kinds except `mutation` (`:773-775`). Nothing opens the artifact: `floor` is never `json.load`ed on this path, so its `task` (`:423`), `engines` (`:427`), per-engine `run.tests` / `run.expected_failures` and `coverage.coverage_percent` are all ignored. `conventions.md:59-60` states the requirement as a row "whose floor figure … has no artifact **behind** it" — the implementation delivers "an artifact with that task's *name* in the filename".

Probed (throwaway repo, real `cmd_check`, `--base` = the fixture's first commit):

- row `| 2026-11-04 | T-EMPTY | builder | a | Ran 9999 tests, cov 12.34%, xf 99 | s |`, backing file `scripts/figures/T-EMPTY.json` = `{"task":"T-EMPTY","kind":"floor"}`, `engines` absent → **exit 0**, `0 figure(s) with no backing artifact`;
- row `| 2026-11-04 | T-OTHER | … | Ran 9999 tests | s |` with `scripts/figures/T-OTHER.json` = a byte copy of a file whose own `"task"` reads `T-EMPTY` → **exit 0**.

Engine/provenance half, from the tree rather than a probe: `floor` writes `pair_complete` (`:426`) and prints `SINGLE-ENGINE` (`:446-450`), and `grep` across `scripts/**.py` finds those two lines and nothing else — `check` never reads the field. Four committed artifacts are `pair_complete:false` (`MUT-1`, `PRISTINE-00`, `PRISTINE-01`, `VIEWS-SPLIT`); a row quoting a two-engine pair is backed identically by them. `measured_at` is likewise written (`:425`) and read by nobody, so an artifact may predate the code it is said to describe by any interval — which is exactly the "a number survives in prose long after the thing it described has moved" failure the module docstring opens with (`:16-20`).

The unit suite does not merely miss this; it **pins it**: `test_the_matching_artifact_makes_the_row_pass` writes `{"task": "GATE-7", "kind": "floor"}` — no engines, no counts — for a row quoting `1836 tests`, and asserts `status == 0` and `0 figure(s) with no backing artifact` (`test_changelog_figures.py:476-484`).

Fix route: NEXT-BUILD — for each kind, require the artifact to *contain* the figure (parse `engines[*].run.tests` / `.expected_failures` / `coverage.coverage_percent` / `.statements` and compare), require `artifact["task"] == task`, and require `pair_complete is True` unless the row itself says `SINGLE-ENGINE`. Change `:476-484` to a negative test first.

### Q05-02 | P2 / MEDIUM | INFRA | `scripts/changelog_figures.py:887-895` + `.github/workflows/backend-tests.yml:512-516`
**`check` returns 0 when the diff it was given contains no added lines, and the CI step deliberately passes `--base HEAD` on branch-creation events — where `git diff HEAD -- <path>` against a clean checkout is empty by construction, so the changelog figure gate is guaranteed green having read nothing.**

`:887-895`: `if not added:` prints the loud notice "Nothing was checked; this is an honest zero, not a pass." and `return 0`. `cmd_check` has no other zero-input path. The workflow's own fallback (`:512-515`) sets `DOC_CLAIMS_BASE="HEAD"` when `github.event.before` is all-zeros ("no usable diff base (branch creation); falling back to the previous tip of this ref."), then runs `check --base "${DOC_CLAIMS_BASE}"` (`:516`). On that event `git diff HEAD -- backend/docs/changes.md` compares HEAD's blob to an unmodified checkout → `added == {}` → exit 0. The sibling `doc_claims` step takes the opposite route for the same event (`:473-476` unsets the variable and lets the scanner fall back to its own *multi-file* defaults, which Q04 already audited as Q04-07); here the anointed fallback is a ref that cannot produce a diff.

The suite pins the vacuity as correct behaviour: `test_nothing_added_is_an_honest_zero_not_a_pass` (`:596-606`) asserts `status == 0` while its own docstring says "an empty scan that exits 0 reads as green."

Adjacent, deliberately not merged: Q04-07 is the same *shape* in `doc_claims.py` (a `+++` header with zero added lines suppresses the notice there). This row is a different file, a different mechanism (no `+++` header at all, because the diff is empty), and a different consequence (artifacts are the only evidence this gate accepts, so a green no-op is the whole gate).

Fix route: NEXT-BUILD — return a distinct non-zero (or 3, "not judgeable") when the base resolves to `HEAD` or to nothing; and in the workflow, pass the PR base sha / previous tip and **omit the step** (or fail it) when neither exists, rather than substituting `HEAD`.

### Q05-03 | P2 / MEDIUM | INFRA | `scripts/changelog_figures.py:654-682` (used at `:911-923`)
**Classification of a table line as "prose, never failed" is decided solely by whether the first cell contains an ISO `YYYY-MM-DD`; dropping or reformatting the date moves any row out of the gate for free, and the row is then reported as a sub-table rather than failed.**

### Q05-04 | P2 / MEDIUM | INFRA | `scripts/changelog_figures.py:756-762` (vs `:566-568`) and `:776-783`
**A `failures=N` figure in the changelog is "backed" by the manifest's own hand-typed `claimed_count` — the exact value the same script refuses to trust when it prints — and by the mere existence of any file at `scripts/mutation_evidence/<task>.json`, including one with no mutations in it.**

Two halves of one file disagree. `cmd_mutation` says, in a comment that is the moral centre of the module: "the verdict and the counts below are read from the replayed run's own summary, not from the manifest: `claimed_count` is the hand-typed figure this whole script exists to stop anyone publishing" (`:565-568`). `artifact_records_failures` then accepts `mutation.get("claimed_count") == count` as proof that a changelog `failures=N` is real (`:756-762`), and `artifact_for` accepts the manifest's sheer presence (`:779`). So a builder writes `claimed_count: 7` into a manifest and `failures=7` into the row, runs neither, and the gate is green. Probed equivalent: `test_a_mutation_manifest_satisfies_a_mutation_figure` writes `{"task": "GATE-7"}` — no `mutations` key at all — for a row reading `FAILED, failures=3`, and asserts exit 0 (`test_changelog_figures.py:486-494`).

This is also how the one existing exemption entry that matters got through: the `GATE-3` inventory row's `["mutation","failures=6"]` and `["mutation","failures=4"]` figures are exempted by prose acknowledging they are "the pg gate's certified failure count … not a mutation replay" (`scripts/changelog_figures_baseline.json`). Fix route: NEXT-BUILD — a mutation figure must be backed by a *replay record* (an outcome JSON produced by `mutation_evidence --json` with `status == "held"` and `observed_count == N`), not by the manifest's claim; and `artifact_for` must require the manifest to parse with a non-empty `mutations` list whose `claimed_count` equals the figure it is asked about.

### Q05-05 | P2 / HIGH | CODE | `scripts/changelog_figures.py:549-563` (and `:572-581`)
**`mutation --task` pairs a captured run to a mutation by `test_scope` label equality, so when two mutations share a scope and the earlier one aborts before running, the earlier one is printed with the later one's measured counts and the later one is printed as `NO RUN` — a paste-ready bullet quoting a figure that its own mutation did not produce.**

`index = next((i for i, (labels, _) in enumerate(available) if labels == scope), None)` then `available.pop(index)` (`:550-563`). Mutations in one manifest overwhelmingly share a `test_scope` (same module, different `find`), which is precisely the case where equality cannot distinguish them. The module explains why labels were chosen instead of position — "pairing by position alone would then report one mutation's counts under another's name" (`:486-488`) — and label equality reproduces that outcome whenever the aborting mutation is earlier than a running one.

Probed with the suite's own `FakeMutationModule`, both mutations at `["orders"]`, `skip=["M1"]`, one captured output `Ran 41 tests / FAILED (failures=7)`:

```
- mutation M1: FAILED (failures=7), Ran 41 tests -- error: 'find' text occurs 0 times
- mutation M2: NO RUN -- held: every expected test failed as recorded
- 0/2 mutations killed …
```

and `main()`/`cmd_mutation` **exits 0** (`:589` is an unconditional `return 0`; `problems` only prints to stderr at `:582-588`). Note the internal contradiction on those three lines: M1 is stamped with a verdict its own status (`error`) denies, M2's status is `held` while the bullet says `NO RUN`, and the tally counts 0 kills for a replay in which one mutation held.

The unit case that should have caught this does not exercise it: `test_a_mutation_that_never_ran_gets_no_figure` (`test_changelog_figures.py:1036-1055`) is named for the abort case but passes `skip=()` — both mutations run, and the assertion is the ordinary happy path. The one case that does pass `skip` skips the **last** mutation (`:1057-1073`), which is the ordering where label matching happens to be correct.

Fix route: NEXT-FIX (P2, one-line-class) — pair by identity, not by label: have `recording_run_tests` capture the mutation id (require `run_tests` to be called from within `replay_mutation`, e.g. pass the id through, or record a sequence and refuse when counts disagree per scope), and make `cmd_mutation` return non-zero whenever `problems` or `held != len(mutations)`.

### Q05-06 | P2 / HIGH | INFRA | `scripts/pg_gate.py:111-135` (guard at `:320-344`, verdict at `:371-405`)
**`pg_gate` cannot distinguish "the certified set is clean" from "nothing ran": the summary parser ignores `skipped=` and never looks at `Ran N tests`, so `Ran 0 tests` + `OK`, or `OK (skipped=1836)`, produces `problems=0`, which trivially satisfies the anti-vacuous cross-check, converts every baseline entry into a "no longer failing" warning, and exits 0.**

`parse_summary` builds `numbers = {"failures": 0, "errors": 0}` and only `COUNT_RE` (`failures|errors`) can overwrite them (`:129-134`); `body` fragments such as `skipped=1836` are dropped. `reported = failures + errors` (`:323`); the cross-check `header_count != reported` (`:337`) is therefore `0 != 0` → pass. `extracted` is empty, `new` is empty, `healed` is the whole baseline (`:371-372`), and `healed` is explicitly the non-failing direction (`:393-397`). Exit 0, with the reassuring final line.

Probed against a 6-id PostgreSQL baseline:

| log | exit | printed |
|---|---|---|
| `Ran 0 tests in 0.001s` + `OK` | **0** | `problems=0 extracted_ids=0 baseline_ids=6 new=0 no_longer_failing=6` / `every failure is in the certified baseline.` |
| `Ran 1836 tests` + `OK (skipped=1836)` | **0** | same |

The gate's own docstring claims the opposite property: "a gate that reads nothing looks exactly like a gate that passed" (`:18-19`) and "The summary line is the authority on HOW MANY problems occurred" (`:21-22`). The count of *tests* is authority on whether anything was measured, and it is read by a different file: `backend-tests.yml:386-417` pins `tests_baseline=2468` and is red when the `Ran` count shrinks or is unparseable. That backstop is real and does its job — for that workflow, in a later step, in a different file. `pg_gate` invoked on its own (the module docstring offers it as "the tool that closes the defect", `:12-16`; the CI step at `:419-422` is standalone) has no such guard.

Fix route: NEXT-BUILD — parse `Ran (\d+) tests` in `pg_gate` itself and exit 2 when it is absent or when `skipped + expected_failures >= ran`, and treat "every baseline entry healed" as at minimum a printed anomaly and, when the run measured zero, as exit 2.

### Q05-08 | P2 / MEDIUM | CODE | `scripts/mutation_evidence.py:365-379`
**`--verify-count` runs the whole suite *after* `replay_mutation` has already restored the file, so it measures the unmutated tree and reports any mutation that genuinely held as `failed`; the flag cannot confirm a claim, only contradict one.**

`outcome = replay_mutation(...)` (`:366`) applies the mutation, runs the scoped tests, and restores the bytes in its `finally` (`:338-341`). The whole-suite run therefore sees the original file. Its help text promises the opposite: "also run the whole suite per mutation to check `claimed_count`" (`:394-400`).

Probed with a stubbed runner that records whether the target file contained the mutated bytes at call time:

```
calls (labels, file_is_still_mutated?) -> [(['orders.tests_returns'], True), ([], False)]
status=failed claimed=1 observed=None detail=whole-suite count None != claimed 1
```

The mutation held (its expected test failed, `claimed_count` was right) and `--verify-count` still reported `failed`, because the clean tree's `FAILED (failures=N)` is absent — this repo's floor is green with `expected failures=4`, so **every** mutation with `claimed_count >= 1` is reported `failed` under this flag. Nothing in `test_mutation_evidence.py` exercises `verify_count` (grep: zero hits), so the flag's only contract is its help string.

Fix route: NEXT-BUILD — move the whole-suite run inside the mutated window (a callback passed into `replay_mutation`, or re-apply/mutate around it), or drop the flag and let `--verify-count` mean "run the scoped suite under the mutation and compare `parse_failure_count`, which `replay_mutation` already does at `:320-334`".

### Q05-09 | P2 / MEDIUM | INFRA | `scripts/load/run_races.py:937` + `:1020-1027` + `:1051-1062`
**The race runner has two paths that exit 0 having evaluated no invariant, one of which writes a results artifact stamped `"unverified": false`; and it has no guard that distinguishes the UAT box from production before it mutates stock and mints real gateway intents.**

(a) Exit 0 with nothing verified. With `--skip-db` it is at least stamped `True`.

(b) `verify-json` exits 0 when the checks file carries no checks. `rows_by_id` is built from the *supplied rows*, and `evaluate_checks(emitted.get("checks", []), …)` (`:1055`) returns `[]` for a truncated or hand-edited checks file; `failed = []` → `return 0` (`:1057-1062`). Probed: `{"checks": []}` in both files → **exit 0** with no verdict printed at all. (The inverse is handled correctly — real checks with no rows yields one `FAIL` per check and exit 1, probed.)

(c) No target guard. `LOAD_BASE_URL` is required (`:918-921`) but only for truthiness; there is no `--dry-run`, no confirmation, no `"test" in base` assertion, no host allowlist, and `--phase all` is the default (`:1073`). Related exit-code conflation in the same function: `cmd_run` catches only `SetupError` (`:1034`), so an uncaught `psycopg.OperationalError` from `run_live_db_checks` (`:882`) or an `OSError` from `write_json` (`:1017`) exits 1 — the code documented as "at least one DB invariant violated" (`:54-58`) — and dumps a traceback that names the DSN's host/user.

Fix route: NEXT-BUILD — make `--emit-sql` return 3 (or stamp `"verified": false` explicitly and refuse to name a results file as evidence), make `cmd_verify_json` return 3 when the checks list is empty, cap `except` to `(SetupError, OSError, psycopg.Error)` with a distinct exit code, and require an explicit `--i-understand-live` plus a host allowlist.

## Axis coverage

**1. INVARIANTS.** The flow's stated invariants are (i) *every published figure has a measurement behind it*, (ii) *a green verdict must never come from an empty read*, (iii) *the engine a figure was measured on is a fact, not an assumption*, (iv) *a mutation replay restores the tree byte-exactly*, (v) *the certified PG failure set compares by SET, not count*, (vi) *credentials never reach a log or a committed artifact*.
Enforcement: (i) **broken** — Q05-01, Q05-04; (ii) **broken** — Q05-02, Q05-06, Q05-09; (iii) **half** — `floor` measures and records it (`:320-345`, `:426`), `check` ignores it (Q05-01), `pg_gate` measures and prints it but does not judge it (Q05-07); (iv) **held** — sha256 verify in `finally` (`:338-347`), well tested; (v) **held** — set difference plus the header/problems cross-check, which is the one anti-vacuity guard in this flow that works as documented, though the cross-check itself is vacuous when the runner reports zero problems (Q05-06); (vi) **held for the userinfo form** — `_redact` (`:375-384`), verified against the committed artifacts, with the two residual disclosures noted above.
Uniqueness / locking / money invariants: not applicable — none of these modules writes the DB with its own connection except `run_races`' read-only `SELECT`s (`:883-887`) and `pg_gate`'s suite *collection* (`:186-189`). No `Decimal`/float decision exists in this flow: the one numeric coercion is `int(results["expected_captured"])` (`run_races:746`) over a count, not money.

**2. CORRECTNESS.** Swallowed exceptions: `pg_gate.detect_engine` (`:268-269`) and the resolver (`:219-224`) both swallow and degrade to a *reported* problem, which is right; `run_races`' per-attempt `except Exception` (`:189-194`, `:357-358`) records rather than swallows, also right. Real defects found: the mis-pairing (Q05-05), the post-restore count (Q05-08), the exit-code conflation and unverified-but-exit-0 paths (Q05-09). Immutable-field writes / `update_fields` / timezone / pagination: none applicable (no ORM writes). Timezone: all timestamps are `datetime.now(timezone.utc)` or an aware `.isoformat()` (`:120-121`, `changelog_figures:425`), correct. Partial-failure mid-loop: `run_task` appends outcomes as it goes and a raise mid-manifest leaves earlier outcomes unreported — acceptable, since the file restore is in a `finally` per mutation.

**3. SAST.** No `shell=True`, no `eval`/`exec`/`pickle`/`yaml.load`, no network in the evidence scripts at all. `mutation_evidence.run_tests` builds an argv list from manifest content (`:246-258`) — no injection. `run_races` interpolates values into SQL that is executed live (`_sql_literal`, `:787-795`, used at `:726,733`); the values come from `os.environ` and from run results, are int/str only, and strings are quote-doubled — an env-derived injection vector into the UAT DB, not a user-reachable one, and the same file's `--emit-sql` mode is *designed* to hand literal SQL to an operator, so I do not raise it. Unbounded loops: `pg_gate._iter_ids` is a recursive suite walk (fine); `run_races` waves are bounded by `RACE_N`/`CAPTURE_REPLAYS` and the intent budget. PII/secrets: covered in question 6 above. No `subprocess` in this flow is reachable from user input.

**4. ARCHITECTURE / SMELLS.** The four modules have a consistent shape (pure parsers + a thin shell + a documented exit-code contract) and the docstrings are unusually honest about *why* — several of them, however, now describe checks that do not exist (pg_gate:378-387 Q05-07, mutation_evidence:394-400 Q05-08, changelog_figures:649-650 Q05-03, run_races:54-58 Q05-09). That drift between prose and code is itself the architectural smell this flow exists to prevent, and the four files reproduce it in their own comments. Duplication: `SUMMARY_RE`/`COUNT_RE`/`parse_run`'s summary logic exist twice in near-identical form (`changelog_figures:128-149` and `pg_gate:53-57`), and `run_races` re-implements the `Ran N tests` reading a third time — the xfail-vs-failures bug is documented as having been fixed in each independently, which is the cost of that duplication. Hidden I/O: `changelog_figures` shells `git`, the suite and `coverage`; `mutation_evidence` shells `git status` and the suite; `pg_gate` imports Django at module *call* time (not import time) and calls `os.chdir` (`:184-191`, `:259-271`) — process-global state, restored in `finally`, acceptable in a CLI but it means `pg_gate` cannot be used as a library alongside another Django user. Module-level side effects: `run_races` reads six env vars at import (`:106-117`), so importing it to test `evaluate_checks` already fixes `INTENT_CAP`/`RACE_N` for the process — that is what `test_intent_cap_default_is_twenty` is asserting, and it makes the constants untestable without env manipulation. Dead code: none material; `has_decorated_date_cell` is used only for a report line.

**5. TEST SIDE.** Covered as Q05-10. In one line: the suites test the *parsers* hard and the *gates* not at all, and the three "backed" cases assert green on artifacts that record nothing — so a builder who reads the tests learns the wrong contract.
