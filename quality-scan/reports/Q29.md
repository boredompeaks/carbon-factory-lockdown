## 0. The questions the brief asked, answered directly

**(a) How is the clock frozen — freezegun, injection, or by mutating `created_at`?**

Both non-freezegun techniques, and neither is injection.

* The clock is frozen by `unittest.mock.patch("orders.views.timezone.now", return_value=….)` at
  `tests_returns.py:2313`. `_return_eligible` (`return.py:268`) calls `timezone.now()`, and
  `_return_window_refusal` takes `now` as a **parameter** (`return.py:378`, the caller owns the single
  read) — so the patch reaches the production call path. There is no freezegun dependency and no
  clock parameter threaded from the test.
* Ages are then fabricated by writing the column directly:
  `Order.objects.filter(pk=…).update(created_at=self.NOW - created_age, delivered_at=…)`
  (`tests_returns.py:2329`). Production never writes `created_at` (`auto_now_add`, `models.py:333`)
  and there is still no writer for `delivered_at` (`models.py:329`), so *every* age in this class is a
  manufactured column value, not elapsed time.

That is a legitimate technique (you cannot wait 30 days), but it has a measurable consequence, which
is finding **Q29-05**: the fixtures only ever produce instants where an exact-instant comparison and
a date/microsecond-truncated comparison agree.

**(b) Does it cover exactly-once at the window edge?**

Yes for the *verdict*, no for *once*.

* Inclusivity is genuinely pinned at the exact instant: `created_at = NOW - 30d` with the window at 30
  must be `201`, `NOW - 31d` must be `409` (`2373-2397`), and the same both-sided pin is repeated for
  1/14/30/3650 (`3103-3154`) and for the ORM-storable 3651 (`3208-3258`). Because `_placed` uses
  whole-day deltas from a fixed `NOW` with `microsecond=0`, `anchor + 30d == now` **exactly**, so this
  is a true equality test and it kills a `<=` → `<` mutation. Good.
* "Exactly once" in the *concurrency* sense is **not** covered in this range: no probe fires two create
  calls on the same order at the frozen boundary instant, and none drives the boundary while a request
  is already open. (The seam's own guard is `select_for_update` + `already_open` + the savepointed
  `IntegrityError` retry at `return.py:723-795`.) Whether that is covered elsewhere is out of this
  range; **inside 2252–3437 there is no probe of it**, and the class's docstring at `2288-2293`
  ("a fact rather than a race") is about determinism, not about once-only.

**(c) Timezone?**

No. There is no `timezone.override`, no non-UTC `TIME_ZONE`, no naive datetime, and no assertion that
the anchor/now are aware. Every instant is noon UTC (see **Q29-05**).

**(d) Partially refunded order?**

Not in this range. See **Q29-09**.

**(e) Does "surface not widened" enumerate every route?**

No — and one of its two probes cannot fail at all. See **Q29-01** and **Q29-02**.

### Q29-01 | P3 | CODE | High | FOLD-INTO-NEXT
**`test_no_returns_route_is_mounted_in_an_admin_family` is a guard that cannot fail.**

`tests_returns.py:3412-3420`:

```python
admin_routes = [str(p.pattern) for p in config_urls.urlpatterns if "return" in str(p.pattern)]
self.assertEqual(admin_routes, [])
```

`config_urls.urlpatterns` (`config/urls.py:115-195`) is a list of **literal top-level patterns plus
two `include()`s**: `admin/dashboard/`, `api/admin/orders/…`, `admin/` (`path("admin/", admin.site.urls)`
at `:182`), `api/settings/`, `api/orders/` (`:187`, `include("orders.urls")`), `api/v1/` (`:194`,
`include((v1_urlpatterns, "v1"))`). An `include()`'s pattern string is the mount prefix — it reveals
none of its children. None of those literal strings contains `"return"`, so the filtered list is `[]`
**regardless of what any app or the admin mounts underneath them**.

Concretely: this very test file uses `CHANGELIST = "/admin/orders/returnrequest/"` (`:123`) — a live,
reachable returns surface inside the admin family — and `:3412-3420` reports "no returns route is
mounted in an admin family" while that route exists. Walking `admin.site.urls` (or resolving
`/admin/orders/returnrequest/`) is what the claim requires; scanning the root urlconf for one substring
is not.

Why it matters: this is the class's single assertion about the *staff* surface, and it is green for a
structural reason rather than a behavioural one. A future `path("returns/…", …)` added directly to
`config.urls` **would** be caught (it is top-level), but an admin-mounted or app-included one never will.

Suggested pin: resolve the reverse of the ReturnRequest admin changelist and assert the resolved prefix
is `/admin/`, or walk `admin.site.urls` for `returnrequest`, then assert the capability gate on it.

### Q29-05 | P3 | CODE | High | FOLD-IN-TO-NEXT
**The boundary is pinned at whole days, noon UTC, microsecond 0 — so microsecond truncation, date
arithmetic and any non-UTC handling are all invisible; and a naive `delivered_at` writer would 500
before any test notices.**

Evidence:

* `tests_returns.py:2299` — `NOW = datetime(2026, 10, 2, 12, 0, 0, tzinfo=UTC)`, and the comment at
  `2296-2298` states the `microsecond=0` is deliberate.
* `tests_returns.py:2316-2331` — every fixture is `NOW - timedelta(days=N)` / `timedelta(seconds=N)`,
  i.e. always `microsecond=0`, always derivable from noon UTC.
* Every boundary case is a whole number of days: `2373-2397` (30/31), `2433-2453` (7/8/11),
  `3114-3120` (1, 14, 30, 3650 at N and N+1), `3232-3237` (3651/3652).
* Production `Order.created_at` is `auto_now_add=True` (`orders/models.py:333`), so **real rows always
  carry a non-zero microsecond component**; `delivered_at` is a plain nullable `DateTimeField`
  (`models.py:329`) with no writer and no normalisation.
* `USE_TZ = True`, `TIME_ZONE` defaults to `UTC` (`config/settings.py:484-488`).

Consequences, all of which the class cannot detect and none of which is pinned anywhere else in the
file:

1. **Microsecond truncation.** A gate that stamped/compared `anchor.replace(microsecond=0)` or
   `now.replace(microsecond=0)` behaves identically at `12:00:00.000000` for every case here. The
   class's own claim that the boundary is "a fact rather than a race" (`2296-2298`) is what makes this
   class unable to see the truncation: the fixtures never have a fractional part to lose.
2. **Date arithmetic.** At noon UTC, a rewrite to `(now.date() - anchor.date()).days <= window` gives
   30 at the 30-day case and 31 at the 31-day case — byte-identical verdicts. The only instants that
   separate a day-count from a timedelta comparison are fractional-day ages
   (`anchor + window + 1 second`, `anchor + window - 1 second`, or 23:xx local), and there is **no
   probe at any sub-day offset from the boundary**.
3. **Non-UTC.** No `timezone.override("Asia/Kolkata")`, no `TIME_ZONE` variation, no assertion that
   `self.NOW`/`_return_window_anchor(order)` are aware (contrast `shipping/tests_tracking.py:1043`,
   which does assert `tzinfo is not None`). Noon UTC is the one instant per day at which the UTC date
   and the IST date agree, so a `localtime(...).date()` rewrite is also invisible.
4. **Forward risk from the missing writer.** `delivered_at` has no writer and `_return_window_anchor`
   returns it raw (`return.py:328`), compared against an aware `timezone.now()` at `return.py:416`. A
   writer landing with `datetime.now()` (naive) turns that comparison into `TypeError: can't compare
   offset-naive and offset-aware datetimes` → 500. `_placed` always writes an **aware** value
   (`NOW - age`), so this class would stay green through exactly that regression. There is no pin
   that a naive `delivered_at` is rejected or normalised.

Suggested pins (cheap, and each fails on a real mutation): one order at `NOW - (30d − 1s)` (admitted)
and `NOW - (30d + 1s)` (refused); one fixture with `created_at` carrying microseconds; one
`timezone.override("Asia/Kolkata")` case around a local-midnight instant; one case asserting
`_return_window_anchor` returns an aware datetime.

### Q29-06 | P3 | CODE | High | FOLD-INTO-NEXT
**The structural pin's negative half cannot fail for the regression it names.**

`tests_returns.py:2541-2552`:

```python
window = _executable_source(_return_window_days)
self.assertIn("SiteSettings", window, …)          # :2543
self.assertNotIn("django.conf", window, "a merchant-set window must never be deployment configuration")  # :2548
```

`_executable_source` (`:2237-2248`) parses **only the function's own source**; module-level imports are
not in it. The regression the message names is:

```python
from django.conf import settings
...
return settings.RETURN_WINDOW_DAYS
```

whose executable body unparses to `return settings.RETURN_WINDOW_DAYS` — it contains `"settings"`, and
never the literal `"django.conf"`. The assertion therefore passes on precisely the implementation it
exists to forbid. (The real defence is the separate `test_no_return_window_setting_is_declared` at
`:2681-2693`, which scans `dir(settings)` for names containing `RETURN` **and** `WINDOW` — that one does
work.)

The positive half, `assertIn("timezone", gate)` at `:2535`, is weak in the same family: it is satisfied
by *any* `timezone` mention in `_return_eligible`, including the one every implementation must keep
(`timezone.now()`, `return.py:268`), so it cannot distinguish "the window is consulted" from "the clock
is read for some other reason". The class says as much at `2529-2532` — but then still presents
`assertNotIn("django.conf")` as a load-bearing pin (`2549-2552`), which it is not.

Suggested fix: scan for `"settings"` in the unparsed body (a token that *would* appear), or assert the
value is read from `SiteSettings` by monkeypatching a settings attribute and showing it is ignored.

### Q29-07 | P3 | CODE | High | FOLD-INTO-NEXT
**The "not from a cache" probe cannot detect the caching it is named for, because it replaces the
function that would hold the cache.**

`tests_returns.py:2554-2568`:

```python
with patch("orders.views.return._return_window_days", return_value=0):
    self.assertFalse(_return_eligible(order))
    self.assertEqual(self.ask(order.order_number).status_code, 409)
self.assertTrue(_return_eligible(order))
self.assertEqual(self.ask(order.order_number).status_code, 201)
```

The docstring (`:2556-2559`) says: "A gate that read the window at import time, or memoised it, would
keep answering with the number it first saw; this walks the SAME order through the seam twice and
watches the answer change under it."

Both named defects survive the probe:

* **`@lru_cache` / module memo inside `_return_window_days`** — the patch replaces the whole function
  object, so the memo is never consulted; the first call returns 0, the second (unpatched) returns the
  memoised 30. Test green.
* **Read at import time into a module constant** (`_WINDOW = SiteSettings.load().…`) — again the patch
  replaces the getter, so the constant is never read. Test green.

What it actually proves is narrower and still useful: *the gate reads the value through this helper*
(a build that queried `SiteSettings` inline in `_return_window_refusal` would ignore the patch and stay
201, failing at `:2566`). The genuine anti-caching pin in this file is elsewhere:
`test_a_closed_refusal_is_not_the_expired_window_refusal` (`:3063-3072`) mutates the **row** between
the two `ask()` calls on the same order, which *is* unreachable for a memoised read. The comment
should point at that test, or the probe should be rewritten to change the row rather than the function.

### Q29-09 | P3 | CODE | High | FOLD-INTO-NEXT
**A partially refunded order is never driven through the window — the one row `_return_eligible`'s
cycle-3 docstring exists for is only ever tested at age ≈ 0.**

`grep -n partially_refunded backend/orders/tests_returns.py` returns hits only at **593–815**, i.e. the
`RefundSeamIntegrationTests` / machine-enumeration classes, all of which file the return request
immediately (`:760-772`, `:805-820`) — inside any window. In **2252–3437** the token does not appear
once.

It cannot appear by accident either: `ReturnTestCase._order` (`:156-178`) derives
`payment_status`/`fulfilment_status` from `LEGACY_STATUS_DIMENSIONS` via `payment_for_status`, whose

by the refund seam.

Why this is not merely cosmetic: `_return_eligible` evaluates the machine half **first** and the window
**second** (`return.py:264-268`), and both refusals return the *same* 409 body
(`return.py:765-768` — `RETURN_REFUSAL_NOT_ELIGIBLE` and `RETURN_REFUSAL_OUTSIDE_WINDOW` share one

byte-identical at the seam. A regression that refused that row on the *machine* half again — the exact
cycle-3 defect the docstring at `return.py:196-206` records — makes the out-of-window case return the
same 409 with the same body, and no probe in this range can tell the difference. The out-of-window
verdict for that row is simply unpinned.

Suggested pin: in `ReturnEligibilityWindowTests`, refund `300.00` through the real seam (the helper at
`:736-753` already exists), stamp `created_at` to `NOW - 31d`, then assert both that `ask()` is 409
**and** that `_return_eligible(order)` is False for the window specifically — e.g. by asserting the row
is still admitted at `NOW - 29d`, so the machine half is proven not to be the cause.

### Q29-10 | P4 | INFO | CODE | High | FOLD-INTO-NEXT
**`clock_frozen_at` is a process-global patch, not a scoped seam injection; the docstring's account of
it is wrong in a way that could mislead a future reader into moving the seam.**

`tests_returns.py:2302-2314`:

```python
with patch("orders.views.timezone.now", return_value=target):
```

The path resolves `orders.views.timezone` — which is the **`django.utils.timezone` module object
itself**, imported by `orders/views/__init__.py` — and then patches the `now` **attribute on that shared
module**. `orders/views/return.py` reaches it via `from django.utils import timezone`, the same object,
which is why the patch works at all. So during the block, *every* `timezone.now()` in the process is
frozen, not just the gate's, and `patch` mutates a module shared by all threads.

The docstring says the opposite — "`orders.views` is patched at its OWN attribute" (`:2305`) — and uses
that to argue the production call path runs (`:2307-2308`). The conclusion (production path runs) is
true; the mechanism described (a module-local alias) is not. Since `busy` suite neighbours and
`SiteSettings.load()`'s `get_or_create` also read the clock inside these blocks, the freeze's real scope
is wider than documented. Nothing here is broken today; it is recorded because the docstring is the only
place a maintainer would learn what the seam actually is.
