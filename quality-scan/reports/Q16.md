## Verdicts on the five directed questions

**1. Does `test_seed_demo.py:103` pin the out-of-vocabulary `status="paid"`? YES — twice, and it locks the fix.**
`test_seed_demo.py:102-104` asserts `all(o.status == "paid" and o.payment_status == "paid" ...)` over the seeded
orders; `seed_demo.py:143-144` writes those values, and both are absent from `orders/state.py:36-42`
(`STATUS_CHOICES`) and `:130-137` (`PAYMENT_STATUS_CHOICES`). The same literal is planted a second time in the
fixture at `test_seed_demo.py:212-214` (`_make_foreign_rows`), so even fixing only the command leaves the test
writing the OOV row. Consequence: QC-004's fix (`seed_demo.py` → `confirmed`/`captured`) turns this test red, and the
test file is the reason the defect is "cheap to leave". New, separate detail beyond QC-004: the seed writes the orders
through `Order.objects.create(...)` (`seed_demo.py:141-153`), bypassing the state machine that every other writer
goes through, and this test asserts nothing about `OrderStatusEvent` — the immutable transition ledger
(`orders/models.py:533-604`) is empty for the demo set, and no assertion notices. → row Q16-06.

**2. Does `test_csrf_security.py` drive a real cross-site request or just assert settings? Mostly the middle thing.**
The cart half is real: `APIClient(enforce_csrf_checks=True)` un-suppresses Django's own check, the GET issues the
cookie pair, and the tokenless POST is 403 while the same POST with the header is 201 — delete the gate and
`test_cart_add_with_session_cookie_and_no_csrf_token_is_403` fails, so that pin is mutation-provable. What is *not*
real: (a) the two money-path pins that the brief cares about most, `test_checkout_with_jwt_and_no_csrf_token_succeeds`
(`:182-196`) and `test_apply_coupon_with_jwt_and_no_csrf_token_succeeds` (`:198-215`), run on the class-default
`self.client`, whose CSRF checks are **suppressed** (`common/testing.py:59` → `APIClient`; suppression proven by this
file's own differential test at `:129-137`) — so their 201 is produced with the gate inactive and they cannot fail
however the gate is ordered or worded; (b) no request sets `Origin`/`Referer`, so nothing here is a cross-site
request in the browser sense; the pins prove "tokenless is refused", which is stronger and equal in effect, but the
origin-forgery case (a stolen token replayed with a hostile `Origin`) is untested; (c) every 403 is asserted by status
code only, never by refusal reason, so
a 403 produced by a permission class instead of `CSRFCheck` satisfies the same assertion. The ordering pin at `:57-68`
does catch "gate moved before JWT" at the settings level; it cannot catch the same regression implemented in code.
→ rows Q16-04, Q16-05.

**3. Does the correlation-id test assert the impossible middleware branch? YES — this is QC-108, reconfirmed.**

is exactly why the *other* test (`:100-103`, real 500 through the client) passes for the right reason. Already tracked
as QC-108 (P3). New test-side additions for this file are the tautology at `:66` and the fact that the formatter claim
is never exercised through the wired `plain` formatter → row Q16-10.

**4. Does `test_logging_baseline.py` prove no secret/PII is logged? No — it proves handlers exist plus one narrow
credential check.**

pinned, `_build_logging` shape). `NoSecretsInLogTests` (`:257-286`) runs **one** request (verify with a non-existent
order → 400), and asserts only that `TEST_RAZORPAY_KEY_ID` / `TEST_RAZORPAY_KEY_SECRET` do not appear in that
`assertLogs` capture. Not covered: the ERROR branch in the same file (`:240-254`) whose record carries a traceback
(`assertIsNotNone(logs.records[0].exc_info)`), the audit mirror line

enforcement — `clean_audit_payload` is a credential-name denylist (`common/audit.py:47-89`), not an allowlist — and no
test anywhere asserts it, so it is a comment, not a contract. I found no live call site that violates it today
(every `detail=` I read is id/PII-free), so this is a test gap, not an active leak. → row Q16-07.

**5. Does the e2e purchase flow assert money on the wire and the stock outcome? Stock yes, money no.**
