## Direct answers to the four focus questions

**1. Is the backfill idempotent and atomic?**
- *Idempotent*: **yes**, and for the right reason — convergence is a property of the `provider__isnull=True` filter (`backfill.py:54`), not of a marker column, so a second `--apply` sees nothing and reports `linked 0` (pinned at `tests_backfill.py:195-199`).
- *Atomic*: **no.** `backfill_shipments` has no `transaction.atomic` and no per-row error handling (`backfill.py:54-64`). Each `save()` commits on its own; if the loop dies at row 200 of 500 the first 199 links are committed and the exception discards the counts entirely, so the operator cannot tell 199 from 0. → **Q34-03**.
- *Partial failure recordable*: **no.** No progress file, no mapping output, no per-row log line, no non-zero exit; the only record of a run is the stdout summary, which is not printed on failure. → **Q34-03, Q34-05**.
- *No double-stamp*: two backfill runs stamping the same parcel with the same provider is harmless, **but** the write is an unconditional `save(update_fields=["provider"])` after a snapshot read, so it can overwrite a link an *operator* made in between — the exact decision the module's docstring says it will never overwrite (`backfill.py:41-43`). → **Q34-02**.

**2. Does the estimate endpoint validate its inputs?**
- Not at all beyond non-emptiness. `state` and `pincode` are `.strip()`ed and checked for blank (`views.py:61-68`); there is **no length bound and no charset check**. No numeric input exists (amounts are server-derived, `pricing.py:291-316`), so "*negative/Decimal values*" has **no attack surface here**; "*weight bounds*" is **N/A by model decision** — `shipping/models.py:17-22` records that no product carries a weight in grams, so no weight-based rate exists to feed. Both are checked-and-clean, not gaps.
- The real gap is the *postal code*: the schema declares `ShippingRate.postal_code_prefix` is at most **10** characters (`models.py:255-260`), yet the destination pincode is unbounded and `_geography_conditions` builds one prefix per length (`pricing.py:106`), i.e. `len(pincode)+1` SQL parameters per anonymous request. A pincode that cannot match anything is not rejected — it silently falls through to the wildcard/national rate and the caller is told **delivery is available to a nonsense destination**. → **Q34-01**.

**3. Is any shipping view missing a permission class or object scope?**
- **No.** `ShippingEstimateView.permission_classes = [AllowAny]` (`views.py:58`) and `ShipmentTrackingView.permission_classes = [AllowAny]` + `throttle_classes = [TrackingRateThrottle]` + `throttle_scope = "tracking"` (`views.py:226-228`) are both explicit, and both openings are argued in the module docstring against conventions.md:26. Object scope on the one endpoint that needs it is real, not nominal: authenticated → `order__user=request.user`, anonymous → `order__guest_token=<header token>` (`views.py:168-174`), and the `Order` XOR check constraint (`orders/models.py:386-392`) makes a `guest_token` on an account order impossible, so the token path cannot leak a registered customer's parcels. Uniform 404 body (`views.py:120-137`) and `no-store`/`Vary` on every response including the miss (`views.py:230-245`) are correct. The staff-side gates exist and are unused by design (`common/permissions.py:266-281`). One residual: neither view clears `authentication_classes`, so a stale bearer turns the "anonymous by design" estimate into a 401. → **Q34-08**.

**4. Does the command have a dry-run, and does it refuse production?**
- Dry run: **yes**, and it is the default (`--dry-run` and `--apply` in a mutually exclusive group, `commands/backfill_shipment_providers.py:22-38`), and the dry pass shares the *identical* matching loop with apply (`backfill.py:37-64`) so the two cannot disagree about matching.
- Production refusal: **no, and no confirmation either.** `--apply` alone writes; there is no `--yes`, no `DEBUG`/host guard, no `CommandError` path at all. The repo's own sibling command for a customer-visible rewrite requires `--apply --yes` and refuses otherwise (`remint_legacy_order_numbers.py:106-116`), `seed_e2e` refuses anything that is not a resolved test DB (`seed_e2e.py:343-369`), and `restore_drill` refuses the configured production database. The backfill — which rewrites *the link a customer's tracking page follows* — has neither gate. → **Q34-04**.

## Findings

### Q34-01 | P2 | MEDIUM | CODE | `shipping/views.py:61-68` (+`shipping/pricing.py:106`) | NEXT-BUILD
**Claim.** The public estimate accepts an unbounded, unvalidated destination and answers it as if it were a real one.

**Evidence.**
- `views.py:61-62` read `state`/`pincode` from `request.query_params`; `views.py:64-68` reject only *blank*. Nothing constrains length or characters.
- `pricing.py:106`: `prefixes = {postal_code[:length] for length in range(len(postal_code) + 1)}` → the parameter count of the `postal_code_prefix__in` predicate (`pricing.py:109`) is a direct function of caller input. `models.py:255-260` declares `postal_code_prefix = CharField(max_length=10)`, so every prefix longer than 10 characters is *provably* unmatchable yet is still enumerated and bound.
- Consequence A (**certain, source-read**): per-request work on an anonymous, unthrottled endpoint scales linearly with attacker input — `ShippingEstimateView` declares no `throttle_scope` (`views.py:58`, and `settings.py:1279-1283` leaves unscoped views unthrottled by design). Deploy-runbook's front door is nginx, whose default `large_client_header_buffers` caps a request line near 8 KB, so the practical ceiling is ~8k bind parameters per request rather than an unbounded one; a direct app-server or a proxy without that cap reaches the driver's parameter limit instead (SQLite ~32 766 / Postgres 65 535) and 500s. **This sub-claim is inferred, not run** — marked M.
- Consequence B (**certain**): a pincode of `"abcdef"`, `"!!!"`, or 500 characters matches no prefix rate, so `shipping_options` falls through to whatever wildcard/national rate exists and returns **200 with delivery options** (`pricing.py:309-316`) — the serviceability check says "we deliver to `!!!`".
- Consequence C: the raw values are echoed back unchanged in the 200 body (`views.py:91-92`), so response size tracks caller input too. JSON-encoded, so no XSS *here*; it is a reflected-value concern for the SPA, not an injection in this endpoint.
- Tests: `tests.py:406-417` pins presence/blank only. No test feeds a long or non-numeric pincode, so deleting any future bound would not go red today.

**Fix shape.** Bound the destination at the boundary the schema already declares (state ≤ 100 like `ShippingRate.region`, pincode ≤ 10 and `[0-9]{4,10}`-shaped per the store's market) and 400 with a validation message instead of pricing it; the enumeration in `pricing.py:106` then cannot exceed 11 elements. `views.py:172` already applies exactly this discipline to the *other* public input (guest token length), which is the in-file precedent.

### Q34-02 | P2 | HIGH | CODE | `shipping/backfill.py:54-60` | NEXT-BUILD
**Claim.** The backfill can silently overwrite a provider link an operator made — the one thing its own docstring promises never to do.

**Evidence.**
- `backfill.py:54` iterates a *snapshot* of `Shipment.objects.filter(provider__isnull=True)`; the queryset is fully evaluated at loop start.
- `backfill.py:58-60` then writes `shipment.provider_id = <match>; shipment.save(update_fields=["provider"])` with **no condition and no lock**. There is no `select_for_update` anywhere in the module, and no `filter(provider__isnull=True).update(...)`.
- `backfill.py:40-43` states the invariant verbatim: *"a link an operator (or an earlier run) already made is a decision, and a backfill is not allowed to overwrite it."* The admin change form is a concurrent writer of exactly that field (`shipping/admin.py:137` exposes `provider` on the shipment form).
- Timeline: backfill snapshots parcel #7 as NULL → staff links #7 to `bluedart` in the admin → backfill reaches #7 and writes `delhivery`. The operator's decision is gone with no audit row (the admin's `save_model` trail only records *status* changes, `models.py:74-99`).
- The repo's own precedent does this correctly: `remint_legacy_order_numbers.py:166-177` takes `select_for_update()` and **re-checks** the predicate inside the lock, documenting the outcome as *"the second run skips a row instead of overwriting it"*.
- Not covered by any test (`tests_backfill.py` has no concurrent/operator-interleaved case — see Q34-07).

**Fix shape.** One conditional statement per row inside a transaction: `n = Shipment.objects.filter(pk=shipment.pk, provider__isnull=True).update(provider_id=match)` and count `n`. `ShipmentQuerySet.update` refuses only `status` (`models.py:87-99`), so `provider` is a legal bulk write; the width gate it adds is irrelevant for an FK id. `updated_at` then stays untouched, matching the migration's stated intent (`0005:51-54`).

### Q34-03 | P2 | MEDIUM | CODE | `shipping/backfill.py:54-64` | NEXT-BUILD
**Claim.** A failed apply leaves a half-written table and reports nothing about what it did.

**Evidence.**
- No `transaction.atomic()` wraps the loop; `backfill_shipments` is called straight from `handle` (`commands/backfill_shipment_providers.py:37`). Each `save()` is its own autocommit transaction.
- The `counts` dict (`backfill.py:51`) is only returned on normal completion. Any raise mid-loop — a `DataError` on Postgres, an FK violation if a provider row is deleted concurrently, a `ValueError` from the width gate at `models.py:466-477` on an instance that changed — propagates out of the management command as a traceback with **no counts and no record of which rows were already stamped**.
- So "how much of the table did that run change?" is unanswerable after a failure. Recovery is a blind re-run (which is at least safe, because of Q34's answer 1), but the operator has no evidence the first run was partial.
- Contrast `remint_legacy_order_numbers.py:139-142`, which wraps the whole repair in one `transaction.atomic()` with the reasoning spelled out: *"a bounded retry that cannot find a free number must leave every row as it was, never a table half-reminted."* The same argument applies here and is absent.
- There is no test that provokes a mid-loop failure.

**Fix shape.** Wrap the apply loop in `transaction.atomic()` (all-or-nothing, which the filter makes free to re-run), or — if a partially-applied run is preferred — catch per row, keep a `failed` counter with the pk list written to stdout, and exit non-zero via `CommandError` so a deploy script can detect it.

### Q34-04 | P2 | MEDIUM | CODE | `shipping/management/commands/backfill_shipment_providers.py:35-43` | NEXT-BUILD
**Claim.** `--apply` is a one-flag, unconfirmed, environment-blind write to the customer-visible tracking link.

**Evidence.**
- `handle` reads `options["apply"]` and calls the writer; there is no confirmation token, no `settings.DEBUG`/host check, no `CommandError` on any path (`commands/…:35-45`). The module docstring calls the run "safe to run repeatedly" (true) and stops there.
- What it writes is not cosmetic: `Shipment.provider` drives `Shipment.tracking_url` (`models.py:431-464`), which the storefront renders as the customer's tracking link, and the backfill's own docstring warns a wrong link "would send a paying customer to somebody else's tracking page".
- The repo already holds the higher bar for a *less* sensitive rewrite: `remint_legacy_order_numbers.py:108-112` refuses `--apply` without `--yes`; `seed_e2e.py:361-374` refuses unless the resolved database is a test one; `restore_drill` refuses the configured production database by name.
- No test, because there is nothing to test: the flag set is `--dry-run|--apply` only (`commands/…:22-33`).

**Fix shape.** Require `--apply --yes` (matching the sibling writer) and add the resolved-database guard shape already written at `seed_e2e.py:343-358` when the intent is "operator-only, never a deploy step"; alternatively require `--provider <code>` to bound the blast radius of a mistaken run.

### Q34-05 | P3 | LOW | CODE | `shipping/backfill.py:51-52` (+`commands/…:39-43`) | FOLD-INTO-NEXT
**Claim.** The summary numbers are stale by construction, and the rows an operator must act on are counted but never shown.

**Evidence.**
- `counts["already_linked"]` is measured with a separate query **before** the loop (`backfill.py:51-52`), so a run that links 2 parcels prints `linked 2 … already linked 0` — the post-run truth is 2. Harmless but the line is not a consistent snapshot: it is "linked (this run)" beside "already linked (before this run)", and the second query is a second full-table count.
- `ambiguous` and `unmatched` are integers only (`backfill.py:61-64`); nothing names the parcel or the carrier, so the operator cannot fix the 40 rows the backfill refused to guess about. `remint_legacy_order_numbers.py:130-131` prints one line per affected row for exactly this reason, and offers `--mapping` to leave a durable record.
- The command exits 0 regardless of `ambiguous`/`unmatched` (`commands/…:35-45`), so a wrapper script cannot tell "everything linked" from "nothing linked".

**Fix shape.** Emit one line per unresolved row (`pk`, carrier, candidate count) and a `CommandError` when `ambiguous` is non-zero under an explicit `--strict`; or drop `already_linked` from the same-run summary since `linked` already answers the question.

### Q34-06 | P3 | LOW | CODE | `shipping/backfill.py:54` | FOLD-INTO-NEXT
**Claim.** The scan materialises every legacy parcel as a full model instance and issues one UPDATE per row.

**Evidence.** `for shipment in Shipment.objects.filter(provider__isnull=True)` evaluates the whole queryset into `_result_cache` (Django caches on iteration) — every column of every matching `Shipment`, including the `internal_note` `TextField` (`models.py:409-412`), and one `save()` per row. There is no `.iterator(chunk_size=…)`, no `values_list`, no batched `bulk_update` (and `bulk_update` is unavailable for `status` but legal for `provider`). The adjacent command models the cheap shape: `legacy_rows()` selects two columns and streams them (`remint_legacy_order_numbers.py:36-46`).

**Why LOW not P2.** It is a one-shot operator command over a table whose linked rows drop out of the filter, so it converges; the cost is memory and query count on a very large `shipments` table, not a wrong answer. It becomes a P2 the moment this is wired into a deploy step (which Q34-04 is exactly about).

### Q34-08 | P3 | LOW | CODE | `shipping/views.py:58` (and `:226`) | FOLD-INTO-NEXT
**Claim.** "Anonymous by design" is true for a caller with *no* credential and false for a caller carrying a stale one.

**Evidence.** `settings.py:1261-1271` puts `JWTAuthentication` in `DEFAULT_AUTHENTICATION_CLASSES`. DRF authenticates in `initial()` **before** it evaluates `permission_classes`, so an expired or malformed `Authorization: Bearer …` on `GET /store/shipping/estimate` raises `InvalidToken` → 401, even though the view is `AllowAny` and the guest path would have answered 200. A signed-in customer whose access token expired mid-session therefore loses the delivery price until the SPA refreshes. `ShipmentTrackingView` (`:226`) has the same shape, where a stale bearer is *worse* than no bearer: the guest-token path is never reached, so the customer gets 401 instead of their parcels.

**Confidence M** — the DRF ordering is certain, but whether it reaches users depends on the storefront's refresh behaviour, which is out of this flow.

**Scope note.** This is not shipping-specific: `authentication_classes = []` appears exactly once in the backend (`orders/webhooks.py:563`), so every `AllowAny` view shares it. Fixing it here only would be a local inconsistency; it belongs in a repo-wide decision (or a lenient JWT authenticator that treats a failed token as anonymous **only** on views that declare `AllowAny`).

## Axis 2 — correctness details checked and clean
`update_fields` is honoured (no `updated_at` side effect); `casefold` vs. exact-name comparison is deliberate and documented; the empty-carrier/`None`/whitespace cases return an empty set before any provider is touched (`backfill.py:26-28`, pinned `tests_backfill.py:79-83`); the estimate's `currency` is read from the same setting checkout uses (`views.py:98`); ordering is deterministic in both pricing (`pricing.py:140`, `:165`, `:180`) and tracking (`views.py:188`); `select_related("provider")` prevents a per-parcel query (`views.py:184-186`); no swallow-and-continue anywhere; no timezone arithmetic on this flow.

## Axis 3 — SAST checked and clean
No `'__all__'` serializers; no raw SQL; no `eval`/pickle; no secrets; no `request.user.is_staff` inline; error bodies are constants (`UNKNOWN_METHOD_MESSAGE`/`UNSERVICEABLE_MESSAGE`, `pricing.py:52-56`) and `str(exc)` on `ShippingUnavailable` carries no store data; no unbounded loop other than Q34-06; the tracking serializer cannot be posted to (all fields `read_only`, `serializers.py:103-115`).

## Axis 4 — architecture
`backfill.py` is the right shape (one pure matcher + one orchestrator, no I/O at import). The deliberate duplicate of the matcher in migration `0005:23-38` is documented and defensible (a migration must not import live code). Real smell: `backfill.py` performs hidden I/O in a loop with no transactional boundary, and the command is a third layer that adds only argument parsing plus a summary string — which is the right layering, but it means the failure semantics live in the module, where they are absent.
