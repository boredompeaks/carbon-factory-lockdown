## Q11-01 — P1 CRITICAL — `StoreUserAdmin` lets the `admin` tier change a **superuser's password / email / is_active**, defeating the SPEC-1-B03 tier guard (CODE, Confidence H)

**Where**: `backend/accounts/admin.py:276-281` (`capability_map` → `"change": "staff.manage"`), `backend/accounts/admin.py:408-412` (`get_readonly_fields` protects only `is_staff/is_superuser/user_permissions`), `backend/accounts/admin.py:286-302` (fieldsets: `email`, `is_active`, `password` writable for that capability).

**Invariant broken**: "an Admin can never mint or unmint the tier above itself" — stated and enforced for the roles field (`admin.py:365-394`, `_refuse_restricted_roles`; `_pending_role_change` refuses *before* rendering the interstitial) and pinned by `tests/test_superadmin_tier.py:347-435`. The same class hands the same caller an unfettered path to the tier above through the credential channel.

**Evidence (source-read, from the installed Django the class inherits)**:
- `accounts/admin.py` overrides no `get_urls` and no `user_change_password` (only `orders/admin.py:452` defines `get_urls` anywhere in the repo).
- `django/contrib/auth/admin.py:97-105` registers `<id>/password/` → `self.user_change_password`.
- `django/contrib/auth/admin.py:150-153`: `user_change_password` gates **only** on `self.has_change_permission(request, user)` — which for this class is `_map_grants(request, "change")` = `staff.manage` (`common/admin.py:178-196`), held by the `admin` role (`common/roles.py:125`). No superuser check anywhere on that path.
- `email` is writable on the same change form, and the public `POST /api/accounts/password-reset/` mails a valid reset token to that address (`accounts/views.py:713-739`), so the same caller can take the account over without ever touching the password URL.
- `is_active` is writable too, so the trust anchor can be deactivated by the tier below it.

So a staff user holding only the `admin` role group can (a) set `/admin/auth/user/<superuser_pk>/password/` to a password of their choosing, or (b) rewrite the superuser's email and complete a public password reset, or (c) deactivate the superuser. Any of the three converts the `admin` tier into the `superadmin` tier — exactly the escalation `platform.configure` (`common/roles.py:130,140`) and `_refuse_restricted_roles` were built to stop.

**Why it was missed**: the guard was designed around "role and flag fields"; the Django-inherited credential-recovery views are not fieldsets, so neither `get_readonly_fields()` nor `changeform_view()` sees them.

**Fix direction**: override `user_change_password` (raise `PermissionDenied` unless `request.user.is_superuser` or the target is not above the caller's tier), and make `email` / `is_active` read-only on any target that holds a role the caller may not assign (`user_may_assign_role` against `target.groups`) — the same diff-refusal the roles field already uses. A test must POST the password-change URL as an `admin`-role user against a superuser and expect 403.

## Q11-02 — P2 HIGH — TOTP replay watermark is read–verify–write with no lock: one code can be spent twice (CODE, Confidence H)

**Where**: `backend/accounts/serializers.py:126-136` (staff API door) and `backend/accounts/admin.py:183-194` (Django admin door).

Both do:

```python
counter = totp.verify_code(device.secret, code, at_time=totp.now(),
                           last_used_counter=device.last_used_counter)
...
device.last_used_counter = counter
device.save(update_fields=["last_used_counter"])
```

No `transaction.atomic()`, no `select_for_update()`, no conditional `UPDATE ... WHERE last_used_counter < counter`. Two concurrent logins presenting the same still-valid code both read the same watermark, both verify, both persist the same counter, and both mint a token pair. `common/totp.py:85-107` is written precisely to guarantee "any counter at or below it is skipped, so a code already consumed for this device can never verify again — even inside its own validity window"; under concurrency that guarantee does not hold. The admin form has the identical shape, so the primary staff door carries the same hole, and `accounts/views.py:853-868` (`_consume_code`) is a third copy.

**Why it matters**: an observed/relayed code (shoulder-surf, phishing proxy that forwards the code and races the victim) yields more than one session. MFA replay protection is the whole point of the watermark.

**Evidence that this is a real lock-order omission and not a theoretical one**: the same app locks for the adjacent concerns — `accounts/views.py:50-61` (`_lock_user_addresses` → `User.objects.select_for_update()` then `Address.objects.select_for_update()`) and `accounts/views.py:304-329` (`_lock_presented_refresh`, with a comment stating "check-then-blacklist is not atomic on its own"). The TOTP consumption path got no such treatment.

**Tests**: `tests/test_mfa.py` exercises the replay guard only sequentially (`:181-193`, `:863-866`, `:1073-1078`, `:1465-1469`); `accounts/tests.py` does not touch the serializer's watermark at all. No concurrency case exists on either engine.

**Fix direction**: one helper — inside `transaction.atomic()`, `TOTPDevice.objects.select_for_update().get(pk=device.pk)`, re-read the watermark, verify, then `save(update_fields=["last_used_counter"])`; or an `UPDATE ... WHERE last_used_counter IS NULL OR last_used_counter < %s` and treat `rowcount == 0` as replay. The three copies (serializer, admin form, `views._consume_code`) should collapse into that one helper — see Q11-06.

## Q11-03 — P2 MEDIUM — MFA trust is granted but never revoked on a credential change (CODE, Confidence M)

**Where**: `backend/accounts/mfa_trust.py:52-62` (the only writer of `trusted_until` in the module is `grant_trust`; there is no `revoke_trust`), `accounts/views.py:926-947` and `1034-1035` (the two ad-hoc clearers), `accounts/views.py:773-796` (password reset).

The module docstring claims to be "the whole opt-in … the only place that decides whether a login may skip the challenge" (`mfa_trust.py:1-33`), but it owns only the *grant* leg. `reset_password` blacklists every outstanding refresh token (`views.py:776-780`, per R-17.10) and the session dies — while `TOTPDevice.trusted_until` and the browser's signed `mfa_trusted_device` cookie both survive for up to `MFA_TRUST_DAYS` (default 30, `settings.py:964`). Logout (`views.py:377-415`) does not clear the cookie either.

Bounded blast radius, stated plainly: trust is `AND`-ed with the password, so a leaked password alone still earns nothing from another browser. The gap is that the documented "bounded twice, revocable" posture has no revoke path on the one event that is defined as a critical credential change, and that "reset my password because I think I'm compromised" leaves the attacker's browser MFA-exempt for the rest of the TTL if they obtain the new credential.

**Fix direction**: add `revoke_trust(user)` to `mfa_trust.py` (single writer: `trusted_until = None` on the device, plus a `delete_cookie` on the response), call it inside the reset transaction and on logout, and replace the two inline clears at `views.py:938` / `views.py:1034` with it.

## Q11-04 — P3 LOW — Registration accepts usernames the availability oracle reports as unavailable (CODE, Confidence H)

**Where**: `backend/accounts/serializers.py:53-56` (only an `iexact` uniqueness check; no minimum length) versus `backend/accounts/views.py:600-603` (`username_available` refuses anything under 3 characters with "Username must be at least 3 characters.").

`POST /api/accounts/register/` with `username: "ab"` is accepted (201) — Django's `User.username` carries only `UnicodeUsernameValidator`, no length floor — while `GET /api/accounts/username-available/?username=ab` says unavailable. The two shipped surfaces of the same rule disagree, and the frontend gates on the oracle, so the disagreement is user-visible. `tests.py:624-632` pins the oracle's rule; no test pins register to the same rule.

**Fix direction**: a shared `USERNAME_MIN_LENGTH` constant applied as `MinLengthValidator` in `RegisterSerializer.validate_username` and consumed by the oracle.

## Q11-05 — P3 LOW — A malformed `THROTTLE_ADMIN_LOGIN_RATE` 500s the admin login instead of falling back (CODE, Confidence H)

**Where**: `backend/accounts/admin.py:69-70` (`get_rate` returns the raw env string) into `rest_framework/throttling.py:68-71,97-107` (`parse_rate` does `num, period = rate.split("/")` and `int(num)`).

`ADMIN_LOGIN_THROTTLE_RATE` is read raw from `os.getenv` (`settings.py:977`) with no `_env_int`-style guard, unlike every other env knob in that file (`_env_int`, `_env_bool`, `_env_iso_date` all fail safe — `settings.py:1387-1390` states the doctrine). A typo such as `THROTTLE_ADMIN_LOGIN_RATE="10"` or `"ten/min"` raises `ValueError`/`KeyError` inside `AdminLoginThrottle()` at `admin.py:157`, i.e. inside `MFAAdminAuthenticationForm.clean()` — an unhandled exception on **every** `/admin/login/` attempt. The documented kill switch is the empty value only (`admin.py:93-94`), so an operator cannot recognise the difference between "throttle off" and "door down" from the config alone.

**Fix direction**: validate at settings load (fall back to `"10/min"` on a bad shape, as `_env_iso_date` does) or wrap `parse_rate` in `get_rate` and disable the bound on failure.

## Q11-10 — P4 INFO — TOTP secrets are stored in plaintext, protected only by "we never render it" (CODE, Confidence M)

**Where**: `backend/accounts/models.py:44` (`secret = models.CharField(max_length=64)`).

The model docstring (`models.py:25-27`) and `TOTPDeviceAdmin` (`admin.py:592-631`) discharge the *display* half of secret hygiene correctly — the column is in no field, column, filter or search target, writes are denied for every role including the superuser bypass, and the setup endpoint is the single return path. ## Answers to the six focus questions

1. **Does registration run the same `validate_password` policy as reset (F-07)?** Yes, and it does it correctly — same validator list (`settings.py:413-426`), same user-aware call, transient user seeded with the submitted username/email, identical field-error shape. Parity is pinned from both ends (`tests.py:178-270`). F-07 is genuinely closed for the fields that reach `validate()`; the blank/missing-email corner remains the separately tracked xfail.
2. **Is email/username uniqueness a DB constraint with `IntegrityError` handling, or check-then-act?** Check-then-act, both fields — `serializers.py:53-65`; no `IntegrityError` retry in `create()`. Username has a case-**sensitive** unique index behind a case-**insensitive** `exists()`, and `email` has no unique index at all. KNOWN as F-10 / V-08; not re-reported.
3. **Are MFA trust cookies signed, scoped, expiring, and revocable on password change?** Signed with a purpose-specific salt, HttpOnly, SameSite=Strict, Secure unless DEBUG, double-expiring — all yes. Scoped: only by cookie name/path (`path` defaults to `/`, i.e. sent to every path on the host — minor, not a row). **Revocable on password change: no** → Q11-03.
4. **Does the admin expose password hashes or TOTP secrets?** No, on both counts, and by construction rather than by luck: `password` rides Django's `ReadOnlyPasswordHashField`, whose template renders `render_password_as_hash` — a hasher summary ("algorithm: pbkdf2_sha256, iterations: …"), never the stored hash — plus a link to the password-change form; `TOTPDeviceAdmin` omits `secret` from `fields`, `list_display`, `list_filter` and `search_fields` and denies add/change/delete unconditionally, superuser bypass included. The *link* that field renders is, however, the escalation of Q11-01.
5. **Is the role-assignment path capability-gated (superadmin vs admin)?** Yes for the roles field, in both directions, on both the interstitial leg and the commit leg, and pinned. No for the account-recovery path on the same ModelAdmin → Q11-01.
6. **Do serializers have explicit fields?** Yes — all four (`RegisterSerializer`, `AddressSerializer`, and the two token serializers declare their own) list explicit fields; no `'__all__'` anywhere in the flow, matching `conventions.md`.
