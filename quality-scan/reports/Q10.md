## Answers to the four focus questions

### 1. Is `test_postgres_row_locking.py` actually locking (TransactionTestCase + second connection/thread)?

**No, and it does not pretend to at the mechanism level - but two of its tests do silently become no-ops on
SQLite.** The module contains no `TransactionTestCase`, no second `connections[...]`, no thread, and no
concurrent writer (grep: `TransactionTestCase` appears in exactly two files repo-wide,
`tests/test_notification_outbox.py:56` and `tests/test_notification_outbox_worker.py:67`, both outbox).
What it observes instead is three things, none of which is mutual exclusion:

| Where | What is actually asserted | Is it a lock? |
|---|---|---|
| `:164` | `queryset.query.select_for_update is True` | ORM flag on a queryset object, never evaluated |
| `:79-84` | `QuerySet.select_for_update` was *called* on a model (monkeypatched spy) | a call, not a hold; an unevaluated queryset passes |
| `:142-154`, `:276-279` | emitted SQL contains / lacks a `LEFT OUTER JOIN "orders_coupon"` | SQL text |

So the module proves *"the guard code asks for a lock and does not join a nullable FK"*. It never proves
*"two writers cannot interleave"*. **No test anywhere in this repo proves that** for Order/Product/Coupon:
the only threaded test is the outbox worker pair, and `tests/test_e2e_concurrency.py:1-7` states in its own
docstring that it resolves two verifications "in sequence", i.e. the loser is refused by the coupon
`usage_limit` predicate re-check, not by the lock. On SQLite those "race" tests would pass with
`select_for_update` deleted entirely. That fact is already recorded at
`docs/run/section-00-infrastructure.md:116` and is therefore **not** re-reported as new; what is new is that
this module - which other flows cite as the PG-lane proof of locking (Q09 said so explicitly) - supplies
**zero mutual-exclusion evidence either**, and two of its own assertions vanish without trace on the default
lane (Q10-01, Q10-08).

### 2. Does the isolation test prove test isolation or just assert a helper's contract?

**Almost entirely the helper's contract, and the one test that looks like it proves the wiring is a tautology.**

- Genuine isolation proof: `:336-362` spawns a real child process and asserts `REFUSED` + no `ACQUIRED`. That
  is mutation-solid and cannot be faked in-process. It is the only such test.
- The remaining ~33 tests pin `DatabaseSuiteLock` / `test_database_identity` / `parallel_shares_one_database`
  contracts on fabricated `DATABASES` dicts - legitimate unit tests, but they hold even if the runner is
  never installed.
- `:364-370` is named `test_the_key_from_this_run_is_the_configured_database` and is the one test that appears
  to close that wiring gap. It asserts
  `LockedDiscoverRunner(...).get_lock_key() == test_database_identity()`; `get_lock_key`
  (`common/test_isolation.py:293-296`) returns exactly `test_database_identity()` when no override is passed.
  **The assertion is `f(x) == f(x)` and cannot fail for any state of the world** (Q10-03).
- The actual wiring (`config/settings.py:407`, `TEST_RUNNER = "common.test_isolation.LockedDiscoverRunner"`)
  is asserted by **no test in the repo**: grep for `TEST_RUNNER` across `backend/` returns that one settings
  line and a changelog row, nothing under `tests/`. Delete line 407 and this 543-line module stays green.

### 3. Are the alert/RBAC tests asserting a code outcome or a log string?

**Alerts: overwhelmingly code outcome. RBAC: no log assertions at all, but its central matrix is
self-referential.**

- `test_alerts.py` has 30 tests. Five assert a log string (`:169`, `:338`, `:350`, `:392`, `:423`) and in four
  of them the log *is* the contract being pinned (log-only send failure, INFO on suppression) - correct use.
  The fifth, `:163-169`, asserts only `"suppressed"` appears in the log and **never asserts that no second
  mail left**; an implementation that logged the message and sent anyway would pass (the sibling `:126-137`
  does assert the mailbox, so the strong form already exists).
- Everything else asserts `mail.outbox`, `notify_*` return values, or a cache key - real outcomes.
- `test_rbac_foundation.py` asserts return values, HTTP status codes, `PermissionDenied` and rendered bytes;
  no log strings. Its weakness is different: `test_role_capability_matrix_matches_the_map` (`:113-123`) builds
  its expectations **from `CAPABILITY_ROLES`**, the same dict the permission classes read, so it proves the
  two agree, not that the map is right. The file knows this (`:380-381`) and answers it with absolute pins at
  `:389-402` - for **3 of the 20 capabilities** (Q10-07).

### 4. Do the restore-drill tests verify data equality or only row counts?

**Row counts only, and not even all of them.** `_verify` compares `_row_counts` (`restore_drill.py:109-116`,
`:280-300`); nothing compares a single field value, and no test ever creates a row with a distinctive value
to prove the restored copy carries it. The only corruption the suite exercises is *deleting a row*
(`--simulate-failure`), i.e. the one divergence counting can see. Worse, `_row_counts` iterates
`apps.get_models()`, whose `include_auto_created` default is `False` (installed
`django/apps/registry.py:169`), so **every auto-created M2M through table is outside the measure** -
including `auth_user_groups` / `auth_user_user_permissions`, i.e. the entire staff role-assignment substrate
(Q10-02).

## Detail

### Q10-01 - Two lock tests are branch-hosted smoke tests on SQLite
**P2 MEDIUM - TEST - Confidence H - NEXT-BUILD**

`test_bulk_action_locks_orders_without_joining_their_nullable_fks` (:183-221) and
`test_verify_still_locks_the_order_row_it_mutates` (:281-298) both put the whole guarded body inside

```python
if connection.features.has_select_for_update:          # :202, :291
```

Outside that branch they assert only that the bulk action / the verify succeeded and the status landed
(`:197-199`, `:297-298`). The module's own docstring (:11) states SQLite's
`features.has_select_for_update` is `False`, so on the engine this suite normally runs on those two tests
assert nothing about locking and **report as ordinary passes** - not skips, not xfails, nothing in the output
distinguishes them. Deleting `select_for_update()` from the verify path's Order fetch therefore leaves both
green on SQLite; only the PostgreSQL lane would notice, and the PG lane is the one the repo runs least.

Two aggravating details, both verifiable in the file:
1. The coupon lock got an engine-independent pin - `recording_locks()` (:63-84) records the ORM *call* - but
   that helper is used **only** in `test_verify_locks_the_coupon_row_it_reads_and_increments` (:319). The
   verify path's **Order** lock has no such pin, so of the two locks the module exists to protect, one is
   pinned on both engines and one only on PostgreSQL.
2. `recording_locks` records `select_for_update` *calls*; a call on a queryset that is never evaluated (or a
   call on a different queryset of the same model) satisfies it. It proves intent, which the docstring says
   it does, so this is stated as a limit of the pin rather than a defect - but it means even the
   "engine-independent" half is not evidence that a row was locked.

Fix shape: use `recording_locks()` in the two gated tests and assert the *call* unconditionally, leaving only
the `FOR UPDATE`-text half inside the feature gate; or `self.skipTest()` in the else-branch so the lane's
output stops claiming coverage it does not have.

### Q10-02 - The restore drill's PASSED can survive a restore that loses every role assignment
**P2 MEDIUM - TEST - Confidence H - NEXT-BUILD**

- `restore_drill.py:109-116` - `_row_counts` iterates `apps.get_models()` and counts `model.objects.using(alias).count()`.
- Installed Django 6.1 `django/apps/registry.py:169` - `def get_models(self, include_auto_created=False, include_swapped=False)`:
  the default **excludes** auto-created models, and auto-created through models are the only representation
  of `auth_user_groups`, `auth_user_user_permissions` and `auth_group_permissions`. Those tables carry every
  staff role assignment in the product; they are dumped by `dumpdata` (m2m is serialized on the parent
  object) and are simply **not counted** on the way back.
- `_verify` (:280-300) compares only those counts. It compares no field value, so a restore that zeroes every
  `price`, swaps every `status`, or truncates every `detail` JSON blob is also a pass, because the counts match.
- The tests pin exactly the failure counting can see: `--simulate-failure` deletes one row (`:256-278`), and
  `test_drill_verifies_a_populated_database` (:433-446) proves only that the snapshot line is not " 0 objects".
  No test creates a row with a distinctive value and asserts it in the restored copy, and no test simulates a
  *content* divergence - so the verifier's discriminating power beyond counts is itself unverified.
- Consequence in the operator's hands: `docs/runbook-incident-recovery.md:16-31` makes this command step 0 of
  recovery, and `docs/compliance/S22.md:19` marks R-22.10 IMPLEMENTED on "19 hermetic tests". A rehearsal that
  returns rows but no role assignments would be signed off.

Fix shape: add `include_auto_created=True` to `_row_counts` (one-line, no behaviour change on the sqlite
target), and add a content digest - e.g. one sha256 over the serialized dump per model compared after
`loaddata` - plus a test that corrupts a field (not a row) and expects failure.

### Q10-03 - The isolation module's wiring test is `f(x) == f(x)`
**P3 LOW - TEST - Confidence H - FOLD-INTO-NEXT**

`test_the_key_from_this_run_is_the_configured_database` (:364-370):

```python
self.assertEqual(
    LockedDiscoverRunner(verbosity=0, interactive=False).get_lock_key(),
    test_database_identity(),
)
```

`get_lock_key` (`common/test_isolation.py:293-296`) is `if self._lock_key_override is not None: return it;
return test_database_identity()`. No override is passed, so both sides call the same function with the same
(default) argument. The assertion is true for every possible settings module, every `DATABASES`, and even if
`LockedDiscoverRunner` were deleted from `settings.TEST_RUNNER`. Its name and its "the runner's default key
must be exactly what the pure identity function derives for it" comment promise wiring coverage the test
structurally cannot deliver.

The wiring gap it hides is real: **no test asserts `settings.TEST_RUNNER`** (grep over `backend/` for
`TEST_RUNNER`: one settings line, one changelog row, zero test files). A one-line assertion
(`self.assertEqual(settings.TEST_RUNNER, "common.test_isolation.LockedDiscoverRunner")`) is what actually
guards the P0-1 fix; the two-halves story in the docstring (:1-19) is 543 lines of helper unit tests around
that one missing line.

Secondary to the same question ("does it prove isolation?"): `TestRunRedisClearIsolationTests` (:113-157) is a
real runtime proof of the cache half, but it `skipTest`s on three separate conditions (:119, :121, :142) -
unset `REDIS_URL`, non-Redis default backend, unreachable Redis - so on a Redis-less CI it contributes
nothing while its class name still reads as proof.

### Q10-04 - The cooldown-expiry test deletes the expiry it is meant to test
**P3 LOW - TEST - Confidence H - FOLD-INTO-NEXT**

`:149-161` sends once, then does `caches["alerts"].delete("alerts:cooldown:low_stock")` and sends again,
asserting two mails. That proves "if the marker is absent, the alert sends". It does not touch the mechanism
that makes it absent: `ops/alerts.py:82-86` sets the marker with `timeout=settings.ALERT_COOLDOWN_SECONDS`
(`config/settings.py:1082`, default 300). If that `timeout=` argument were dropped, set to `None`, or bound to
a wrong setting, the suite stays green and the documented "mail-bomb bound" becomes "suppressed forever after
the first alert". A `timeout` mutation is the obvious thing this test should be red on.

Fix shape: assert the marker's TTL (`caches["alerts"].ttl(...)` where the backend supports it, or
`override_settings(ALERT_COOLDOWN_SECONDS=0)` and send twice), keeping the deterministic no-sleep property.

### Q10-05 - The per-process-cooldown regression is not actually pinned
**P3 LOW - TEST - Confidence H - FOLD-INTO-NEXT**

`CooldownBackendTests` (:426-443) is the class whose docstring names the defect it exists for ("LocMemCache is
per-process, so each gunicorn worker held its own window and the documented mail-bomb bound did not hold"). Its
two tests assert (a) the marker is on `caches["alerts"]` and not on `caches["default"]`, (b)
`caches["alerts"] is not caches["default"]`. Both are satisfied by *any* two distinct cache objects, including
two `LocMemCache` instances. Setting `ALERT_CACHE_BACKEND` (`config/settings.py:1071-1074`) to
`django.core.cache.backends.locmem.LocMemCache` re-introduces exactly the ASYNC-2d defect and this class stays
green. Nothing asserts the backend is shared out-of-process, nor that `settings.CACHES["alerts"]["LOCATION"]`
differs from the default alias's.

Fix shape: assert `settings.CACHES["alerts"]["BACKEND"]` is not a `locmem` backend (or that it is the
`filebased`/`redis` class), which is the property that makes the window cross-process.

### Q10-06 - The saved-filter uniqueness authority is a mock, and three zero-assertions have a zero baseline

### Q10-08 - `assertLess(elapsed, 5.0)` cannot see a missing retry
**P3 LOW - TEST - Confidence H - FOLD-INTO-NEXT**

`:321-329` creates a 0.2s-timeout contender against a held lock, times `acquire()`, expects `SuiteLockError`
and asserts `elapsed < 5.0`. An implementation with `self.timeout = 0` (immediate refusal) satisfies this

actually spent - is unasserted, and an accidentally-zero `TEST_SUITE_LOCK_TIMEOUT` default
(`test_isolation.py:159-165`) would ship silently. `assertGreaterEqual(elapsed, 0.15)` restores the other half
without any sleep-based flakiness (the sleep is 0.1s).

### Q10-09 - "Every hook writes inside its side effect's atomic block" is proven for two hook families
**P3 LOW - TEST - Confidence M - FOLD-INTO-NEXT**

`:6-8` states the claim universally. The two `rollback together` pins are `test_checkout_rolls_back_together_

writes the event and no other row of its own), which is why this is a docstring-scope point rather than an
