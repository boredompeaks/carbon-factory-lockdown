## Focus questions, answered

1. **Does `notify_background_job_failure` keep its never-raises contract on every call path?** Mostly, but not
   by construction. `_send` (alerts.py:92–123) wraps the cooldown check *and* the recipient loop in one
   `try/except Exception`, and the dead-letter caller (`common/notifications.py:920–925`) does not need its own
   guard because of that. What is **not** covered is the prologue every public entry point runs before
   `_send`: `not _recipients()` sits outside any try at alerts.py:311 (and 134/223/284), and
   `notify_payment_failure_spike` evaluates the audit queryset with `len(recent)` at :200 — a DB read — outside
   a try. So the promise holds for send failures and does **not** hold for a failure in the guard itself; see
   Q21-06. The blast radius when it breaks is real: the dead-letter alert is raised inside a drain pass that has
   already failed, and `drain_notifications` (notifications.py:1100) has no per-row guard, so one raise ends the
   rest of the batch.
2. **Is alerting deduped/throttled so a failing job cannot alert-storm?** Frequency yes, size no, and the bound
   is softer than the docstring implies. One marker per alert type for `ALERT_COOLDOWN_SECONDS`; but the marker
   is armed *before* the send (so a failed send burns the window and a terminal dead-letter is never re-alerted,
   Q21-03), it fails open with no fallback when the cache raises (Q21-05), `ALERT_COOLDOWN_SECONDS` is parsed
   with `_env_int` so `0` disables it silently, and one mail's body is unbounded (Q21-04).
3. **Are ops models append-only and bounded?** Only one model exists (`SiteSettings`, singleton pk=1), so
   nothing grows without bound and there is no append-only log to violate. It is mutable config, not a ledger,
   and its `save()` forces `pk=1` on any instance (Q21-08). Django `LogEntry` covers admin edits of it; in-app
   there is no history of the previous policy value.
4. **Does the admin expose destructive actions without capability/confirmation?** No. `SiteSettingsAdmin` maps
   `view`/`change` to `settings.manage` (admin + superadmin only), hard-returns `False` for both add and delete
   above the superuser bypass, declares no bulk actions (so `action_capabilities`/confirmation machinery is
   never reached), and `get_queryset().filter(pk=1)` + the changelist redirect make the second row unreachable.
   The one write is the ordinary change form. Covered by `orders/tests_returns.py:2781`
   (`test_only_settings_manage_roles_may_read_or_write_the_window`: a support POST is 403 and the stored policy
   is unchanged). Clean.
5. **Are job-failure/backup status writes atomic and monotonic?** The status machine itself
   (`common/notifications.py`) is sound where it matters: the claim is `select_for_update` + lease + re-check
   in one short transaction (:816–837), `attempts` increments at claim time (:834) so a worker that dies still
   spends an attempt, and `_record_success`/`_record_failure` use conditional `QuerySet.update()` and branch on
   the updated row count so a purged row reports `VANISHED` instead of a false success (:873–882, :947–962).
   What is **not** monotonic is the status predicate: the three terminal writes match on `pk` alone, so a late
   write is last-writer-wins rather than "only from a non-terminal status" (handoff H1). Ordering is right for
   the alert: the row is stamped before the mail is attempted, so an alert failure can never lose the row.
   Backup status writes (`ops/management/commands/backup_db.py`, 521 lines; `restore_drill.py`, 286) are outside
   this brief's file list and cross-flow owned — **not audited** (see UNCHECKED).
6. **Secret/PII in alert payloads or logs?** No secret reaches an alert payload: the outage body carries
   `database/media_writable/shipping_configured/razorpay_mode/smtp_configured`, i.e. booleans and a mode word —
   never a key, host user or password. PII reaches two places: the failing-recipient log line at alerts.py:118
   (staff addresses) and the dead-letter mail body, whose `_error_text` is the raw exception text — for
   `SMTPRecipientsRefused` that includes the *customer's* refused address, and the suite asserts exactly that
   string reaching the alert body (`test_notification_outbox_worker.py:1370–1384`). Q21-10.

## Q21-01 — P2 MEDIUM — the public `/health/` probe writes a fixed-name file per request: a two-request overlap turns a healthy store into `degraded`/503
`backend/ops/services.py:83–91` (path `:86–88`); served by `backend/ops/views.py:69–94`; public (no permission
class, reachable anonymously — pinned by `tests.py:39–72`).

```python
settings.MEDIA_ROOT.mkdir(parents=True, exist_ok=True)
probe = settings.MEDIA_ROOT / "health_probe.txt"   # one fixed name for the whole process group
probe.write_text("ok", encoding="utf-8")
probe.unlink()                                      # <- second finisher raises FileNotFoundError
```

Two overlapping probes — a load-balancer healthcheck and the compose `HEALTHCHECK`, or any anonymous caller
pacing requests — interleave as write/write/unlink/unlink; the second `unlink` raises `FileNotFoundError`, the
`except Exception: return False` swallows it, and `get_health` reports `media_writable: False` →
`status: "degraded"` → **503** (services.py:160–162). Probe 2 reproduces the mechanism deterministically
(`second unlink raised FileNotFoundError`). Three consequences beyond the wrong status:

- every release-time waiter gates on that status (`compose up --wait`, `release-uat.sh` `curl -fsS`, the image
  `HEALTHCHECK` — see the SPEC-Q-S2 changes row), so a flapping probe can fail a deploy or roll a healthy
  container out of the LB rotation;
- the degraded branch fires `notify_integration_outage` (`views.py:80–91`), i.e. the failure mode generates the
  very alert it reports, per cooldown window;
- the endpoint is anonymous and unthrottled, so an unauthenticated caller can force a `write`+`unlink` into
  `MEDIA_ROOT` (settings.py:849, publicly served under `MEDIA_URL="/media/"`, :842) at request rate — a
  file-creation primitive on the same directory that holds customer uploads, plus write amplification.

Fix: use a per-call unique name (`tempfile.NamedTemporaryFile(dir=MEDIA_ROOT, delete=True)` or
`uuid4()` suffix) and treat only ENOENT on unlink as success; or better, probe without creating a file
(`os.access(MEDIA_ROOT, os.W_OK)` plus a `statvfs` free-space check) so a polled public GET has no write at all.
Confidence: H (mechanism executed). Triage NEXT-BUILD.

## Q21-02 — P2 MEDIUM — `get_health()` only degrades for its first query block; later DB reads raise, so the probe 500s and the outage alert never fires
`backend/ops/services.py:124–131` (guarded) vs `:150` and `:156–157` (unguarded); consumer `ops/views.py:74–91`.

Triage NEXT-BUILD.

## Q21-03 — P2 MEDIUM — the cooldown marker is armed before the send it bounds, so a failed alert burns the window and a terminal dead-letter is never re-alerted
`backend/ops/alerts.py:79–89` (arm) vs `:104–118` (send); caller `common/notifications.py:920–925`, row state
`:944–956` / `:994–997`; terminality `:677–680`.

`_in_cooldown` writes `alerts:cooldown:<type>` **first**, then `_send` attempts the mail. If the SMTP send fails,
the marker is already spent for `ALERT_COOLDOWN_SECONDS` and `_send` returns `False` — which `_alert_dead_letter`
ignores. For `background_job_failure` that is not recoverable by repetition: the row that tripped it is `DEAD`,
`CLAIMABLE_STATUSES` excludes `DEAD` (:677–680), and only an operator `--retry-dead` reopens it. So one bad
minute from the mail provider, at the instant a customer's confirmation was dropped, leaves a single
`logger.exception` line as the only trace of both the dropped mail and the dropped alert about it.

The same window is also lossy the other way: a burst of dead rows produces one mail naming one `pk`, never
"N rows died", so a drain that dead-letters 40 rows after a template change reads as a single failure.

No test covers re-attempting after a send failure: `test_all_recipients_failing_reports_false`
(`tests/test_alerts.py:394–408`) asserts `False` and stops; `test_an_alert_send_failure_never_breaks_the_drain_loop`
(`test_notification_outbox_worker.py:1434–1452`) asserts the row still dies and the loop continues.

Fix: arm the marker only after the first successful send (`set()` on the success path), so a failed send leaves
the window open and the next drain tick retries; optionally aggregate the burst count into the body.
Confidence: H (source). Triage NEXT-BUILD.

## Q21-04 — P2 MEDIUM — alert bodies are rendered from unbounded querysets: frequency is throttled, size is not
`backend/ops/alerts.py:266–270` → `:200–210` → `:172–186`; `backend/ops/services.py:195–198` → `alerts.py:126–130`.

`check_payment_failure_spike` builds `AuditEvent.objects.filter(..., created_at window).order_by("-created_at")`
with no `.count()`/slice; `len(recent)` materialises every row and `_failure_rows` renders one line per row into
the mail body — and `send_email` re-renders that body once per recipient. The trigger is a *burst* condition
("at least 3 in 300s"), so the worst gateway hour produces the largest mail: a 50k-failure window is a
50k-line email, assembled in the dashboard request (views.py:186), once per window. Same shape for stock:
`check_stock_alerts` passes the whole `stock=0` / `0<stock<=threshold` querysets to `_alert_rows`, so a
catalogue-wide stock zeroing is one mail with one line per SKU.

The cooldown bounds how many mails, not how big one is — which is exactly the wrong half of the bound for a
storm defense.

Fix: `.count()` for the number, `[:20]` for the sample, and a "(+N more)" tail in the template (the codebase
already has this pattern in `DEAD_RETRY_PK_LOG_LIMIT`, notifications.py:1121–1126). Confidence: H.
Triage NEXT-BUILD.

## Q21-05 — P2 MEDIUM — the only storm bound fails open with no fallback, and one of its triggers is anonymous
`backend/ops/alerts.py:79–89` (fail-open) + `config/settings.py:1082` (`_env_int`) vs `:523` (`_env_positive_int`);
trigger `backend/ops/views.py:80–91`.

`_in_cooldown`'s `except Exception: logger.exception(...)` returns `False` = "not suppressed", so a cache outage
degrades to *one mail per caller*. The docstring justifies the direction ("worst case un-deduped"), which is
right for a single dashboard load and wrong for the route that is polled: `/health/` is anonymous and
unthrottled, so a cache outage coinciding with a degraded probe sends one mail per request to every address in
`ALERT_RECIPIENTS` for as long as both conditions hold. Q21-01 supplies a way for any anonymous caller to *make*
the probe degraded, so the two findings compose.

`ALERT_COOLDOWN_SECONDS` is read through `_env_int` (settings.py:513–520), which accepts `0` and negatives; a
`0` timeout means "expire immediately", i.e. the operator who typed it to mean "don't throttle" has disabled the
bound silently. `_env_positive_int` already exists one function below (:523) and is used for `EMAIL_TIMEOUT` —
it is the right parser here.

`test_cache_failure_fails_open_and_still_sends` (`tests/test_alerts.py:352–366`) pins the fail-open, so the fix
must keep fail-open's *delivered* behaviour while adding a per-process fallback marker (e.g. a
`LocMemCache`-backed secondary window) and validating the knob.

Fix: `_env_positive_int` for the cooldown; keep fail-open but fall back to an in-process marker so a broken shared
cache degrades the bound from "across workers" to "per worker" instead of to "none". Confidence: H (mechanism),
reachability requires a cache fault or the typo. Triage NEXT-BUILD.

## Q21-08 — P3 LOW — `SiteSettings.save()` forces `pk=1` on every instance, so any future `SiteSettings()` save overwrites the entire published policy with defaults
`backend/ops/models.py:187–189`; demonstrated by `backend/ops/tests.py:254–264`.

```python
def save(self, *args, **kwargs):
    self.pk = 1  # singleton
    super().save(*args, **kwargs)
```

The intent (one row) is right; the side effect is that an unsaved instance is not refused, it is **aliased onto
the row**: `SiteSettings().save()` writes field defaults over the live policy (`return_window_days` → NULL, so
the published 30-day window becomes "unset"; `maintenance_mode` → False; contact channels → ""). The test does
exactly this and asserts only the row count, so the data loss is invisible to the suite. Any future management
command, data migration or `get_or_create`-free seed path that constructs an instance is a one-line policy wipe,
and the admin's `has_add_permission → False` does not protect the ORM.

Secondary: `load()`'s `get_or_create(pk=1)` means `GET /api/settings/` and every dashboard render perform a
write attempt on a read path (harmless once the row exists, but it makes an anonymous GET a `SELECT … FOR
UPDATE`-free upsert).

Fix: `if self.pk not in (None, 1): raise ValueError(...)`, or refuse create entirely
(`if not self.pk: raise ValidationError`) and let `load()` remain the only creator. Confidence: H.
Triage FOLD-INTO-NEXT.

## Q21-10 — P3 LOW — alert PII: staff addresses logged on every failed mailbox, and the dead-letter mail body carries raw provider error text (a customer address)

## Axis 3 — SAST

- **No missing permission surface in scope**: `ops/views.py` gates `health_detail`/`dashboard`/`audit_log` with
  capability classes (`HasReportsRead`, `capability_required("reports.read"|"staff.manage")`);
  `/api/settings/` and `/health/` are deliberately public and carry no PII/money (whitelist-projected,
  `views.py:33–66`).
- **Anonymous write primitive** — Q21-01 (the only in-scope write reachable without auth).
- **Unbounded queries/loops** — Q21-04; also `check_payment_failure_spike`'s window query has no `limit`.
- **Secrets in payloads/logs** — none found: the outage alert's `checks` are booleans plus `razorpay_mode`
  (`test`/`live`/`unset`, services.py:94–100), and `smtp_configured` is a `bool()` of presence, never the
  credential. PII: Q21-10.
- **IDOR / mass assignment / raw SQL / SSRF / unsafe deserialization** — none in scope (no request-derived
  queryset scoping, no serializer, no `raw()`/`extra()`, no outbound HTTP).
- **Log injection** — `_error_text` interpolates an exception message that may contain newlines into both a log
  line and the alert template body; a crafted provider/template error could forge a second line in the mail.
  Not worth its own row (arbitrary content already reaches the mailbox by design), noted for the Q21-10 fix.
- **Error leakage** — Q21-02 (500 instead of the degraded envelope) is the only path where an internal error
  reaches the wire; Django's `DEBUG=false` handler means no traceback.

## Axis 4 — architecture / smells

- **Layering**: `services` holds detection, `alerts` holds dispatch, views only wire them — correct direction.
  The dependency back-edge `ops.alerts → common.notifications.send_email` with the compensating function-local
  `common.notifications → ops.alerts` import (`notifications.py:899–903`) is a real cycle broken by convention,
  documented on both sides; acceptable but fragile (Q21-06's prologue inherits it).
