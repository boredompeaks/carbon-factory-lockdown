## Findings

### Q07-01 | P2 HIGH | CODE | `orders/admin.py:1067-1068` (with `1029-1034`) | Confidence H — NEXT-BUILD

**Claim.** `CouponAdmin.save_model` returns before `super().save_model(...)` when `change` is False, so **adding a coupon through the admin never saves it** — and the admin still reports success and writes an `ADDITION` LogEntry for a row that does not exist.

**Evidence.**
- `:1052-1073`: `def save_model(self, request, obj, form, change):` … `if not change: return` (`:1067-1068`) … `super().save_model(request, obj, form, change)` (`:1073`). The `super()` call is *after* the early return and is the only write.
- The add form is reachable: `capability_map["add"] = "discounts.write"` (`:1029-1034`), `RoleAwareModelAdmin.has_add_permission` → `_map_grants(request, "add")` returns True for marketing/admin/superuser (`common/admin.py:178-190`), and `tests/test_admin_rbac.py:133-147` *asserts* that True. No test exercises the add POST for `Coupon` (grep `CouponAdmin|coupon_add|orders_coupon_add` over the whole backend = the two registry lines in that RBAC test).
- Django 6.1.1 `options.py:2148,2152,2157-2159`: `save_form(..., change=False)` does `form.save(commit=False)` (no DB write), `save_model(..., not add)` is what must persist, and `log_addition` + `response_add` then run regardless — "was added successfully" with `object_id` empty.

**Impact.** Marketing adds a promotion, is told it succeeded, the coupon list shows nothing, and checkout answers `Invalid coupon code` (`checkout.py:560`). Fix: `super().save_model(...)` unconditionally and put the `before`-snapshot/log block behind `if change:`.

### Q07-02 | P2 MEDIUM | CODE | `orders/admin.py:490-492,541-550` (contrast `:567-599`) | Confidence H — NEXT-BUILD

**Claim.** The order change form — and the `list_editable` status cell, which routes through the same method — checks the transition against an **unlocked** read of the row and then writes the whole row, so two operators acting on one order produce a lost update and an `OrderStatusEvent` whose `from_status` never happened.

**Evidence.**
- `:490-492`: `old = Order.objects.get(pk=obj.pk).status` — no `transaction.atomic`-scoped lock, no `select_for_update`, and the value is only used to gate `transition_allowed(old, obj.status)` (`:493`) and to stamp the audit row (`:546`).
- `:542` `super().save_model(...)` → Django `options.py:1475` `obj.save()` = every column, no `update_fields`, no status predicate in the `UPDATE` (unlike the bulk twin's per-row re-check at `:630`).
- The bulk twin is the model: `_locked_orders` = `.select_related(None).select_for_update().order_by("pk")` (`:594-599`), documented at `:576-585` as necessary *because* the changelist query carries outer joins — i.e. the lock discipline was already thought through for the bulk path only.
- `list_editable = ("status",)` (`:303`); Django `options.py:2297-2308` sends each changed changelist row through `save_model(..., change=True)` inside one `atomic` block — so the same unlocked read gates it.

**Impact.** Order `pending`; A submits `confirmed`, B submits `cancelled`; both pass `transition_allowed("pending", …)` against the same read; the second `UPDATE` overwrites the first (Postgres READ COMMITTED does not re-evaluate a `WHERE` that does not name the status — *source-read reasoning, not probed against a live DB*), and the trail holds two events both claiming `from_status="pending"`, one of which describes an edge the row never took. The row can therefore end in `cancelled` **from** `confirmed`, an edge `ALLOWED_TRANSITIONS` declares illegal, and every editable column (address, phone, `user`) is clobbered by the stale instance. Fix: `Order.objects.select_for_update().get(...)` at `:492` (the change view's outer atomic holds it to commit) + a status predicate on the write, mirroring `_locked_orders`.

### Q07-03 | P2 MEDIUM | CODE | `orders/admin.py:493-522` | Confidence H — NEXT-BUILD

**Claim.** Both refusal branches `return` out of `save_model`, but Django logs the change unconditionally afterwards, so a refused transition still writes a LogEntry saying the order's status changed — on a financial record whose privileged-action trail is a compliance artefact (spec 6.12.6).

**Evidence.**
- `:505-507` and `:520-522`: `self.message_user(..., messages.ERROR)` then `return  # abort the save; status unchanged`.
- Django `options.py:2152-2162`: `save_model` → `save_related` → `construct_change_message` → **`log_change`** — no branch on what `save_model` did. `log_change` writes `/admin/orders/order/<pk>/history/` "Changed Status." with the submitted value, which is still in `obj` while the DB keeps the old one (the early return skips `super().save_model`, so nothing was written).
- The repo already knows this exact trap and documents it as the reason the sibling surface validates in the form instead: `admin.py:1418-1423` — "an aborted `save_model` still gets logged by Django's own `log_change` (it runs after `save_model` returns, unconditionally), so a refusal that way would leave a 'Changed status' entry on a row whose status never moved." `ReturnRequestAdminForm.clean_status` is the fix pattern already in this file.

**Impact.** Every blocked attempt (unpaid order → shipped, paid order → cancelled) leaves a false history entry plus a message telling the operator nothing changed. Fix: move the two guards into an `OrderAdminForm.clean_status` (or re-raise as a form error) so the save never starts.

### Q07-04 | P2 MEDIUM | CODE | `orders/admin.py:353-361` (with `335-352`) | Confidence H — NEXT-BUILD

**Claim.** The order change form exposes `user` **and** `guest_email` as writable, but nothing validates the two-owner rule the database enforces, so clearing the customer — or typing a guest email on an account order — raises an `IntegrityError` (HTTP 500) instead of a form error.

**Evidence.**
- `fieldsets` `Customer` group: `{"fields": ("user", "guest_email", "full_name", "phone")}` (`:355-360`). `readonly_fields` (`:335-352`) lists neither, and `OrderAdmin` declares no `form`/`clean` anywhere in the file (only `IssueRefundForm` and `ReturnRequestAdminForm` exist).
- `models.py:386-392`: `CheckConstraint(condition=Q(user__isnull=True, guest_email__gt="", guest_token__isnull=False) | Q(user__isnull=False, guest_email="", guest_token__isnull=True), name="orders_account_xor_guest_ck")`.
- `models.py:127-133` `user` is `null=True, blank=True` — the FK widget therefore offers an empty choice, and `guest_email` is `blank=True, default=""` (`:143-147`), i.e. a free text input on every row. Either edit violates the constraint at `obj.save()`.
- `checkout.py:410-412` states the rule that the admin does not check: "the Meta constraint allows exactly one owner per row, and an account row carries the empty guest_email, never NULL."

**Impact.** A 500 (the atomic block rolls back, so no corruption) on a one-click action for any `orders.fulfill` holder — and the operator gets a server-error page instead of "this order already has an owner". Fix: an `OrderAdminForm.clean()` enforcing the XOR, or render `guest_email` read-only while `user` is set (and vice versa).

### Q07-05 | P2 MEDIUM | CODE | `orders/views/checkout.py:421-429` vs `661-687` | Confidence H — NEXT-BUILD

**Claim.** The cart gates run **before** the `Idempotency-Key` probe, so a keyed retry that arrives after the sale was captured answers `400 Cart is empty` (or 404) instead of replaying the original order — the one case idempotency exists for.

**Evidence.**
- Order of the body: `resolve_cart(request, create=False)` (`:421`) → `404 Cart not found` (`:423-424`) → `if not cart_items.exists(): 400 Cart is empty` (`:428-429`) → … → the keyed probe at `:661-687`.
- Real settlement empties the linked cart: `inventory.py:291-295` `Cart.objects.select_for_update().filter(order=locked_order).first()` then `linked_cart.items.all().delete()`. The `Cart` row survives (and is bound to the order at `checkout.py:820-821`), so `resolve_cart` still returns it and the answer is exactly `400 {"error": "Cart is empty"}`.
- The docstring claims the opposite: `:651-660` — "a keyed replay collapses onto the original order regardless of payload drift, the dedup window, or **a settled first attempt**".
- The test that is supposed to pin it fakes settlement instead of performing it: `orders/test_idempotency.py:194-196` does `Order.objects.filter(pk=...).update(status="confirmed", razorpay_payment_id="pay_SETTLED")` and never clears the cart — see Q07-08.

**Impact.** A retry queued offline/after a page reload replies "Cart is empty" to a customer who already paid; an SPA that retries on 400 with a fresh key mints a second order. Fix: probe `(user, Idempotency-Key)` — or `cart.order` — before the emptiness gate, since the cart row already carries the binding.

## Axis sweep

**Axis 1 — invariants.** Money: `Decimal` end-to-end, single `quantize_money` at the total (`checkout.py:767`), 2-dp strings on the wire via `MoneyField`/`money_string`; the coupon minimum is rendered with `money_string` (`:596`). Atomicity: order + number + key binding + snapshots + reservations + status event + `AuditEvent` in one block (`:619-907`), shipping refusal raised *out* of the block so nothing partial commits (`:613-618,909-917`). Lock order: cart → user (`:627,662`) vs Order → products → coupon → cart at capture (`inventory.py:133,154,214,292`) — no cycle found. Uniqueness: order number retried on `IntegrityError` inside a savepoint (`:775-810`), reservations re-target under a lock (`:345-359`), return/refund request duplicates caught by a partial unique index + savepoint (`return.py:723-795`). State machine: every status write in `admin.py` goes through `transition_allowed` + `precondition_failures`, and `checkout.py` uses `state.TRIGGER_ORDER_CREATE` rather than a literal; the return machine is a second, documented table (Q07 focus 4). Authz: `permission_classes` on every view, ownership as the queryset filter in `return.py`, capability map on every admin — no inline `is_staff` anywhere in the four files. **Violations: Q07-02 (lock), Q07-03/Q07-07 (audit truthfulness), Q07-04 (constraint not validated at the form).**

**Axis 2 — correctness.** Non-string bodies are typed-gated on both seams (`_object_body` `:68-80`; `_return_body` `:85-124`, which refuses `int`/`list`/`dict`/`bool` instead of coercing). `_field_length_rejection` reads the width off the model (`:131-148`). Pagination is totally ordered with an id tiebreaker (`return.py:575-579`) and `get_page` never 404s. Timezone: every comparison is tz-aware `timezone.now()`; the return window is inclusive of its last day and reads the clock **once** per predicate (`:378-418`). Exceptions: `ShippingUnavailable`, `RefundRefused`, `RefundGatewayError`, `MalformedReturnRequestBody`, `Coupon.DoesNotExist`, `Order.DoesNotExist` all caught; no bare `except`. Check-then-act: the two that remain (coupon `used_count`, `:582`) are documented advisory gates with a capture-side record (`inventory.py:183-256`) — not reported. `update_fields` omissions: the bulk writers list `updated_at` deliberately (`:656-658,817-824`); the change form's bare `obj.save()` is the *over*write problem in Q07-02. Partial failure mid-loop is per-row atomic and reported to the operator (`:1281-1298,1312-1333`).

**Axis 3 — SAST.** No missing `permission_classes`; no IDOR (ownership is the filter in all three return reads and `_guest_lookup_miss`/`_return_detail_miss` are byte-uniform 404s); no mass assignment (no `**request.data` into a model; the admin's editable-field set is declared); no secrets or credentials logged; no `eval`/`pickle`/raw SQL; no SSRF (the only outbound call is `refunds_core`); no `__all__` serializers; the one error-leak risk is handled (`shipping` refusal echoes our own message only, `:915`). Log injection: the checkout log lines interpolate `duplicate.customer_name`/`user`, not headers (`:635-640,680-685,761-766`) — the webhook path's raw-header log is QC-024, elsewhere. Unbounded: `export_csv` streams the whole selection (`:961`) — no cap, noted but not filed. PII to third parties: none. **One injection finding: Q07-10.**

**Axis 4 — architecture.** `checkout.py` (1,104) and `admin.py` (1,516) are at the far end of god-module sizing, but the prose density is deliberate and the seams are single-purpose. Duplication that could drift: the coupon rule set exists twice — the full one in `validate_redeemable_coupon` (`checkout.py:984-1021`) and an inline copy in `create_order` (`:555-599`) with *different* messages, which is intentional (uniform rejection public, differentiated authenticated) but means one new coupon rule must be added in two places. Hidden I/O: `_return_window_days()` performs a `get_or_create` INSERT on the singleton inside a *create* request's transaction (`return.py:287-293`, acknowledged). Module-level side effects: none beyond registrations. Layering inversion: Q07-12.

**Axis 5 — test side.** Would the test fail if the guard were deleted? `tests_state_vocabulary.py` is the good case (hand-written literals, never derived from the constant under test, deliberately mutation-proof). The idempotency suite is the weak case: Q07-08. Missing negative/authz/concurrency coverage in this flow: (a) the order change form's serialization of two operators — unprovable on SQLite (no `select_for_update`), so it needs a lock/SQL pin like the one the bulk twin now has; (b) the aborted-transition LogEntry (asserting *no* `LogEntry` was written); (c) the two-owner XOR through the admin form; (d) `mark_delivered` confirmation (the interstitial path is already tested for `cancel_pending`, so extending it is cheap); (e) a coupon-add round-trip. Every claim above is a static read; nothing was executed against SQLite or Postgres.
