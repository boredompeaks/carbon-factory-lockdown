## Verdicts on the seven focus questions (detail in the findings)

| Question | Verdict |
|---|---|

## Findings

### Q08-01 | P2 MEDIUM | CODE | `shipping/models.py:466-477` (with `:87-126`, `lifecycle.py:103`) | Confidence H — NEXT-BUILD

**Claim.** A parcel's status can be moved with **no** `ShipmentEvent` and with **no** order sync through a plain object save, which is the one write path both the append-only guards and the module's own docstrings say is closed.

**Evidence.**
- `models.py:87-99` refuses `"status"` in `ShipmentQuerySet.update`; `:101-126` refuses it in `bulk_update`. `:202-213`'s docstring concludes: *"`ShipmentQuerySet.update` is what makes that true rather than merely intended: a bulk `update(status=...)` would move a parcel with no record of where it moved from, so it is refused."*
- `Shipment.save` (`:466-477`) applies only the width gate, then `super().save(...)`. Django 6.1.1 `_do_update` (`venv/.../db/models/base.py:1208-1246`) issues the UPDATE via `filtered._update(values, returning_fields)` at `:1243` — the private method, not `QuerySet.update` — so **the guard is never reached**. Verified by reading the installed framework, not inferred.
- Consequence: `shipment.status = Shipment.Status.DELIVERED; shipment.save()` commits a delivered parcel with `label_created` as the last trail row and leaves the linked order at `confirmed`, because `sync_order_status` is called **only** from `ShipmentAdmin.save_model` (`admin.py:235`). The drift `lifecycle.py` exists to prevent (`lifecycle.py:1-14`) reappears silently.
- The bulk paths are pinned as closed (`tests_tracking.py:1333`, `:1341`), and `:1341-1347`'s comment even states *"that is why the refusal lives on the QUERYSET rather than on `Shipment.save`"* — i.e. the gap is acknowledged as a design choice, but the choice is unsafe: the natural writer for the carrier-integration half of spec 6.9 (line 2007) is exactly `obj.status = …; obj.save()`.

**Impact.** A trail that is append-only and complete only for the admin writer. Fix is one guard in `Shipment.save` (refuse a status change unless a flag/`save_model` path set it, or write the event there) — a single place, since the admin is the only sanctioned caller today. **No test fails today if the guard is added or removed** (see Q08-10).

### Q08-02 | P2 MEDIUM | CODE | `shipping/models.py:243-246` (with `pricing.py:198-211`) | Confidence H — NEXT-BUILD

**Claim.** `ShippingRate.amount` is money with **no range validation anywhere** — not in the model, not in a constraint, not in the admin form, not in the resolver — so a negative (or column-overflowing) rate is storable and flows straight into `Order.shipping_amount` and `total_amount`.

**Evidence.**
- `models.py:239-246` declares `DecimalField(max_digits=10, decimal_places=2)` with no `validators`, no `clean`, no `MinValueValidator`. `migrations/0001_initial.py:51` is the same field and adds no `CheckConstraint` (`grep CheckConstraint|MinValue shipping/migrations/*.py` → none).
- `ShippingRateAdmin` (`admin.py:77-93`) declares no `formfield_overrides`, `get_form` or `readonly` for `amount`, so Django's `ModelForm` gives a plain `DecimalField` that accepts `"-49.00"` (Django imposes no `min_value` from `max_digits`).
- `pricing._charge` (`:198-211`) only quantizes: `quantize_money(rate_amount)` → `Decimal("-49.00")`. `common/money.quantize_money` (`:16-24`) is a bare `quantize(...)` with no sign or bound check.
- `checkout.py:713-767` then stores it: `shipping_amount = shipping_quote.amount`, `total_amount = quantize_money(merchandise_total + shipping_amount)` — so every order in that geography is **discounted** by the typo, and the gateway charge follows (`total_amount` is what `create_payment` reads).
- The same absence bites in the other direction: a rate near the column cap added to merchandise near the cap overflows `Order.total_amount` (`max_digits=10`) — a `DataError` 500 on Postgres and a silent write on SQLite, the exact engine-asymmetry the module guards for string widths (`models.py:54-71`).
- The codebase's own position that negative money is invalid is stated twice: `config/settings.py::_env_money` refuses negatives (pinned `tests.py:1321-1323`) and `seed_shipping_methods._money` refuses `-1` (pinned `tests.py:1682-1687`). The **admin** path — the one a merchant actually uses — has no equivalent.

**Impact.** A one-character staff typo silently reprices a whole zone and undercharges every order in it; refund ceilings and reconciliation read the same lowered `total_amount`. Fix: `MinValueValidator(Decimal("0.00"))` + a `CheckConstraint(amount >= 0)` (a migration), which makes both engines agree. No test covers this (Q08-10).

**Claim.** A parcel moving **back** to `label_created` or to `exception` syncs nothing and reports nothing, so a corrected parcel leaves the order (and `fulfilment_status`) stuck at `delivered` with no operator warning — the same divergence the module exists to prevent, one direction only.

### Q08-06 | P3 LOW | CODE | `shipping/models.py:272-275` vs `shipping/pricing.py:108` | Confidence H — FOLD-INTO-NEXT

**Claim.** The "one amount per method per geography" constraint is case-**sensitive** while the lookup is case-**insensitive**, so the duplicate the constraint exists to refuse is accepted at the form and the losing row silently never applies.

**Evidence.**
- `models.py:272-275` — `UniqueConstraint(fields=["method", "region", "postal_code_prefix"], name="shipping_rate_geography_uidx")`; the docstring (`:266-271`) promises *"with it, the admin form says so at the point of entry"* and that otherwise *"the winner would be a coin toss"*.
- `pricing.py:108` — `Q(region__iexact="") | Q(region__iexact=region)`. On both SQLite and Postgres the unique index compares bytes by default, so `("standard","Maharashtra","")` and `("standard","maharashtra","")` coexist; `ModelForm.validate_unique` is exact-match too, so the admin shows no "already exists".
- Both rows then match a `Maharashtra` 400001 destination with `_specificity == 1`, so `_rate_rank` (`:165`) falls through to `rate.amount`: the **cheaper** one is charged every time and the other is inert — a silently dead row in a money table, which is the failure mode the docstring claims to have designed out.
- `tests.py:104-110` pins destination-side normalization only (the fixture rate is already lower-case), so the asymmetry is untested.

**Impact.** Mispricing by silent inactivity rather than by coin toss — bounded, deterministic, and invisible in the admin. Fix: store a normalised region (save-time `casefold`) or make the constraint case-insensitive (`UniqueConstraint(Lower("region"), Lower("postal_code_prefix"), "method")`), so the form's uniqueness check matches the lookup.

(f) *Provider path idempotent* — holds; `backfill` and `seed_shipping_methods` both filter/upsert on the state they are about to change.

**CORRECTNESS.** The pricing precedence is a genuine total order on every axis (`_rate_rank` = specificity desc, amount, method code, pk; `_method_rank` = amount, method code, pk) and `_candidate_rates` forces `order_by("pk")` so the database's row order cannot decide a price — pinned (`tests.py:160-177`). No mutable-field write found (the order FK is read-only on the change form; `get_readonly_fields:156-168` and `tests_tracking.py:1954` pin that a posted `order` cannot re-point a parcel).

**SAST.** No `permission_classes` omission found (both views declare `AllowAny` deliberately and the second is owner-guarded; the admin classes inherit the RBAC base). No IDOR (two owner filters, uniform 404).
