## Direct answers to the brief

### 1. Does `test_e2e_admin_ops.py` assert the **admin outcome** or only the HTTP code?

**It asserts the outcome half-way: the status column, and nothing else.** Every case ends in `order.refresh_from_db()` + `assertEqual(order.status, ...)` (`:90-106`, `:114-115`, `:121-122`, `:130-131`, `:187-190`, `:199-207`, `:220-223`) — that part is real and would fail if the guard were deleted.

What is **never** asserted is the other half of "admin outcome":

- **No audit row.** `OrderAdmin.save_model` writes one `OrderStatusEvent` per legal transition, inside the same atomic block (`orders/admin.py:541-550`, `_append_status_event` `:134-145`). Not one assertion in this module mentions `OrderStatusEvent`. A mutation that deletes `_append_status_event(...)` at `:544` leaves all 12 tests green. The invariant *is* pinned — but in `orders/tests.py:3300-3331` (`test_admin_change_form_appends_one_event_per_legal_transition`, `..._skips_noop_saves_and_illegal_moves`), i.e. this e2e module duplicates the status half of the unit suite and drops the audit half.
- **No money assertion.** `total_amount` / `discount_amount` / `currency` are `readonly_fields` (`orders/admin.py:335-352`) and sit in the "Payment (server-computed — read only)" fieldset (`:362-375`), so the change form cannot rewrite them — good — but no test posts `total_amount=1.00` in `_change_status` and asserts the row kept 100.00. The one money-adjacent write in the file is `Order.objects.filter(pk=...).update(payment_status="captured")` (`:86`, `:182`), a fixture that *bypasses* the admin entirely.
- **A real defect this blindness hides (Q32-01).** `save_model` aborts an illegal/precondition-failed transition with a bare `return` (`orders/admin.py:507`, `:522`). Django then continues the view: `_changeform_view` calls `self.save_model(...)` and **unconditionally** `self.log_change(...)` (`venv/…/django/contrib/admin/options.py:2151-2162`), and the `list_editable` changelist path calls `save_model`, then `log_change`, then `changecount += 1` and shows `<n> order(s) were changed successfully` (`options.py:2295-2319`). `OrderAdmin` has `list_editable = ("status",)` (`orders/admin.py:303`) and overrides neither `log_change` nor `response_change` (grep: no override in `orders/admin.py` or `common/admin.py`). So for the exact case at `test_e2e_admin_ops.py:112` (superuser, confirmed→cancelled), the state machine holds, **but `/admin/audit-log/` — which reads `LogEntry` as *the* privileged-action trail (`ops/views.py:243-253`) — records "Changed status" for a change that never happened**, and the grid cell reports success. That is a false privileged-action record on a financial record.
  The sibling module `tests/test_superadmin_tier.py:1012-1017` *does* assert `LogEntry` absence for a refusal — but only for the Django-field-validation refusal (`assertIn("status", form.errors)`, `:1010`), which never reaches `save_model`. The `save_model`-abort refusal is the untested one.

**Weak-but-not-vacuous:** every `assertEqual(res.status_code, 200)` here is taken after `follow=True` (`:78`, `:176`), which lands on 200 both when the change applied (302→changelist) and when the form re-rendered with errors. The code assertion therefore only catches a 5xx; the DB assertions carry all the signal. That is acceptable, but it is why the false-success-message class is invisible.

### 2. Does `test_checkout_refresh.py` prove totals are recomputed and the client cannot inject an amount?

- **Recomputed: yes, once, indirectly.** `:156` asserts `"900.00"` for a 1000.00 cart with a 10 % coupon — that value can only come from `subtotal_amount += product.price * quantity` (`checkout.py:495`) and `coupon_merchandise_discount` (`:605`). But it is the **first** submit that proves recompute; every refresh case only proves the replay returns the *same* number.
- **Cannot inject an amount: not in this file.** No test in the module posts `total_amount`, `amount`, `price`, `discount_amount`, `shipping_amount` or `subtotal` in `checkout_payload()` (`common/testing.py:279-289` — addresses only). The sibling `orders/tests.py:636-658` (`test_total_computed_server_side_client_amounts_ignored`) does forge `total_amount="1.00", discount_amount="999.99", status="delivered", user=<other>` — **on the create path only**. The replay/collapse branch, which is this module's subject, is never given a forged amount. The property it would pin is stated in source at `checkout.py:250-252` ("a collapse returns the ORIGINAL order, with its own persisted shipping_amount and total_amount, so no replay can reprice anything whatever it posts"). The mechanism makes injection *structurally* impossible on the collapse path (`_checkout_response` → `OrderSerializer(order)` off the persisted row, `checkout.py:167-176`), so the test gap is low severity — but the module's docstring sells exactly this safety and never exercises it.
- **A gap that is worth more than injection: no concurrent double-submit.** All nine cases are *sequential* replays (`:56`, `:80`, `:93`, `:111`, `:144`, `:171`, `:189`, `:207`, `:225`, `:247`). The `grep` for `concurrent|ThreadPool|threading|TransactionTestCase` across `orders/tests*.py` and `test_idempotency.py` returns no thread-based test at all. The guard the module exists for (`_find_duplicate_pending_order`, `checkout.py:261-291`) is a check-then-act whose only serialization is the cart row lock at `checkout.py:627` (`Cart.objects.select_for_update()`, inside `transaction.atomic` at `:620`, with the duplicate check at `:629` **inside** the lock — so the code is correct). That lock is unpinned: delete it and every test in this file still passes, because nothing overlaps.
- Minor: the `ORDER_CREATED` audit count (`:73-78`) is asserted only in the first case; `test_repeated_refreshes_never_accumulate_orders` (`:80-91`) — the case that would expose one event per retry — asserts only row counts.

## What these files do well (do not regress)

- `test_nonobject_bodies.py:42-55` is the best assertion pattern in the tree for this defect class: the `{}` response is the **oracle**, and every raw body must match it **byte for byte** (`res.content == expected.content` *and* `res.data == expected.data`). A differentiated error body, a 500, or a per-shape branch all fail. The raw-string posting rationale at `:11-17` (DRF's `format="json"` treating falsy payloads as "no data") is the kind of note that stops the next author from writing a test that posts nothing.
- `test_e2e_isolation.py:79-82` asserts the **persisted** row after the refused cross-tenant write (`quantity == 2`), and `:82` asserts no order was minted. That is outcome-not-code, the standard Q32-01/Q32-03 are missing.
- `test_checkout_refresh.py:73-78` asserts exactly one `ORDER_CREATED` audit row across a replay — the audit-as-outcome habit the admin module lacks.
- `orders/tests.py:3317-3330` already proves the pattern Q32-03 asks for (refusal ⇒ no transition event); porting it into the e2e is a two-line change.
