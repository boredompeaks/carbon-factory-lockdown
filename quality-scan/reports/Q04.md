## Direct answers to the six brief questions

1. **Can `doc_claims.py` pass vacuously?** Yes, four distinct ways, all confirmed in source: the byte-integrity half is bolted to the contents of its own JSON baseline (`Q04-03`); the "green must never mean empty" notice is suppressed by any file that has a `+++` header but zero added lines (`Q04-07`); the existence index is built from the working tree, not from the ref being gated (`Q04-02`); and `.ts`/`.js` names are registered from any occurrence in any file (`Q04-08`). An *empty* base is the one case handled correctly: `empty_scan_notice` fires on `[]` and the exit code is still 0 — by design, documented in the module docstring and mirrored in the workflow's branch-creation fallback, so I do not report that as a defect.
2. **Is a failure attributed to the right file/line?** For real claims, yes: `path` and `line` come from the `+++` header and the `@@` hunk of `--unified=0`, and each added line is scanned individually with its own number (`doc_claims.py:1387-1407`, `1491-1493`). Two exceptions, both recorded below or in the notes: byte-integrity pseudo-errors carry **line 0** (`:1529-1536`), and a *name-resolved* cite can be attributed to a different file than the author meant when uniqueness changes (`§Secondary 4`).
3. **Can a quoted test name be "verified" without the test existing?** Yes, two mechanisms: the index is a working-tree walk that ignores `--head` (`Q04-02`), and for non-Python files any occurrence of the token — a comment, a `.skip`ped spec, an unrelated string — registers the name (`Q04-08`).
4. **Does the red-team script mutate the repo or a DB, and is it safe to run?** It mutates neither the repo's tracked content nor a local DB, but it **does** write `scripts/t1a_evidence.json` into the repo (not gitignored) and it fires live POSTs — register, login, forged Razorpay webhooks, checkout, refund, inventory adjust, cart DELETE/PATCH — at `--base`, **whose default is `https://api.boredompeaks.me`, a non-test host, with no environment guard of any kind** (`Q04-01`). Safe only if the operator remembers to pass `--base https://test.boredompeaks.me`. There is no `--dry-run`, no confirmation, and no `assert "test" in base`.
5. **Are the tests exercising failure (exit 1) or only the happy path?** Neither, for the gate's contract: **no test calls `main()`, `run()` or `added_lines()` at all.** The 190-case suite covers only the pure core. Deleting the entire shell (1,314-1,625, ~310 lines) or flipping the exit code to a constant leaves it green (`Q04-04`). Failure *outcomes* inside the pure core are tested thoroughly and well — `test_missing_test_name_is_an_error`, `test_line_past_end_of_file_is_an_error`, the map's "target died" branches, the directive refusal matrix — so this is a coverage *boundary* defect, not a happy-path-only suite.
6. **Shelling out with unquoted user input / writing into the repo?** No injection: all three `subprocess.run` calls (`doc_claims.py:1365, 1453, 1502`) pass argv **lists** with no `shell=True`, and `redteam_t1a.py` has no `subprocess` at all (`grep shell=True|os.system|eval(|exec(|pickle|yaml.load` → zero hits). Repo writes: `write_baseline` → `scripts/doc_claims_baseline.json` (`:1466`) and the red-team `--out` default (`redteam_t1a.py:1581, 1628`). The first is the documented, manual-only mechanism; the second is an unignored file carrying live session ids (folded into `Q04-01`).

## Findings (severity order)

### Q04-01 | P2 / HIGH | INFRA | `scripts/redteam_t1a.py:37` (and `:44`, `:1580-1581`)
**The red-team runner fires destructive live requests at a non-test host by default, and its own stated safety rail ("nothing targets a non-test environment: the base URL is explicit per run") is contradicted by the code: the base is not explicit, it has a default to the production-looking API host.**

`DEFAULT_BASE = "https://api.boredompeaks.me"` (`:37`) and `ap.add_argument("--base", default=DEFAULT_BASE)` (`:1580`). `main()` (`:1578-1661`) has **no** guard: no `--i-understand`, no `assert "test" in args.base`, no host allowlist, no `--dry-run`. `python scripts/redteam_t1a.py` with no arguments therefore, in order: registers a fresh account (`:252-262`, `POST /api/v1/account/register/`), attempts two logins (`:263-276`), sends six forged Razorpay webhook deliveries plus two concurrent ones (`:335-417`), a refund POST for order 1 (`:493-495`), an inventory adjustment `delta=-99` and a product create with `stock=-5` (`:571-616`), nine checkout payloads and a 10-wide parallel checkout burst (`:917-949`, `:1094-1095`), cross-session cart `DELETE`s and a `PATCH` (`:1146-1160`), then 12+ coupon shots and up to 55 username probes (`:783-871`). Every one of those is *expected* to be refused, and the rows record the refusal — but the script cannot tell "refused" from "accepted and mutated" before it is already on the wire, and against the wrong host it will have already mutated whatever it could reach. The test host exists and is hardcoded elsewhere in the same file (`TRUSTED_ORIGIN = "https://test.boredompeaks.me"`, `:44`), so the default is not merely stale — it is inconsistent with the file's own notion of "test".

Same "safe to run" question, second half: the default `--out scripts/t1a_evidence.json` (`:1581`, `:1628`) writes into the repo, and that path is **not** in `.gitignore` — the "Ad-hoc probe / red-team / load-test scratch (never committed)" block lists `red_team_probe.py`, `redteam_probe*.log`, `collapse_hammer*`, `probe.py` but not `t1a_evidence.json`. The docstring asserts it is "untracked" (`:19`); nothing enforces that. The file contains captured session-id prefixes (`:1268`), cart ids, usernames and response bodies, so one `git add -A` commits live session material. It also dirties `git status`, which the orchestration protocol treats as a stop condition.

Fix route: NEXT-BUILD — default `--base` to the test host (or make it required), add a host assertion plus `--i-understand`, and add `scripts/t1a_evidence.json` to `.gitignore` (or move the default under an ignored directory).

### Q04-02 | P2 / MEDIUM | INFRA | `scripts/doc_claims.py:1473` (index built at `:1410-1440`)
**The existence index is a walk of the WORKING TREE, while the claims it verifies are read from `--head`: uncommitted files can satisfy a quoted test name or path, and line counts come from a tree the commit may not contain.**

`run()` calls `build_index()` (`:1473`) which `rglob`s five source roots under `REPO_ROOT` (`:1415-1425`) and reads them from disk (`:1430-1435`). Nothing in it takes `head`; `--head` is honoured only by `git diff`, `git show` and `ls-tree` (`:1481, 1483, 1489`). So the gate mixes two trees: prose from `<head>:<path>`, existence facts from the checkout. Consequences, all reachable in this repo's own operating model:

- a doc row quoting `test_foo` is verifiable by `def test_foo` sitting in an **untracked scratch file** (the worktree at `1ffe926` carries 4 untracked files) or in a locally-modified test module that has not been committed. The concrete instance is already blessed by `.gitignore`: `backend/tmp_*.py` is the repo's own scratch-file convention, is ignored so it can never be in a commit, and is under `backend/` and not in `SKIP_DIRS` (`:151-165`), so its `def test_*` names are admitted by the index;
- a `file.py:123` cite is checked against the **working-tree line count**, so a locally longer file greens a cite that is past EOF at the commit under test — the exact class the check exists for;
- `--head <sha>` (a documented flag, `:1554`) silently produces a report whose path/test facts describe a different tree than the one it names.

The inverse (a test exists at `head`, not in the working tree) is not reachable in CI because checkout == head, which is why this survives: the CI path is correct and the local/`--head` paths are not.

Fix route: NEXT-BUILD — index from the tree, not the disk (`git ls-tree -r` + `git show`, or a `--worktree-index` flag that is explicit and off by default).

### Q04-03 | P2 / MEDIUM | INFRA | `scripts/doc_claims.py:1499` (and `:1443-1446`, `:1462-1465`)
**The byte-integrity half iterates the baseline JSON's own keys, never `BYTE_INTEGRITY_DOCS`: deleting or hollowing one entry in that file silently disables the check for that document, with no error, no warning, and no log line — and the unit suite still passes.**

`run()`: `for rel, recorded in baseline.items()` (`:1499-1501`). `BYTE_INTEGRITY_DOCS = ("backend/docs/changes.md",)` (`:142`) is used **only** by `write_baseline` (`:1452`); nothing ever compares the two sets. `load_baseline()` returns `{}` for a missing file (`:1443-1446`) — no error. `check_byte_integrity` only compares keys that are *present* (`:1279-1303`), so a baseline entry reduced to `{"cr": 0}` makes the check a near-no-op. Probed: `check_byte_integrity(b'x\ny\n', {'cr': 0})['ok'] is True`. The only shape guard is `BaselineShapeTests.test_baseline_records_byte_facts_and_nothing_else` (`test_doc_claims.py:1385-1394`), which asserts non-empty + key-subset + int/bool — `{"backend/docs/changes.md": {"cr": 0}}` satisfies all three, and `BYTE_INTEGRITY_DOCS` is not even imported by the suite (import list `:20-40`). So the file that records the evidence is also the file that decides what evidence exists, and it is edited by the same agents the gate is watching.

Fix route: NEXT-BUILD — fail (exit 2) when `set(BYTE_INTEGRITY_DOCS) - set(baseline)`, require all five facts per entry, and pin that requirement in `BaselineShapeTests`.

### Q04-04 | P2 / MEDIUM | INFRA | `scripts/tests/test_doc_claims.py:1900` (suite boundary vs `doc_claims.py:1314-1625`)

### Q04-05 | P2 / MEDIUM | INFRA | `scripts/redteam_t1a.py:44` (used at `:437, :703, :916, :1144`)
**`TRUSTED_ORIGIN` is hardcoded to the test deployment while `--base` is free, so every sessioned row sends the test origin's `Origin`/`Referer` and CSRF token to whatever host `--base` names — and the resulting refusal is recorded as a PASS of a backend invariant.**

`browser_csrf(H.jar, origin=TRUSTED_ORIGIN)` (`:220-235`) always stamps `Origin: https://test.boredompeaks.me` + `Referer: …/` (`:229-230`), and the four call sites that build "browser-shaped" requests all use it (`:437, :703, :916, :1144`). On the shipped default base (`api.boredompeaks.me`, `:37`) those requests are cross-origin, so Django's CSRF origin check refuses them before the view runs. Rows that then record PASS against an *application* invariant include `F4-G2` ("Session presence changes nothing: the deadend refusal is user-independent…", `:972-984`), `F3-C2/C3` (`:725-779`) and `F1-V1`'s sessioned leg (`:432-445`). Each would have passed identically if the view had no guard at all. The file knows the hazard — `:38-44` says the origin "must be listed in the box's CSRF_TRUSTED_ORIGINS for checkout to work at all… otherwise Django's referer check refuses them before the application layer and the row would measure the wrong thing" — but the invariant it states is only enforced for the one host that happens to be hardcoded.

Fix route: NEXT-BUILD — derive the origin from `args.base` (and take the expected refusal text from the same place), or assert `TRUSTED_ORIGIN`'s host is a suffix/registrable-domain match of `--base` before any sessioned phase runs.

### Q04-06 | P3 / LOW | INFRA | `scripts/doc_claims.py:1269` (compare at `:1279-1303`, dropped at `:1462-1465`)
**The "byte count that moved" is measured and then never compared to anything, and `control_detail` (line/column/byte of every control byte) is computed, returned, and dropped by the baseline writer — so a byte eaten mid-line, which is the documented corruption this check was built for, passes.**

`measured` records `bytes`, `lines`, `control_bytes`, `control_detail`, `cr`, `crlf_pairs`, `trailing_lf` (`:1268-1276`). The comparison block tests only `control_bytes` (count), `cr`, `crlf_pairs`, `lines` (shrink only) and `trailing_lf` (`:1279-1303`); `bytes` is never read. `write_baseline` persists five keys and omits both `bytes` and `control_detail` (`:1462-1465`). So the module docstring's "a byte count that changed because a PowerShell write mangled the file" (`:6-7`) and `backend-tests.yml:431`'s "a byte-integrity regression on a tracked doc blob" describe a control that catches CRLF conversion, control-byte insertion, a lost trailing LF and a shorter file — but **not** `c873b27`'s "ate the leading byte" (`doc_claims.py:41`), which leaves every one of those five facts unchanged. Probed: `check_byte_integrity(b'abc\n', {'bytes': 999})['ok'] is True`. The count-of-control-bytes rule has a second blind spot by construction: a corruption that moves one control byte from line 675 to line 900 keeps the count identical.

Fix route: FOLD-INTO-NEXT — record `bytes` and compare it against a monotonic rule (`>= recorded`, like `lines`), and compare `control_detail` as a multiset so a moved byte is a change.

### Q04-07 | P3 / LOW | INFRA | `scripts/doc_claims.py:1399` (effect at `:1518`, `:1352`)
**`added_lines` creates a key for every `+++` header even when the file has zero added lines, so `files_scanned` is non-empty and `empty_scan_notice` — the one guard whose job is "green must never mean empty" — stays silent while zero lines of prose were actually read.**

`added_lines` does `files.setdefault(current, set())` unconditionally on each `+++ ` line (`:1391-1399`) and only fills line numbers from `@@` hunks (`:1400-1406`). A pure-deletion hunk has header `@@ -10,3 +9,0 @@`, so `int(match.group(2) or 1)` is `0` and `range(9, 9)` is empty: the file keeps an empty set. `run()` then reports `files_scanned=sorted(files)` (`:1518`) including that file, and `empty_scan_notice` returns `""` for any non-empty iterable (`:1352`) — probed: `empty_scan_notice(['a.md'], 'b', 'HEAD') == ''`. A diff that only *removes* documentation therefore prints `0 claims in 1 file(s)` with no notice, from the same code path the docstring at `:96-110` says exists so "green can never again mean empty". It is not a full false-green (stdout still says 0 claims), but the guard's own contract is broken and its message — the actionable part, naming `$DOC_CLAIMS_BASE` — never prints.

Fix route: FOLD-INTO-NEXT — compute `files_scanned` from files with at least one added line (or pass `report.claims`-bearing files) to `empty_scan_notice`.

### Q04-08 | P3 / LOW | INFRA | `scripts/doc_claims.py:1438-1439` (probe-confirmed)
**For every `.ts/.tsx/.js/.jsx/.mjs` file in the tree, `RE_TEST_NAME.findall` registers EVERY occurrence of a `test_…` token as an existing test name — so a quoted frontend test is "verified" by its name appearing anywhere, including a comment, an unrelated string, or a `.skip`ped spec.**

`build_index`: Python files must supply a real `def` (`RE_DEF_TEST`, `:1436-1437`), but JS/TS files are searched with the bare name regex (`:1438-1439`). Probed: `RE_TEST_NAME.findall('// test_checkout_flow was removed in c1')` → `['test_checkout_flow']`. Because the walk covers `frontend/src` as well as `frontend/tests` (`:1415-1421`), the *claim's own subject* can be satisfied by a stale comment or by a string in application code, and a `test.skip('test_checkout_flow', …)` still resolves the name. The Python half of the same gate is strict (`def` only), so the asymmetry means the frontend claims this repo writes about are the weakest ones verified.

Fix route: FOLD-INTO-NEXT — require a call-shaped occurrence (`test(`/`it(`/`describe(` with the name as the first argument) for JS/TS, and exclude comments.

## Secondary observations (real, not in the 10-row table)

1. **Corrupt baseline misreports itself as claim errors.** `load_baseline()` calls `json.loads` uncaught (`doc_claims.py:1443-1446`); `main()` catches only `(RuntimeError, OSError)` around `run()` (`:1574-1578`), so a malformed `doc_claims_baseline.json` raises `JSONDecodeError` → traceback → **exit 1**, which the module docstring defines as "errors present" (`:122`). An environment failure is reported under the claims-error exit code.
2. **An unreadable source file fails closed but names the wrong cause.** `build_index`'s `except OSError: continue` (`:1433-1434`) drops the file from the index, so a doc citing it reports "no `def` for this name anywhere in the tree" / "no such file in the tree" rather than "could not read". Fails red, misattributes. (The prompt's "unreadable file treated as clean" does not hold — worth stating because it is the safer direction.)
3. **`dump()` merges previous-run rows under one timestamp.** `redteam_t1a.py:1598-1611` re-reads the existing evidence file when `meta.base` matches, keeps rows for families not in `--only`, and rewrites a single `meta.finished` (`:1616`) over the union. Rows therefore carry no per-row time or run id, so a two-run stitch is indistinguishable from a single 12-minute run when the JSON is quoted. A corrupt old file is `except (OSError, ValueError): old = None` (`:1603-1604`) — silently discarded and then overwritten (`:1628`).
4. **Name resolution can flip a stale cite from red to green without the prose changing.** `_resolve_path` returns a match when the suffix/basename pass finds **exactly one** candidate (`doc_claims.py:1006-1013`, `_same_basename` `:1021-1023`). Delete one of four `views.py` files and a bare `views.py` cite that was correctly an error (`PathResolutionTests.test_bare_filename_ambiguous_is_refused`, `test_doc_claims.py:232-240`) starts resolving — to a file the author never meant. The design is documented (`:998-1004`), the flip is not.
5. **Byte-integrity findings have no line.** The pseudo-`Claim` uses `line=0` (`doc_claims.py:1529-1536`), printed as `ERROR backend/docs/changes.md:0 [byte_integrity] …` (`:1594-1597`). The file is right; the "line" is a placeholder that reads as a location.

## Checked and holding (no finding)

- **No command injection / no shell.** `_git` and both `git show` calls pass argv lists, no `shell=True`, no `os.system`, no `eval`/`exec`/`pickle`/`yaml.load` in any of the three files (`grep` → 3 hits, all `subprocess.run(`).
- **The pure-core regexes are not vacuous and are mutation-proofed by the suite.** Every "matches nothing" risk I looked for has a positive and a negative test: `test_bare_number_is_not_a_claim` (`:139`), `test_bare_all_is_not_treated_as_a_universal` (`:152`), `test_does_not_match_a_test_name_inside_a_longer_identifier` (`:91`), the `.py.bak`/`.pyx`/`.pyc` tail tests (`:743-791`), the dotted-id exemptions (`:631-715`), and the directive refusal matrix (`:986-1168`). Deleting most of these guards does break a test.
- **Base resolution precedence is correct and tested both ways** (`doc_claims.py:1314-1342`; `BaseResolutionTests` `test_doc_claims.py:1326-1377`), including "a blank env var is ignored, not used".
- **Workflow wiring is correct on the points that matter.** `fetch-depth: 0` in both jobs means the resolved base SHA is actually present (the `exit 2 → red on a green tree` failure is closed, `backend-tests.yml:186-202`); `backend/*` in the change-detector means a docs-only PR still runs the claim scan (`:236`) — the gate is not skipped on the PR that adds prose; the branch-creation all-zeros `before` is handled explicitly (`:473-476`); the nightly treats the scanner's exit code as the gate and cross-checks "errors>0 but exit 0" (`doc-claims-nightly.yml:107-111`).
- **The restructure map fails closed.** Unknown keys, missing `cites_in`, scope outside the scanned docs, a short reason, a dead target, and `tracked is None` for an untracked entry all produce an error rather than a pass (`doc_claims.py:1056-1242`), and every pass prints `RESTRUCTURED` with its reason (`:1614-1618`). The `external: true` shape is an unwitnessed pass, but it is scoped by `cites_in`, printed, and its reason clears the same floor (`:1214-1218`).
- **The counter-example directive cannot be produced by rewriting a sentence.** "there is not a test named `test_x`" still errors (`test_doc_claims.py:900-905`); the quota refuses *all* directives when two share a line (`:420-426`); a reason must name a ledger-shaped token (`:300-303`).
- **`scripts/tests/__init__.py` is a genuine discovery fix**, not an empty marker: its docstring records the `NO TESTS RAN / exit 0` defect, and `backend-tests.yml:546-565` closes it by requiring the runner's collected count to be non-zero AND equal to the sources' own `def test_` count, instead of pinning a number that moves.
