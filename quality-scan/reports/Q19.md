### Q19-01 — P3 LOW — the uniform-miss matrix is anchored to a baseline minted by the endpoint under test, so 12 of its 13 probes go vacuous under a total auth bypass
`backend/shipping/tests_tracking.py:434–440,442–448,546–549`.


Every one of the 13 shapes (`:510–544`) is compared to a baseline the same view produced. Delete the owner
filter at `views.py:168–174` (i.e. return every shipment matching the order number) and the baseline becomes
`200` **with the parcel body**, after which all 13 shapes — wrong token, over-wide token, cross-order token,
empty/whitespace token, unknown order, stranger, session cookie — return that same leaked 200 and
`_assert_uniform` passes for each. The file's central property ("ONE byte-identical answer") then rests on a
single assertion, `:443`:

```python

```

That line does fail in the scenario above, which is why this is P3 rather than P2 — the authz property is
*caught* (`:443`, `:588`, `:599`, `:612`, `:628`), only the **uniformity** property is not independently
anchored. The fix is one line: compare each miss shape against a *literal* expected body
(`_tracking_lookup_miss().content`, already imported at `:79`) instead of against `self.baseline`. Note the
matrix is otherwise well built: `:549`'s `assertEqual(len(shapes), 13)` is a literal count on a dict built
six lines above (a self-referential pin, P4), while `:498–544`'s deliberate ordering of anonymous-before-
authenticated probes is a genuinely non-obvious correctness precaution.
Confidence **H** (source-read of the view + these tests).

### Q19-03 — P3 LOW — "no code path can rewrite, delete or forge a recorded step" is contradicted by the class's own fixtures
`:1178–1185` (class claim), `:1234–1246` (bulk_create refused), `:1189–1193` and `:1074–1078` (single-row create).

happened — the exact defect `StatusCannotBeMovedInBulkTests` (`:1333`) exists to prevent from the other

`models.py:499–501` ("no code path can rewrite, delete or forge a recorded step") should be narrowed to
"rewrite, retarget or delete", or the append path needs its own writer-only seam plus a test.
Confidence **H** (mechanism); severity kept P3 because this is a doc/claim and test-coverage defect, with the
production-side question handed to Q08.

### Q19-04 — P3 LOW — the width gate is never driven by the Postgres overflow, and the one test in the class pins a bypass of the invariant the class declares
`:1427–1436` (claim), `:1554–1566` (the bypass), `models.py:32–51`.

The class declares: "No column is ever written a value wider than the column declares" (`:1428`), "SQLite
ignores a `varchar(n)` width and Postgres enforces it" (`:1430`). No test in the range runs against Postgres
and no test mocks one, so what is measured is only the app-level `ValueError` from `_reject_oversized`
(`models.py:32–51`) — the Postgres `DataError` premise is source-read reasoning, stated as such, and that is
acceptable. What is not acceptable is the class containing its own counter-example:

```python
def test_a_computed_value_is_left_to_the_database_not_measured(self):   # 1554
    Shipment.objects.filter(pk=self.shipment.pk).update(
        carrier=models.F("tracking_number")                             # 1562
    )
    self.shipment.refresh_from_db()
    self.assertEqual(self.shipment.carrier, "TRK-401")                 # 1566
```

This passes only because the *source* value is 7 characters. The identical call with
`models.F("internal_note")` — a `TextField` reachable by any staff writer at `:1549`, where the suite itself
stores 5,000 characters — writes 5,000 chars into `carrier varchar(60)`: a clean pass here and a `DataError`
500 on production, i.e. exactly the failure the class exists to prevent, pinned as accepted behaviour with no
marker distinguishing "expressions are out of scope" from "this is safe". Fix: assert the boundary explicitly
(`update(carrier=F("internal_note"))` should be refused, or the docstring at `:1428` must say expressions are
excluded and a `Substr`/`Cast` guard owned elsewhere).
Confidence: mechanism **H**; production reachability **M** (needs an expression write, not a form POST).

### Q19-08 — P3 LOW — the two-sibling delivery race the module is built around has no concurrency test, and cannot have one on this suite's engine
`lifecycle.py:84–100,134,144`; `admin.py:184–192`; `:1677–1703` (the sequential look-alike).

`_every_parcel_delivered` reads the sibling statuses and `sync_order_status` reads the order under
`select_for_update()` "so the second writer sees the first writer's parcel already at its new status". The
only test of that rule, `test_one_delivered_parcel_does_not_deliver_a_split_order` (`:1677`), drives the two
parcels **sequentially through one client**, which passes identically whether or not the lock exists. On
SQLite `FOR UPDATE` is inert — `admin.py:188–192` says so — so no test in this suite can distinguish
"serialised" from "lucky". The same is true of the `from_status` claim at `admin.py:184–187` ("two operators
editing the same parcel cannot both record the same `from_status`"). This is the one axis-5 category the file
has no example of at all (no `TransactionTestCase`, no threads, no `select_for_update` assertion).
Fix: at minimum assert the lock is requested (`mock.patch.object(Order.objects, "select_for_update")` wrapper
or `assertNumQueries` on the `FOR UPDATE` form on a Postgres run); the honest alternative is to state in the
docstring that the lock is unverified in-suite.
Confidence **H** for the absence; **M** for whether ordering can even be violated on Postgres in practice.

## Axis 5 — what the range proves and what it does not

**Would these fail if the guard were deleted? Yes, for:** the owner/token filter (`:443,471–476,588,599,612`);
all four append-only bulk paths plus both deletes (`:1196–1306`, message asserted, so a Django-internal
`ValueError` would not satisfy it — a good, non-tautological choice); the status bulk guard on both
`update()` and `bulk_update()` (`:1333,1341,1353,1404`); the width gate on all five gated columns
(`:1442–1489`); capability gating on read and write for four roles (`:950–999`); the provider scheme rule at

failure at `:777`); the JWT-only credential contract, including a forged and a dead-account token
(`:615–658`). The `force_authenticate`-free posture (`login_as`, `:186–202`) is the single best decision in
the file: it means the authz tests are about the shipped auth stack, not about the test client.

**Tautologies / declaration pins (P4, named, not otherwise reported):** `:263` and `:860` assert
`_meta.ordering` literals; `:248` asserts the choices set equals a literal set; `:285–286`, `:2252–2256`
assert `on_delete`/`null`/`related_name` declarations; `:943–944` assert two class attributes. All are
refactor tripwires rather than behaviour, which is defensible, but they are the reason the file's line count
understates how much behaviour is actually pinned.

**Invariants with no test at all (beyond I9–I12 above):**
1. **No query-count guard**, despite the view documenting its eager loading (`views.py:181–189`):
   `assertNumQueries` appears 0 times in the range. Drop `prefetch_related("events")` and a 3-parcel order
   silently becomes 4 queries with the whole suite green.
2. **The `ShipmentEvent` change form is never POSTed.** `admin.py:244–283` claims "a view, not an editor";
   `:929–938` pins `has_add_permission` / `has_delete_permission` and `:936–938` the add page 403, but nothing
   posts to `shipmentevent/<pk>/change/`, which is the surface a forger would actually try.
3. **Case-mangled schemes** (`JaVaScRiPt:`) are unprobed — they are safe (`urlsplit` lowercases the scheme)
   but only because of a Python library detail, not because a test says so.
4. **A hostile `tracking_number` in the rendered link** is unprobed: `Shipment.tracking_url`
   (`models.py:449–464`) substitutes the reference into a URL that the storefront places in `href`, and a
   reference containing `?`, `#`, `/` or whitespace is accepted by both the model (`:357–360`, no validator)
   and `urlsplit`; no test renders a reference that re-points the link.
5. **`Payment_status` drift** on a shipment-driven order move: `sync_order_status` writes
   `["status", "fulfilment_status", "updated_at"]` (`lifecycle.py:157`), and no test asserts the two
   dimensions it deliberately omits are untouched *on a firing move* (see Q19-07).
