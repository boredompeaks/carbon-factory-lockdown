## Direct answers to the brief's questions

The module docstring's safety rail — "nothing targets a non-test environment: base URL is explicit per run" (`:29`) — is **false**, and it is the same false sentence Q04-01 proved false in t1a. **SHARED.**
2. **Dry-run / env guard?** None of either kind. The only pre-flight is `try: open(out_path)` (`:1872-1878`), which reads a JSON file.
3. **Evidence into the repo, with session ids/tokens?** Yes, and worse than t1a: the default out path is `pathlib.Path(__file__).with_name("t1b_evidence.json")` (`:1862`) — i.e. **`scripts/t1b_evidence.json` inside the repo** — and `.gitignore` has **no matching rule** (`grep -i "evidence|t1b|scripts"` on `.gitignore` → no matches; the "never committed" scratch block lists `red_team_probe.py`, `redteam_probe*.log`, `collapse_hammer*`, `probe.py`, none of which match). The docstring calls the file "(untracked)" (`:31`) and the changelog row repeats "(untracked)" — nothing enforces it. And unlike t1a, this file carries **the fixture password in plaintext** (`SHARED["fixture_pass"] = FIXTURE_PASS` at `:257`, `:338`, dumped as `meta.env_state` at `:1898`). See Q24-02.
4. **Can PASS hit a wrong outcome?** Yes — five distinct mechanisms, Q24-03 (empty-`all()` on a shot-1 429), Q24-04 (paired transport failure satisfies `same()`), Q24-06 (hardcoded second base + hardcoded trusted origin make sessioned/origin rows measure the CSRF layer), Q24-07 (evidence computed but not gating), Q24-08 (any 403 from any layer accepted as the capability gate). 5. **Does it delete or mutate rows on the target?** **No DELETE/PATCH/PUT anywhere** (`grep "DELETE|PATCH|\bPUT\b"` → zero code hits) — so the t1a `checkout-DELETE` case has no t1b analogue, and that is a genuine improvement. 6. **Is the evidence file usable as proof?** Partly. It has `meta.base`, `meta.task`, `meta.finished` (ISO-8601 UTC) and `counts`, and per-row `id/family/attempted/invariant/request/response/result/severity` (shape from `Ledger.add`, t1a `:154-167`). It has **no run id, no git SHA/tree, no `started` time, no duration, no `--only` phase list, no per-row timestamp**, and expected/actual exist only as free prose inside `invariant`/`response` strings. A crashed phase is silently partial (Q24-05). So it is a good *narrative* artifact and a weak *proof* artifact.

### Q24-04 | P2 / MEDIUM | INFRA | `scripts/redteam_t1b.py:712` + `:1280` (helper `redteam_t1a.py:141-142`, error shape `redteam_t1a.py:119`)
**NEW blast radius on a SHARED helper.** `same()` compares `status` and `body`, and `Http.request` turns any exception into `{"status": None, "body": "TRANSPORT-ERROR <repr>"}` — so **two consecutive network failures are "byte-identical"** and satisfy every oracle-uniformity row that does not independently pin the status.

t1a `:118-119`: `except Exception as e: return {"status": None, "body": f"TRANSPORT-ERROR {e!r}", "headers": {}}`. t1a `:141-142`: `same(a, b)` → `a["status"] == b["status"] and a["body"] == b["body"]`. Two identical failures (same exception type and args — e.g. `ConnectionRefusedError(10061, ...)` to the same host) yield `None == None` and equal reprs, so `same()` is `True`.

- `F6-P1` (`:712`) `uniform_absent = same(absent_bodies[0], absent_bodies[1])` → `verdict(uniform_absent)` (`:725`) with **no status guard at all**. A run against an unreachable host records PASS for "the recovery endpoint answers one uniform message (no status/body diff, no usable timing diff)", and prints `elapsed_ms <x>/<y>` as if timing had been measured.
- `F8-E3` (`:1280`) `user_uniform = l_first is not None and same(l_first, g_first)` → `verdict(user_uniform)` (`:1295`). Same failure mode, and this row is the *user-existence-oracle* claim.

Rows that survive: `F6-M2`/`F6-M3` require `status == 401` explicitly (`:497`, `:518`); `F8-E2` requires two collected 401s (`:1236-1238`); `F8-E4` requires 404 (`:1318`). So the defect is not uniform across the file — which makes it a per-row guard omission rather than an intentional design, and the two unguarded rows are the two strongest oracle claims.

Fix route: NEXT-BUILD — `same()` must refuse when either side is `status is None` (raise/return False), and every uniformity row must additionally assert the expected status. Fixture: `assert not same(errA, errB)` for two transport-error dicts.

### Q24-05 | P2 / MEDIUM | INFRA | `scripts/redteam_t1b.py:1893-1908` (merge at `:1880-1892`, crash path `:1928-1931`)
**NEW** (same shape as Q04 secondary-3, now with a crash path). The evidence document has no run identity and no abort marker, so a partial or stitched run is indistinguishable from a complete one — and the file is the only artifact the report is written from.

`meta` contains exactly `base`, `task`, `finished`, `env_state` (`:1893-1899`). Missing: run id, `started`, git SHA/tree, the `--only` list actually executed, host resolution, and any per-row `measured_at`. `finished` is **rewritten after every phase** (`dump()` is called inside the phase loop, `:1920-1922`), so it is the time of the last write, not of the run.

Three concrete consequences:
1. **Stitch.** When `--only` names a subset, `rows` is recomputed as *old rows for families not re-run* + *new rows* (`:1888-1892`) under one `finished`. A `--only f8` run therefore ships F6/F7/F9 rows from an earlier session, with no marker distinguishing them, and `counts` (`:1900-1905`) aggregates the union. Anyone quoting the JSON cannot tell which rows were measured against which commit.
2. **Crash looks like completion.** `except Exception: dump(); print(...); return 1` (`:1928-1931`) writes no `aborted`/`error` field, and the phase's already-appended rows survive while the rest of the family silently does not exist. Exit code 1 is the only signal and it is not in the file. Because `refreshed_fams` is computed from the *requested* phases (`:1867-1868`), a phase that dies before appending drops the previous run's rows for that family too — so the family's case count shrinks with nothing recording that cases were lost.
3. **No expected/actual.** The `Ledger.add` row shape (t1a `:154-167`) has `invariant` and `response` as prose; the machine-checkable `ok` boolean that produced the verdict is discarded. Re-deriving a verdict from the file requires re-implementing the row's logic — which is why Q24-03/04/07/08 could sit undetected in a file that "has evidence for every row".

Fix route: NEXT-BUILD — add `run_id` (uuid4 at start), `started`, `git rev-parse HEAD` (or an explicit `tree` arg), `phases_requested`, `phases_completed`, `aborted: {phase, error}`; stamp each row with `run_id` + `measured_at`; store `expected`/`actual`/`ok` structurally.
