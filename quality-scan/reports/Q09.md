## Answers to the six focus questions

**1. Can stock go negative?** No reachable path found, through any of the four asked routes:
`adjust_stock` locks and re-checks `new_stock < 0` before writing (models.py:185-198); admin bulk and
REST both call it (admin.py:322, views.py:368); the changelist cell is routed through it too
(admin.py:267). `commit_order_sale` sums demand per product and re-checks under ascending-pk
`select_for_update` before the first mutation (inventory.py:171-181, 267-278) — a per-line check
would have driven it negative, the summed one cannot. Reservation expiry writes `delta=0` only
(expire_reservations.py:100-109). Delist never touches `stock` (admin.py:420). `PositiveBigIntegerField`
is the second, engine-level gate. Caveat: `select_for_update` is a silent no-op on SQLite, so the
*concurrency* half of this is only provable on the PG lane (`tests/test_postgres_row_locking.py`).

**2. Slug generation.** IntegrityError retry, not check-then-act (models.py:151-178; F-25/V-15 fixed).
Per-attempt `transaction.atomic()` savepoint, retry only when the message names `slug`, unbounded
candidate walk with the *base* truncated so suffixes stay distinct (models.py:130-149). Correct.

**3. Delisted visibility.** Listing (`views.py:46`), detail GET (`views.py:216-219`), cart add
(`cart/views.py:97-100`), checkout (`checkout.py:482-518`) all refuse, and the detail/restock refusals
are the *same* miss as an unknown slug (`_uniform_not_found`, restock_views.py:81-95). Staff see every
row via the changelist + `is_active` filter + `on_sale_flag` (admin.py:165, 294-300). Two edges:
(a) a line already in the cart can still be re-quantified via `cart/views.py:194` (no `is_active`
check — harmless, checkout refuses, cart-owned); (b) **capture** has no delist gate, so an order
created before the delist still completes at payment (`orders/inventory.py:135` — handed off below).
Delist is *not* a global "stop the sale" switch; it is a stop-the-*new*-sale switch. That is a
defensible choice but it is not stated anywhere in the flow's own docs.

**4. Permission granularity.** Yes, per capability, no inline `is_staff` in this app:
`HasProductsWriteOrReadOnly` (views.py:29,189), `HasInventoryAdjust` (views.py:311), a purpose-built
`IsAuthenticatedOrSubmittedEmail` for restock (restock_views.py:98-132), and admin `capability_map` /
`action_capabilities` with delist/relist on `products.publish` (admin.py:84-106). The one exception is
`ProductVariantAdmin` (admin.py:465-470): bare `ModelAdmin`, so variant `price`/`stock` edits need no
capability and write no ledger — explicitly deferred to SPEC-6-08 and a test *pins the absence*
(test_variant.py:228-233).

**5. `ProductSerializer` future columns.** No. Explicit whitelist (serializers.py:14-25), plus a
drift-guard test that requires every new concrete column to be classified
(tests.py:1563-1575). `is_active`/`free_shipping` deliberately excluded. F-24/V-19 closed.

**6. Reservations released exactly once / expired deterministically?** Released: every writer filters
`status=ACTIVE`, so the transition is one-shot (inventory.py:263-265, orders/admin.py:558-560,
830-832, webhooks.py:421-423). Expired: the sweep selects `active AND expires_at <= now` then re-checks
both predicates *in the UPDATE* (expire_reservations.py:79-83), so a hold re-armed or converted between
SELECT and UPDATE is skipped, and product locks are ascending-pk like verify_payment. That is correct.
The **ledger row** it writes is not: see Q09-05. Determinism caveat: a sweep run whose SELECT sees a
row that a concurrent writer releases makes the note overstate the released units (same finding).

### Q09-01 — Guest restock opt-in: unverified address, no unsubscribe, no owner check
**P2 MEDIUM · CODE · Confidence H · NEXT-BUILD**

- `restock_views.py:236-248` — an anonymous POST with any syntactically valid `email` arms a
  `RestockNotification` row (`user=None, email=<submitted>`). Nothing verifies the submitter owns the
  address (no confirmation mail exists anywhere in the flow), and nothing checks whether the address
  belongs to an account.
- `restock_views.py:264-266` — the only opt-out filter is `user=request.user`. A guest row has
  `user IS NULL`, so it is unreachable by *every* DELETE: the guest cannot opt out, and the account
  holder whose address was used cannot opt out either (their DELETE matches only their account row).
- The module docstring (`restock_views.py:16-20`, `258-263`) states this as deliberate because "a guest
  row has no caller identity to scope a DELETE by". The consequence is not stated: the row is
  permanently armed and re-mails once per zero→positive stock cycle (`models.py:231-244` re-arms on
  sell-out). Consent can be *granted* by a third party and never withdrawn.
- Consequence: unsolicited mail to an arbitrary address, repeating for the life of the product.
  Throttles bound submission volume (`restock-guest` 5/min per (IP,email), settings.py:1310) but not
  the recipient's exposure.
- Fix shape: a confirmation token (double opt-in) before a guest row becomes mailable, and/or
  unsubscribe-by-token link in the mail body that flips `active=False` on the guest row. Either closes
  both halves; the account path is unaffected.
- Tests: none. `test_guest_post_with_email_arms...` (test_restock.py:663) asserts the *desired* arming;
  no test asserts a guest can be disarmed, because it cannot.

### Q09-02 — `products.price` has no non-negative guard
**P2 MEDIUM · CODE · Confidence H · NEXT-BUILD**

- `models.py:61` — `price = models.DecimalField(max_digits=10, decimal_places=2)`, no
  `validators=[MinValueValidator(0)]`. `ProductSerializer` (serializers.py:14-25) adds nothing, and the
  admin form derives from the model field, so `PATCH /api/products/<slug>/ {"price": "-100.00"}` and a
  changelist inline price edit both accept it.
- Downstream it is summed without a sign check: `orders/views/checkout.py:495`
  (`subtotal_amount += product.price * cart_item.quantity`), `:767` (`total_amount =
  quantize_money(merchandise_total + shipping_amount)`), `orders/views/payment.py:114`
  (`amount = int(order.total_amount * Decimal("100"))`). `orders/tests.py:1752` shows a `0.00` total
  passing through, so no positivity gate exists on the order either.
- Effect: one negative-priced line discounts every other line. In a single-line cart the total goes
  negative and reaches the gateway amount (a 500-class failure at best, a captured underpay at worst
  depending on provider validation — provider behaviour not verified here, marked source-read).
  Requires `products.write`, so this is staff error/compromise rather than an anonymous attack.
- Fix shape: `MinValueValidator(Decimal("0.00"))` on the model field (one place, reaches DRF + admin),
  plus the same guard on `OrderItem.unit_price` if that snapshot is ever client-influenced.
- Tests: none anywhere for a negative price (grepped `products/`, `tests/`, `orders/`).

### Q09-03 — `slug` is writable through the API; null/blank silently regenerates the URL
**P3 LOW · CODE · Confidence H · FOLD-INTO-NEXT**

- `serializers.py:14-25` puts `slug` in an otherwise careful whitelist and does not mark it read-only —
  unlike `stock`, which is explicitly made read-only on update (`serializers.py:36-37`).
- Live probe (DRF 6.1-equivalent, synthetic model with the same field declaration):
  `SlugField read_only=False required=False allow_null=True allow_blank=True`,
  `{slug: ""}` → valid, `{slug: None}` → valid.
- `models.py:151-158` — on save, a falsy slug routes into `_slug_candidates()`, so
  `PATCH {"slug": null}` or `{"slug": ""}` **silently assigns a brand-new slug**: the 200 response
  shows the new value and the product's public detail URL, its restock URL and any external link change
  with it. Meanwhile `admin.py:168` declares `slug` readonly with the comment "the model generates it".
  One surface says model-owned, the other lets any `products.write` holder rewrite or clear it.
- Fix shape: `read_only_fields = ("slug",)` (or an explicit `extra_kwargs`); if merchant-chosen slugs
  are wanted later, that is a deliberate feature with its own validation, not a side effect.
- Tests: `test_serializer_field_set_is_pinned` (tests.py:696) pins the field *set*;
  `test_stock_writable_on_create_read_only_on_update` (tests.py:1577) pins `stock` only. Nothing pins
  `slug` writability, so deleting a future `read_only=True` would not go red.

### Q09-04 — Changelist stock cell: delta from a within-request read; failure is an uncaught `ValueError`
**P3 LOW · CODE · Confidence M · FOLD-INTO-NEXT**

- `admin.py:259-272` — `inline_columns` are written with `obj.save(update_fields=...)` **first**, then
  `loaded = form.initial.get("stock")` and `requested - loaded` is handed to `adjust_stock`.
  `form.initial` is built from the instance the changelist queryset loaded for *this* POST
  (DRF/Django formset construction), so `loaded` is fresh at request start but not under any lock.
- `adjust_stock` then re-reads under `select_for_update` and applies the **delta**
  (models.py:190-198). A sale landing between the changelist read and that lock makes the operator's
  typed absolute count not the stored count (typed 2 with a concurrent sale of 3 → `5 − 8 = −3`), and
  that case raises `ValueError` **out of `save_model` with no handler**: the changelist POST returns a
  500 while the price edit in the same row has already been committed (Django does not wrap the
  list-editable POST in `transaction.atomic`). The operator sees a crash and an unknown split state.
- The below-zero input case is safely handled by form validation before this
  (`tests/test_admin_inline_stock.py:143-151`); only the *race* reaches the exception.
- Fix shape: catch `ValueError` in `save_model` and `message_user(..., ERROR)` (as the bulk action
  already does at `admin.py:324-325`), and/or wrap the per-row write + adjustment in
  `transaction.atomic()` so the price cannot commit alone.

### Q09-05 — Sweep ledger row describes the pre-SELECT batch, not the rows it flipped
**P3 LOW · CODE · Confidence H · FOLD-INTO-NEXT**

- `expire_reservations.py:61-66` selects `id, product_id, order_id, quantity` **outside** any
  transaction/lock. `:79-83` flips conditionally (`status=ACTIVE AND expires_at<=now`), so
  `flipped` can be smaller than `len(rows)` when a concurrent `verify_payment` converts a hold or a
  retried checkout re-arms one.
- `:86` calls `self._record_release(product, rows)` — the **whole** batch — and `:98-99` builds
  `refs`/`units` from it. So the ledger row claims units "back to available-to-sell" that a concurrent
  writer had already accounted for. `delta=0`, so on-hand is unaffected; the audit trail is wrong.
- Same block, `:78`: `products.objects.select_for_update().get(pk=product_id)` is unguarded — a product
  row deleted between SELECT and lock raises `DoesNotExist`, aborting the sweep for every remaining
  product in the batch (the reservations would have cascaded, so this is a narrow window, but the
  failure mode is "no sweep ran" rather than "skip this product").
- Fix shape: collect the pks the UPDATE reported. `update()` returns a count, not pks; re-select the
  flipped rows by `pk__in` + `status=EXPIRED` before building the note, or flip per row and keep the
  returned rows. Guard the `get()` with `.first()` + `continue`.

### Q09-06 — Restock "in stock" refusal ignores reservations
**P3 LOW · CODE · Confidence H · FOLD-INTO-NEXT**

- `restock_views.py:198-202` refuses the opt-in when `product.stock > 0`. `StockReservation` in the
  same app defines available-to-sell as `stock − active reservations` (models.py:620-624), and checkout
  mints holds that make a product unsellable while `stock` is still positive. A fully reserved product
  therefore answers "Product is in stock; no restock notification needed." to a customer who cannot
  actually buy it. Bounded (the state is transient, ≤ RESERVATION_TTL, default 900s) and consistent
  with the checkout gate's own advisory use of `stock` (`checkout.py:486`), but the two surfaces
  disagree with §12.1's vocabulary.
- Fix shape: compare against `stock - Sum(active holds)`, or document that restock is keyed on on-hand
  by design.

### Q09-07 — Explicit `?ordering=` sorts still paginate unstably
**P3 LOW · CODE · Confidence H · FOLD-INTO-NEXT** (remainder of audit.md F-12 / V-20)

- `views.py:84-94` — `products_data.order_by(ordering)` for the six whitelisted values (`price`,
  `-price`, `name`, `-name`, `created_at`, `-created_at`). None appends a unique tiebreaker, so a
  catalogue with duplicate prices/names (the common case for `name` on variants, and for `price` on any
  sale page) partitions pages non-deterministically: a row can appear on page 1 and page 2, or on
  neither.
- `views.py:96-101` fixes exactly this for the *default* branch (`order_by("-created_at", "-id")`), so
  the defect survives only on the branch that was added by the fix's own commit. `test_f12_default_
  listing_order_is_deterministic` (tests.py:255) only exercises the default.
- Fix shape: `products_data.order_by(ordering, "-id")` for every accepted value.

### Q09-08 — Adjustment response can report another operator's movement
**P3 LOW · CODE · Confidence M · FOLD-INTO-NEXT**

- `views.py:374` — after `adjust_stock` returns, the view responds with
  `product.stock_movements.first()`. `StockMovement.Meta.ordering = ("-created_at",)` (models.py:492)
  with no pk tiebreaker and no filter on this request's row, so a concurrent adjustment for the same
  product between `adjust_stock` and this read makes the 201 report a `movement_id`/`delta`/
  `stock_after` that this request did not write. The client-visible contract ("your adjustment") is
  then false.
- Fix shape: have `adjust_stock` return the `StockMovement` it created and serialise that.

### Q09-10 — Guest uniqueness and the owner-XOR constraint are untested
**P3 LOW · TEST · Confidence H · FOLD-INTO-NEXT**
