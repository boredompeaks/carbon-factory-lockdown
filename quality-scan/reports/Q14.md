## The three questions this flow was sent to answer

1. **Does the worker test hold two workers on one row, or replay the race sequentially?** Both, and the real one is
   blind. The *sequential replay* is `test_a_row_another_worker_took_first_is_skipped_not_waited_on`
   (`:243-274`): it monkey-patches `QuerySet.select_for_update` to run the competing `UPDATE` **before** the lock is
   taken on the same connection — so it proves the stale-peek re-check works, not that two connections cannot both
   claim. The *genuine* two-worker test is `OutboxTwoWorkerTests` (`:847-1063`): `TransactionTestCase`, two
   `threading.Thread`s, a `threading.Barrier(2)`, `close_old_connections()` per worker. It is real concurrency. But its
   surviving observable (`row.attempts == 1`) **cannot see a double claim**, because `attempts` is written as an
   absolute value by each claimant (Q14-01); the one artifact that could see it — the `claimed` list — is captured and
   thrown away at `:941` / `:994`.
2. **Dedupe key semantics?** Not in this file, deliberately: `:17-18` states "The dedup key cannot help here and is not
   asked to" and `queue()` (`:141-156`) sidesteps it by giving every row its own `Order`. The semantics live in
   `tests/test_notification_outbox.py:274-403` (8 tests: collapse, key stability across data changes, separator
   non-collision, occurrence discriminator). **No gap in dedupe coverage.** The one interaction nobody pins is that the
   drain *never retires a key* — `_record_success` touches `status/sent_at/last_error` only — so a `SENT` row still
   absorbs a repeat `enqueue`; deleting the row on success would pass every test in both files except the row-exists
   assertion at `:193`.
3. **Lease-expiry recovery (QC-162)?** Half pinned, half not. Pinned: a worker that dies between send and stamp loses
   the row, and it is re-sent once `next_attempt_at` lapses (`:714-756`, `:758-768`). **Not** pinned: (a) the premise
   `NOTIFICATION_OUTBOX_LEASE_SECONDS > EMAIL_TIMEOUT` — the pair can be inverted with every test green, and
   (b) the un-owned settle write that QC-162 names (`_record_failure` is an unconditional
   `filter(pk).update(status=…)`), for which there is no stale-owner test at all — see Q14-03.
4. **Does the superadmin test cover the credential channel?** No. Only role assignment. The guard it exercises is a
   **diff** check (`_refuse_restricted_roles(request, held ^ desired)`, `accounts/admin.py:449`), so every refusal test
   supplies a *different* role set; an admin submitting the same top-tier role back with `email`/`is_active` changed is
   not tested, no test posts to `/admin/auth/user/<pk>/password/` (repo-wide grep → 0 hits), and no test deletes a
   top-tier account (the `User` admin inherits `has_delete_permission` → `capability_map["delete"] = staff.manage` and
   never consults the escalation guard). This is QC-042's channel, unpinned — see Q14-07.

## Axis 1 — invariants, and whether a test would fail if the guard were deleted

**Worker (`common/notifications.py`).**

1. **One in-flight claim per row** (lock + lease push, `:822-837`). *Enforced in code. Blindly tested.* The call-spy
   (`:780-804`) pins "the call was made"; the behavioural test cannot see a double claim (Q14-01), and on SQLite it can
   pass with zero claims (Q14-05). This is the weakest-covered invariant in the flow and the only one where a mutation
   (`delete select_for_update`) survives the test that names it.
2. **At-least-once across a crash** (`SystemExit` between send and stamp → re-send after the lease). *Enforced and
   pinned well*: `:714-727` (lost from the pass, still `PENDING`, one mail), `:729-756` (not claimable inside the lease,
   claimable and re-sent after, two mails, `attempts == 2`). This pair is the file's best work — it would fail a
   stamp-before-send implementation **and** a drop-the-row implementation.
3. **Bounded retries, `DEAD` terminal** (`attempts >= max`). *Enforced*; `:407-426` asserts the exact configured count,
   not "at most", and `:428-438` asserts a dead row is never re-claimed even with `next_attempt_at` in the past.
4. **Backoff env-driven, exponential, clamped** (`:339-374`). *Enforced and pinned with literals* — including the
   exponent clamp at `10**9`, which is the one guard in the module whose absence would look like a wedged worker.
5. **Expiry gate, two layers** (`claims 744-762` + `_claim:828`). *Half pinned* — see Q14-04.
6. **Purge × worker race → `VANISHED`, never a resurrected row.** *Enforced and pinned at four seams* (`:523-590`), and
   the assertion is on `NotificationOutbox.objects.count() == 0` (`:537`) — i.e. it would catch `save()`'s re-INSERT,
   which is the real hazard. Strong.
7. **One pass is bounded and an idle table costs one query.** *Pinned*: `assertNumQueries(1)` (`:221`) and the
   `batch_size` ceiling (`:1251-1262`).
8. **Status vocabulary is a single source.** *Pinned with literals both ways* (`:620-654`), including
   `DrainResult._fields` vs `DrainOutcome` — the exact coupling the module docstring says derivation gave away.
9. **The drain never retires a dedup key.** *Untested*, but the consequence is covered incidentally: a delete-on-success
   implementation fails `:193` (`row.status == SENT` on a refreshed instance).
10. **Alerting is log-only and never aborts the pass** (`:1434-1452`) and **an unconfigured alert budget never costs the
    dead-letter** (`:1418-1432`). *Pinned*, and correctly asserted on **mail** rather than on a log line (`:1321-1323`).

**Superadmin tier.**

11. **`platform.configure` is superadmin-only.** *Enforced and pinned* (`:219-223`), with a literal capability set
    (`TOP_TIER_CAPABILITIES`, `:76-78`) rather than a derived one — good.
12. **The grant cannot climb** (`user_may_assign_role`). *Pinned* (`:455-465`) with a literal `ROLE_GRANT_CAPABILITY`
    equality and a per-role behaviour loop. Mutation-proof.
13. **The guard is symmetric (mint *and* unmint) and on the diff.** *Pinned* (`:347-375`) — but only for non-empty
    diffs, which is precisely how the credential channel slips past (Q14-02).
14. **Deny-by-default** for unknown identifiers and role-less callers. *Pinned* (`:258-271`, `:470-472`).
15. **The Django superuser bypass is preserved, and is not a role.** *Pinned* (`:439-452`, `:474-478`), including
    `get_user_roles(superuser) == frozenset()`.
16. **A refused write leaves the row and the audit trail untouched.** *Pinned for orders*
    (`assert_row_unchanged`, `:965-975`) and *for roles* (`assert_no_superadmin_grant`, `:304-314`). Good pattern — the
    same pattern is missing for the User change form's non-role fields (Q14-02).

## Axis 2 — correctness of the assertions themselves

- **Asserted on the rendered/side-effect state, not the helper's return value**, in the places that matter: mail counts
  (`:196`, `:1011`), persisted status (`:192`, `:1060`), `expires_at` unchanged after a refused retry (`:1549-1553`),
  persisted address (`:1065-1069`). This is the file's strength and it is consistent.
- **No `res.data`-only assertions on money/auth surfaces** in the superadmin file; the two DRF paths assert
  `res.data["code"]` **and** the 403/404 (`:545-546`, `:585`), which is the right pair.
- **Isolation:** `OutboxDeadLetterAlertTests.setUp` clears `caches["alerts"]` (`:1326-1330`) with a stated reason; without
  it the first alert of the class is suppressed by a previous test's cooldown. `reset_sequences` on the
  `TransactionTestCase` (`:857`). No cross-test DB writes outside fixtures, no `sleep`, no network.
- **Time:** every time assertion compares against `timezone.now()` at call time (`:300`, `:315`, `:768`), never a frozen
  literal — no clock coupling.
- **A latent trap in the shared helper:** `queue()` (`:141-156`) documents itself as "bypassing the dedup key" but does
  the opposite — it calls the real `enqueue`, which returns **`None`** for a repeat key, after which
  `NotificationOutbox.objects.filter(pk=row.pk)` raises `AttributeError` on `None`. Every current caller uses a distinct
  order, so it works today; the docstring will invite a second `self.queue()` in the next test and the failure will
  point at the wrong line.
- **Fixture cost:** the file creates a `User` + `Order` per outbox row (5 users/orders for the 5-row cases, 23 for the
  log-bound case at `:1574-1579`); `TransactionTestCase` truncates. Correct, but it makes this file the slowest unit
  suite in the tree.

## Axis 4 — architecture / smells

- **The worker test is a 1,732-line, 15-class module** that tests five different surfaces: the loop, the status
  vocabulary, the claim's SQL, the operator command, and the call-site conversion. Q36's command tests
  (`--retry-dead`, `--status-only`, `--purge-expired`) live here rather than beside the command. Split candidates:
  `test_notification_outbox_command.py` for `DrainCommandTests` + `OutboxRetryRetentionTests` +
  `OutboxBatchSizeArgumentTests`.
- **Five duplicated bodies** (Q14-10) are the visible cost of that growth.
- **The superadmin file is three flows in one**: role declaration, escalation guard, and the R-1-B03 fulfilment queue
  (`:481-1214`, ~730 of its 1,259 lines). The queue half has nothing to do with the tier and inherits the tier's test
  module only because both were SPEC-1-B03.
- **Docstring-vs-behaviour drift is the file's dominant smell**, and it is dangerous in exactly one direction: a reader
  trusts a stated guarantee (`:19-23` "A second worker cannot take a claimed row. Proved twice", `:386` "the claim must
  refuse it", `:929-933` "a double-claim would show as two") and does not re-derive it. Three of the ten rows here are
  that drift (Q14-01, Q14-04, Q14-05). The comments are more confident than the assertions.
- **A stale cross-file docstring** in `tests/test_notification_outbox.py:277-281` still says at-least-once "is the locked
  status/sent_at claim, which ASYNC-2c2 has not built" — it is built, 1,000 lines of it, and tested here.
