## Findings

### Q20-01 — P2 HIGH — `SECRET_KEY` is checked for presence, not for safety; the repo publishes a key that passes
`backend/config/settings.py:56` (guard at `:65–66`), `backend/.env.example:4`.

```python
SECRET_KEY = os.getenv("DJANGO_SECRET_KEY", "unsafe-development-key-change-me")   # 56
DEBUG = os.getenv("DJANGO_DEBUG", "false").lower() == "true"                       # 63
if not DEBUG and not os.getenv("DJANGO_SECRET_KEY"):                              # 65
    raise RuntimeError("DJANGO_SECRET_KEY must be set when DJANGO_DEBUG is false.")
```

The guard's own docstring (V-02) claims the deployment "must set a real DJANGO_SECRET_KEY to boot". It
actually only requires the variable to be non-empty. Two paths end in a **publicly known** signing key:

1. **Template copy.** `backend/.env.example:4` ships `DJANGO_SECRET_KEY=change-me-to-a-long-random-string`.
   A deployment that fills in the blanks it is told about (`DATABASE_URL`, hosts) and leaves the key —
   the file's own header says "copy to .env and fill in" — boots with a key printed in this repository.
2. **`DJANGO_DEBUG=true` in a production process** (incident debugging, forgotten) skips the guard
   entirely and lands on the literal `unsafe-development-key-change-me`, with verbose error pages.

Why the payoff is total rather than cosmetic: `SIMPLE_JWT` (1351–1360) declares **no `SIGNING_KEY`**, so
SimpleJWT falls back to `settings.SECRET_KEY`; the repo itself asserts this in
`tests/test_deployment_contract.py:663–669` ("Rotating SECRET_KEY is a mass logout here, because it signs
the JWTs and the guest-cart sessions"). With `SECRET_KEY` known, an attacker mints an HS256 access token
for any user id (staff/admin included) and forges `django.core.signing` values (password-reset tokens,
`mfa_trusted_device` markers).

Fix: when `not DEBUG`, refuse a key that is shorter than ~50 chars or equal to any placeholder shipped in
the tree (`change-me-to-a-long-random-string`, `unsafe-development-key-change-me`,
`collectstatic-build-only-not-a-real-secret`), and reject `DEBUG=true` booting with a known placeholder.
Confidence: mechanism **H**; reachability **M** (requires the operator mistake, which the template invites).
Triage note: if `.env.example` is in fact the deploy template, this is FIX-NOW (auth bypass); graded P2
because no code path reaches it without that mistake.

### Q20-02 — P2 MEDIUM — `prune_carts` is a documented periodic job with no scheduler, and a test locks the gap shut
`backend/cart/management/commands/prune_carts.py:5` vs `backend/config/settings.py:777–832`.

The command's docstring: *"This command is the scheduled cleanup for those rows"* (anonymous, empty,
orderless carts older than `--days`). The beat schedule contains exactly `expire_reservations`,
`drain_notification_outbox`, `purge_notification_outbox`. `grep prune_carts` over the whole worktree
returns only `cart/tests_merge.py:211` and the `changes.md` row — no beat entry, no cron line in
`deploy-runbook.md` (whose only cron block is the `pg_dump` backup), no `common/tasks.py` shim. Guest
cart rows therefore accumulate for the life of the deployment, at table-growth rate proportional to
abandoned sessions.

This is the exact failure mode `common/tasks.py`'s doctest-like prose was written to close ("all built,
all tested, and none of them SCHEDULED") — reproduced by the next feature that added a sweep.

Aggravating: `tests/test_celery_scheduling.py:103–110` asserts `set(schedule) == set(EXPECTED_SWEEPS)`,
so *adding* the missing entry reds the suite. There is no test of the property that actually matters
("every command whose docstring claims a cadence has a beat entry"), so the gap is invisible to CI and
a fix must edit the pin.

Fix: add `prune_carts` to `EXPECTED_SWEEPS` + `common/tasks.py` + the schedule (daily), or delete the
"scheduled cleanup" claim and document the operator cron. Confidence **H**.

### Q20-03 — P2 MEDIUM — beat cadences take unvalidated ints: one silently collapses to hourly, one kills the boot
`backend/config/settings.py:733–739`, `:786`, `:823`.

`CELERY_BEAT_EXPIRE_EVERY_MINUTES = _env_positive_int(..., 5)` is only checked for `>= 1`, then
interpolated into a crontab field. Measured against the pinned celery 5.6.3 in
`comp-wt/backend/venv`:

```
crontab(minute='*/61').minute  -> {0}          # every 61 min becomes ONCE PER HOUR
crontab(minute='*/90').minute  -> {0}
crontab(minute='*/7').minute   -> {0,7,14,...} # normal
crontab(hour=25)               -> ValueError: Invalid crontab pattern. Valid range is 0-23
crontab(hour=-1)               -> ValueError
```

So `CELERY_BEAT_EXPIRE_EVERY_MINUTES=60..119` silently degrades the reservation sweep from every-N-minutes
to hourly with no log line — while `RESERVATION_TTL` still defaults to 900 s, i.e. the sweep now runs
(up to) four TTLs late and lapsed holds keep gating available-to-sell. Measured, not inferred.
`CELERY_BEAT_PURGE_HOUR=25` (a plausible 24-hour-clock vs 1–24 confusion) raises out of `_beat_schedule()`
at import, killing the deployment with a celery internal message — fail-closed, but it breaks the
module's own stated contract at `:511–512` ("Env-driven ints must never take the app down at startup").

Neither documented coupling is validated: sweep cadence < `RESERVATION_TTL` (`:778–782`), and
`NOTIFICATION_OUTBOX_LEASE_SECONDS` > `EMAIL_TIMEOUT` (`:623–630`, "MUST exceed"). Both are env-overridable,
so a single env change silently breaks a stated MUST.

Fix: validate at import — expire minutes in `1..59`, purge hour in `0..23`, and warn/refuse when
`cadence_seconds >= RESERVATION_TTL` or `LEASE <= EMAIL_TIMEOUT`. Confidence **H**.

### Q20-04 — P2 MEDIUM — `_env_bool` silently disables a default-true security flag on an unrecognised spelling
`backend/config/settings.py:142–152`, consumed at `:155`, `:167`, `:1713`.

```python
raw = os.getenv(name)
if raw is None:
    return default          # absent -> documented default (safe)
return raw.strip().lower() in ("1","true","yes","on")   # present-but-unknown -> False
```

An *absent* variable is handled correctly (`SESSION_COOKIE_SECURE` → `not DEBUG` → True). A *present but
mistyped* one is not: `SESSION_COOKIE_SECURE=enabled`, `=TRUE!`, `=ja`, `=Yes,please` (any spelling outside
the four) returns `False` and **silently discards the hardened default**, so the session and csrftoken
cookies stop being `Secure` in a `DEBUG=false` deployment. No warning; every sibling resolver
(`_env_currency` 1245, `_env_log_level` 1480, `_env_positive_int` 539, `_env_money` 1196) warns on the
value it ignores.

Axis-5: `tests/test_settings_security.py:1473–1486` calls the helper with `default=False` only, so it
pins the harmless direction and would pass unchanged if the safe direction were broken.

Fix: warn on unrecognised values (keep `False` for the off-by-default flags, but return `default` for the
secure-by-default pair, or make `_env_bool` warn unconditionally). Confidence **H**.

### Q20-06 — P3 LOW — CORS keeps its development origins in production while its twin refuses to boot
`backend/config/settings.py:1424–1429` (vs `:1427`).

```python
CORS_ALLOWED_ORIGINS = _host_list(os.getenv("CORS_ALLOWED_ORIGINS", DEV_FRONTEND_ORIGINS))  # 1424
CSRF_TRUSTED_ORIGINS = _env_hosts("CSRF_TRUSTED_ORIGINS", DEV_FRONTEND_ORIGINS, DEBUG)      # 1427
CORS_ALLOW_CREDENTIALS = True                                                              # 1429
```

`CSRF_TRUSTED_ORIGINS` raises `ImproperlyConfigured` outside development (via `_env_hosts`); its twin uses
`_host_list` and keeps `http://localhost:3000,http://127.0.0.1:3000` under `DEBUG=false`, with credentials
allowed. The comment at 1419–1421 admits the reason (the image build boots non-debug without the key), so
this is deliberate — but it means the fail-closed posture has one hole by construction, and a production
browser origin list that silently trusts loopback is the kind of default that survives into a real deploy.
Blast radius is bounded: both auth cookies are `SameSite=Lax`, so no ambient credential rides a cross-site
XHR; the exposure is unauthenticated cross-origin reads from a page on `localhost:3000` (a port this project
itself uses). Axis-5: only the `DEBUG=true` branch is pinned (`tests/test_settings_security.py:576–580`).
Fix: refuse the loopback default outside dev in the runtime boot while keeping a build-time opt-out, or
log a loud warning. Confidence **H**.

### Q20-07 — P3 LOW — no `DEFAULT_PERMISSION_CLASSES`: DRF's default is `AllowAny`
`backend/config/settings.py:1260–1341`.

The `REST_FRAMEWORK` dict sets `DEFAULT_AUTHENTICATION_CLASSES`, `EXCEPTION_HANDLER`,
`DEFAULT_THROTTLE_CLASSES`, `DEFAULT_THROTTLE_RATES`, `NUM_PROXIES` — and nothing else. `grep` for
`DEFAULT_PERMISSION_CLASSES` over `backend/**/*.py` returns **no match**, so the framework default
(`rest_framework.settings.DEFAULTS['DEFAULT_PERMISSION_CLASSES'] == ['AllowAny']`) applies: a view that
forgets `@permission_classes` is public, and the failure is a *missing* line that review has to notice.
`DEFAULT_THROTTLE_CLASSES` shows the deny-by-default instinct was applied to throttling but not to authz.
This is an architecture-level default, not a claim that any shipped view is open. Fix:
`DEFAULT_PERMISSION_CLASSES = [IsAuthenticated]` with the public views made explicit (they already declare
`AllowAny`-equivalent behaviour via their own decorators). Confidence **H**.

### Q20-08 — P3 LOW (DOC-ONLY) — `.env.example` is labelled production and is neither hardened nor bootable
`backend/.env.example:9`, `:16`, `:19`, `:133`, `:134`, `:699`, `:702`.

The template declares `DJANGO_DEBUG=false` + `DJANGO_ENV=production`, yet ships

for a plain-HTTP local run") contradicts its own `DJANGO_ENV=production` / `DJANGO_DEBUG=false`.
Fix: make the template a genuine local template (`DJANGO_DEBUG=true`, no `DJANGO_ENV`), and move the

### Q20-09 — P4 INFO — 1,720-line god module; the URL map is clean
`backend/config/settings.py` (whole file), `backend/config/urls.py:198–220`.

`settings.py` holds ten ad-hoc env resolvers, ~60 knobs with multi-paragraph rationale, the Celery beat
schedule, the Sentry bootstrap and the logging dict in one module, so every parser invariant can only be
tested by re-importing the whole module in a subprocess (`tests/test_settings_security.py:112–129`, 60 s
timeout each) and branch combinations are effectively untestable — which is why the security pins are
subprocess-only. Extracting the resolvers to `config/env.py` (pure, no settings dependency) would make
I1–I3 unit-testable and shrink the boot surface.

URL map (`urls.py`, read in full): no docs route, no `static()`/debug route, `admin/` is MFA-gated
(`admin.py:63–64`), the media route is appended last and unconditional by design (198–220, with the
runbook's nginx alternative) — `django.views.static.serve` guards traversal via `safe_join`, so this is a
performance/architecture posture, not a path traversal. `config/tests.py` pins the dual `/api/` ↔ `/api/v1/`
mounts and the webhook path; it holds no settings assertions (those live in `tests/test_settings_security.py`).

## Focus questions — direct answers

1. **Does anything fail open when an env var is missing?** `DEBUG`, `DJANGO_ENV`, `ALLOWED_HOSTS`,
   `CSRF_TRUSTED_ORIGINS`, `DATABASE_URL`, the proxy-header pair: **no, all fail closed.** `SECURE_SSL_REDIRECT`
   and `SECURE_HSTS_SECONDS` default to the development value outside dev (1670, 1676 — compose turns them on);
   `CORS_ALLOWED_ORIGINS` keeps loopback origins (1424). **`SECRET_KEY` fails open on *value*, not presence** (Q20-01).
2. **Deny by default?** Parsers, yes (with Q20-04's typo hole). DRF authz, **no** — `AllowAny` is the default (Q20-07).
3. **`_env_int`/`_env_bool` bounded and non-throwing?** Non-throwing: `_env_int` catches `ValueError`, `_env_bool`
   never raises — **except** the two knobs that bypass them or feed a validator downstream (`EMAIL_PORT` 553,
   crontab 786/823, Q20-03/Q20-05). Bounded: **no** — `_env_int` has no floor or ceiling, so negative and
   implausibly large values reach consumers (`MAX_UPLOAD_MB`, `ORDER_HISTORY_*`, `MFA_TRUST_DAYS`,
   `CELERY_BEAT_PURGE_HOUR`); only `_env_positive_int` and `_env_money` bound anything.
4. **Does the URL map expose admin/docs/media/debug in production?** admin: yes, by design and MFA-gated;
   media: yes, deliberately, with a documented nginx front door; docs/debug: **no**.
5. **Are throttle scopes wired?** All **11** declared scopes have at least one applier — `coupon`
   (`orders/views/checkout.py:1058`), `cart` (`cart/views.py:58,148,219`, `orders/views/checkout.py:378`),
   `auth` (9 sites), `register` (`accounts/views.py:525`), `username-probe` (584), `recovery` (659,684,712),
   `payment` (`orders/views/payment.py:85`), `restock` (`products/restock_views.py:180`), `restock-guest`
   (the purpose-built `GuestPairThrottle.pair_scope`, 156), `webhook` (`orders/webhooks.py:564`),
   `tracking` (`shipping/views.py:228`). **No declared-but-unapplied scope.** Residual unthrottled public
   POSTs (e.g. `orders/views/return.py:513`) are the open V-04's scope — not re-reported.
6. **Is every periodic task reachable?** The three scheduled ones, yes (they are registered and
   `tests/test_celery_scheduling.py:123` proves it). `prune_carts` is **not** (Q20-02), and a cadence value
   can silently change meaning (Q20-03).
7. **Any secret read at import or printed?** Read at import, yes and unavoidably (`load_dotenv()` + every
   `os.getenv` at module scope, `STORAGES` carries the S3 credential pair at 931–932). **Printed: none found** —
   no resolver logs a secret, DB URLs are never echoed, Sentry gets `send_default_pii=False` and logs only
   the exception type/message. `manage.py`, `wsgi.py`, `asgi.py`, `celery.py`, `__init__.py` contain no I/O
   at import (celery's app config is lazy, no socket).
