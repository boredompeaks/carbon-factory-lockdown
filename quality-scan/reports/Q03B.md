## What I verified as sound (negative results worth recording)

These are the invariants the brief asks about that I could not break. They are not findings; they are the reason the findings below are narrow.

1. **Capture is idempotent against its own callers, and the shared transaction is what makes it sound.** Both writers hold `select_for_update` on the Order row and call `commit_order_sale` inside the same `atomic()` block that writes the capture state (`views/payment.py:304,499,550-559`; `webhooks.py:258-268,393-441`), and the guard reads `locked_order.payment_status` from a **re-read** of that locked row (`inventory.py:133-142`). Callback-then-delivery and delivery-then-callback both decrement exactly once; I traced both interleavings and the loser is refused by the already-processed gate (`views/payment.py:327-350`) or by `CAPTURED_PAYMENT_STATES` (`webhooks.py:337-357`). The guard's value set is derived from the machine (`state.py:286`), not listed — correct, and the docs explain why it is not the returns set.
2. **Stock can't go negative on the sale path.** Demand is summed per product before the decrement (`inventory.py:171-181`) — the per-line-check hole the comment describes is genuinely closed — and `products.stock` is a `PositiveBigIntegerField` (`products/models.py:63`) with Django's `>= 0` check constraint behind it.
3. **Lock order is one total order across both capture writers:** Order → products (`ORDER BY id`) → Coupon → Cart (`inventory.py:133,152-157,213-214,291-293`), matching the callback's own pre-check order (`views/payment.py:304,383-388,447`). I found no cycle: the refund seam's second lock set (`Refund` rows for one order, `refunds.py:203`) is written only by the refund writer.
4. **Webhook authenticity is verified before anything is parsed or mutated, and fails closed.** Raw `request.body` → `hmac.compare_digest` over the exact bytes → only then `json.loads` (`webhooks.py:578-635`); unconfigured secret → 503 before any write (`:580-595`); non-ASCII / wrong-length / whitespace-padded signatures refused before the comparison (`:161-188`), so the unauthenticated 500 the docstring warns about is really closed.
5. **Replay cannot regress the payment dimension, twice over.** Unique `event_id` + insert-before-handler (`webhooks.py:668-694`, `models.py:1257-1260`), and separately the capture-state gate (`:337`) *and* the machine edge (`:359-361`, verified `payment_transition_allowed('refunded','captured') == False`) both refuse a second capture fact.
6. **Refund money is quantized once, on both sides of the gateway** (`refunds.py:59-63`, `_store_money` at `webhooks.py:137-151`), and NaN/Infinity/negative/over-balance amounts are refused before any comparison that could raise (`refunds.py:260-283`).
7. **The `timeout=` kwarg in `refund_payment` is real, not decorative** — verified against the pinned SDK (`venv/.../razorpay/client.py:247-252` → `:151-184`, `resources/refund.py:16-21`): `create(data, **kwargs)` → `post(path, data, **options)` → `session.post(url, auth=…, verify=…, **options)`. `requirements.lock` pins `razorpay==2.0.1`, the version read.
8. `ruff` is clean on all four files: no unused imports, no dead locals, no bare `except:` (every handler names its exception or is a documented trailing-write guard), no `eval`/`exec`/`raw`/f-string SQL.

## Findings (severity order)

### Q03B-01 | P2 / HIGH | CODE | `backend/orders/refunds.py:300`
**The gateway refund is issued inside the transaction that owns the only record of it, so a post-call failure — including the timeout the code specifically handles — rolls back the `Refund` row *and its `Idempotency-Key`*; the retry then refunds the money a second time at the provider while the store's ledger still shows one.**

The sequence is `refunds.py:189` (`with transaction.atomic():`) → `:285` `Refund.objects.create(..., idempotency_key=…)` → `:300` `refund_payment(...)` (a live HTTP call) → `:307` `refund.save(PROCESSED)` → `:338` `log_api_action(...)`. Any exception after `:300` unwinds the whole block, and `:348-357` deliberately re-raises.

Two distinct losses come out of one rollback:

1. **The idempotency key is destroyed.** The replay probe (`:205-223`) is a scan of *committed* `Refund` rows for this order, and the unique constraint that backs it is on those same rows (`models.py:697-700`). On a timeout the row is gone, so a retry carrying the same `Idempotency-Key` finds nothing, passes the probe, and calls the gateway again. That is exactly the case the module, the view and the model all claim is solved: `refunds.py:172-174` ("an `idempotency_key` collapses a retry onto the refund it already produced (no second gateway call)"), `views/refund.py:116-118`, and `models.py:673-676` ("a client that retries the same refund **after a timeout** must collapse onto the refund it already produced rather than pay the customer twice"). The claim is false for the only failure mode it names.
2. **The provider's money and the store's record diverge silently**, because the seam sends the provider no idempotency identifier of its own (`refund_payment` posts only `payment_id` + `amount`, `refunds.py:97-100`), and the balance gate that would catch a second refund reads `Refund.refunded_total` — PROCESSED rows only (`models.py:704-715`) — so it still believes the full balance is refundable.

Reachable, partial-amount case: operator refunds ₹300, the socket times out at `RAZORPAY_TIMEOUT` (`settings.py:594`) after Razorpay processed it; the view answers 502 (`views/refund.py:149-155`); the operator retries with the same key; a second ₹300 refund is created at the provider; the store records one. The provider's own cap stops a *total* overshoot, so the realistic harm is a customer paid twice against a ledger that shows once — the money is wrong and the audit trail (`log_api_action` never ran) has nothing to reconcile from.

This is not V-03/F-04: those are the *capture* side (charge-then-409). This is the refund side, a different writer, and it is a new mechanism.

Evidence that the mechanism is real rather than hypothetical: the repo's own pin `tests_refunds.py:541-552` asserts `Refund.objects.count() == 0` after a **2xx response with no refund id** — i.e. the suite proves that a provider-acknowledged attempt destroys the row and the key. No test then replays the key. The "2xx without an id" branch is itself a false negative: a body-shape change at the provider would be read as "no refund happened".

Fix route: **NEXT-BUILD.** Either commit the attempt (a durable `Refund` row with its key in its own transaction, then a reconciliable `Sent/Unknown` state moved forward by the refund webhook), or send a provider-side idempotency identifier and probe it on retry. The current design cannot be made safe by reordering inside one transaction.

### Q03B-02 | P3 / LOW | CODE | `backend/orders/webhooks.py:151`
**`_store_money` bounds the amount's *type* and *sign* but not its *magnitude*, so a signed delivery carrying a very large integer either raises an uncaught `decimal.InvalidOperation` (reproduced) or overflows `PaymentEvent.amount` on PostgreSQL (source-read) — a 500 that leaves the delivery unrecorded and the provider retrying the same payload forever.**

`_store_money` (`:137-151`) accepts any non-negative `int`, then `:151` does `quantize_money(Decimal(amount_minor_units) / MINOR_UNITS_PER_MAJOR)`. `quantize` raises `InvalidOperation` once the result needs more digits than the decimal context holds — measured in this session:

```
10**26 -> 1000000000000000000000000.00        (ok)
10**27 -> 10000000000000000000000000.00       (ok)
10**40 -> RAISES InvalidOperation
```

and the destination column is `DecimalField(max_digits=10, decimal_places=2)` (`models.py:1284-1289`), i.e. anything above `99,999,999.99` cannot be stored. `SQLite` keeps it (no enforcer), PostgreSQL raises `DataError` at `event.save()` (`:683-685`) — the exact SQLite/PG asymmetry the same module already defends against for its **string** columns.

Why this is a defect and not a nit: the module's central promise is "every delivery is recorded, whatever it turns out to be worth" (`webhooks.py:65-67`, `models.py:1205-1255`), and it enforces that for `event_id`/`event_type`/`gateway_payment_id` by reading the bound off the column itself (`_fits`, `:191-211`). The money column, which is the one the whole endpoint exists to reconcile, has no equivalent check — so the one class of payload that must never go unrecorded can go unrecorded. `DecimalRefundId`-style truncation is rightly refused for ids (`_stored_reference`, `:203-211`); for money the honest answer is "record the delivery, store `amount=None`", which is the vocabulary the model already has (`amount` is nullable "for an event that carries no amount").

Reachability: requires a valid signature, so not user-reachable — hence P3, not P2. The unauthenticated surface cannot trigger it (signature gate at `:597-611`).

Fix route: **FOLD-INTO-NEXT** — bound the value against `PaymentEvent.amount`'s money range inside `_store_money` (the same `_meta.get_field(...)`-derived style as `_fits`) and return `None` for out-of-range, or widen the column. Note the two are one decision: a `_fits`-style helper for money would have caught both the `InvalidOperation` and the PG overflow.

### Q03B-03 | P2 / MEDIUM | CODE | `backend/orders/webhooks.py:494`
**Provider-origin refunds are recorded and then forgotten: nothing in the tree consumes `PaymentEvent`, so `Refund.refunded_total` never learns about money Razorpay returned out of band, and the refund seam's balance gate will refund up to the *full* order total again — leaving `payment_status` and `refunded_total` wrong by construction.**

`_apply_refunded` (`:494-534`) writes `event.gateway_payment_id`, `event.amount`, `event.order`, logs, and returns `RECORDED`. It writes no `Refund` row — a deliberate, documented decision (`webhooks.py:53-63`) whose compensating control is "the finance operator who reconciles payments and refunds ([1.31]) matches it against the Refund rows". **That reader does not exist**: `grep` for `PaymentEvent` across the tree finds only `webhooks.py` (the writer), `models.py` (the definition) and the test modules. So the recorded fact has no consumer, while the only guard against over-refunding is `refundable_remaining = quantize(total_amount) − Refund.refunded_total(...)` over PROCESSED `Refund` rows (`models.py:427-437`, `:704-715`).

Concrete sequence (₹1,000 order): a ₹300 refund is issued from the Razorpay dashboard → `payment.refunded` delivery is recorded → the order still shows `payment_status='captured'`, `refundable_remaining=1000.00`. A finance operator then uses `POST /api/admin/orders/:id/refund/` for ₹1,000: the balance gate passes (`refunds.py:229-230`), the gateway rejects (only ₹700 left), the operator retries with ₹700, which the gateway accepts. The store now records `refunded_total=700.00` and `payment_status='partially_refunded'` for a payment of which **₹1,000 has been returned**, and it can never reach `refunded` because the seventh century of the balance is invisible to it.

Severity is P2 rather than P1 because the provider's own cap prevents an actual over-refund of *new* money; what breaks is the financial record (the dimension the whole refund design is built on) and the reconciliation the webhook was created to feed. Confidence **H** on the arithmetic and on the absent reader; the design is documented, so the triage owner may accept it — but if it is accepted, the docstring's "reconcile against the refund seam" is satisfied by a human, not by any code, and `payment_status` should not be presented as the authority (as `refunds.py:316-322` and `models.py:619-620` do).

Fix route: **NEXT-BUILD** — when a refund event binds to an order, record a `Refund` row with `actor=None`, `reason` from the provider, `gateway_refund_id` as the replay key (it is already `unique=True`, `models.py:656-661`) and `status=PROCESSED`; the existing balance gate and the unique constraint then do the rest. If that is refused on design grounds, the balance gate needs a second term that reads recorded `PaymentEvent` refund rows.

### Q03B-04 | P2 / MEDIUM | CODE | `backend/orders/webhooks.py:606`
**An unauthenticated caller's `X-Razorpay-Event-Id` header is interpolated into the log record on the signature-rejection path, before any validation or width bound — attacker-chosen bytes (control characters, ANSI escapes, up to the server's header limit) land in the money endpoint's log.**

`:597-607`: when the signature header is missing or wrong, the handler logs `request.headers.get(WEBHOOK_EVENT_ID_HEADER)` verbatim at WARNING; the same raw header is logged at ERROR when the secret is unconfigured (`:587-591`). The only validation of that header — `.strip()` and the `_fits(event_id, "event_id")` width bound — happens **later** (`:613`, `:650`), i.e. after both of these lines, and neither runs at all on the reject path. This is reachable by anyone: no signature, no session, no throttle bypass needed (the `webhook` scope allows 120/min/IP, `settings.py:1317`).

CWE-117 (improper output neutralization for logs). The repo already has the house pattern for exactly this class of value and does not apply it here: `common/middleware.py:66-78` `sanitize_request_id` allow-lists an inbound correlation header with a regex and falls back to `""` rather than propagating arbitrary bytes. `webhooks.py` propagates arbitrary bytes.

Honest bound on the claim: a raw CR/LF in an HTTP header value is normally rejected by the WSGI server's parser, so *newline-forged log lines* are not reliably reachable; ANSI/terminal escapes, non-printable control characters and multi-KB values are. The value is also unauthenticated, so it can be produced by any scanner.

Fix route: **NEXT-BUILD** (3 lines) — reuse `sanitize_request_id`-style allow-list on the header before logging (or log only `len()` and a hash on the pre-auth path), and truncate.

### Q03B-05 | P3 / LOW | CODE | `backend/orders/webhooks.py:134`
**`CAPTURED_PAYMENT_STATES` is a hand-written copy of the machine fact `state.CAPTURED_SALE_PAYMENT_STATUSES` — verified byte-identical in content today — in the one module whose docstring promises it writes no status literal, leaving two gates where the machine has one.**

`webhooks.py:134` lists `("captured", "partially_refunded", "refunded")`; `state.py:286` derives `CAPTURED_SALE_PAYMENT_STATUSES` as the closure of `PAYMENT_CAPTURED` over `PAYMENT_ALLOWED_TRANSITIONS`, and `inventory.py:86,135` imports that derived set for the identical question. Verified equal by importing the dependency-free module in this session:

```
derived: ['captured', 'partially_refunded', 'refunded']   equal: True
payment_transition_allowed('refunded','captured') -> False
```

So there is **no live behavioural defect** — the duplicate is masked today by the machine gate at `:359-361`. The latent vector is specific, and it is a money-state regression, not cosmetic: a new payment value placed downstream of `captured` would be admitted by this copy's gate at `:337` (it would read "not captured"), and whether the refunded→captured write is then prevented depends entirely on the *separate* machine gate at `:359`. One gate instead of two, and the surviving one belongs to a different file. It also contradicts this module's own docstring (`:29-32`: "Only the machine writes payment state… Nothing here writes a status literal").

Fix route: **FOLD-INTO-NEXT** — import `CAPTURED_SALE_PAYMENT_STATUSES` (it is already the exact set), delete the literal.

### Q03B-06 | P3 / LOW | CODE | `backend/orders/webhooks.py:426`
**The capture-state write is still two copies: `commit_order_sale` extracted the stock/coupon half of a capture, but status + fulfilment + payment + reference + `paid_at` + the status event + the two audit rows + the notification enqueue remain duplicated between the webhook and the callback — the exact drift class `inventory.py`'s docstring says it exists to end.**

Webhook: `:426-441` (status, `fulfilment_for_status`, `PAYMENT_CAPTURED`, `razorpay_payment_id`, `paid_at`), `:443-449` `OrderStatusEvent(TRIGGER_PAYMENT_WEBHOOK)`, `:450-466` `PAYMENT_VERIFIED` + `ORDER_PAID`, `:479-489` `notifications.enqueue`.
Callback: `views/payment.py:546-559` (`paid_at`, status, reference, then `payment_status = payment_for_status("confirmed")`), `:565-571` `OrderStatusEvent(TRIGGER_PAYMENT_VERIFY)`, `:583-600` the same two audits, `:619-629` the same enqueue.

The two copies already differ in shape: the callback derives `payment_status` from the lifecycle (`payment_for_status("confirmed")`) while the webhook writes the payment constant directly *plus* `fulfilment_for_status(target_status)`, which the callback never touches. No live divergence today only because `fulfilment_status` defaults to `"unfulfilled"` (`models.py:197-201`) and `confirmed` maps to exactly that — a default, not a statement. The next field added to "what a capture records" will be added to one writer.

Fix route: **FOLD-INTO-NEXT** — move the capture-state write into `orders/inventory.py` beside the sale it already owns (or a sibling `commit_capture_state`), leaving each caller only its trigger value and its actor.

### Q03B-07 | P3 / LOW | CODE | `backend/orders/tests_guest.py:1009`
**The only guest-row refund pin mocks the gateway with a bare `return_value` and asserts nothing about the call, so a wrong `payment_id` or a wrong amount inside the seam stays green.**

`tests_guest.py:1009-1010` (`client = self.razorpay_mock()` / `client.refund.create.return_value = {"id": "rfnd_GUEST"}`) then `:1012-1027` asserts the HTTP body, `payment_status`, `refundable_remaining` and `Refund.kind` — all of which are computed by the store from its own request, not from what it told the gateway. `grep` for `assert_called|call_args` in this file: **zero hits**. A seam that refunded `pay_GUEST1` (the other fixture's payment) or sent `amount=1` would produce the same 201 and the same row. `tests_refunds.py` pins the equivalent for account rows; this file is the only pin for the guest-row shape, and it is mutation-blind on the money. It also asserts on `res.data` rather than the rendered wire, so a serializer/renderer change that dropped `refundable_remaining` from the body would not be caught.

Fix route: **FOLD-INTO-NEXT** — `client.refund.create.assert_called_once_with({"payment_id": "pay_GUEST2", "amount": 100000}, timeout=ANY)` (the amount is a literal, per the repo's no-recomputed-oracle rule).

### Q03B-08 | P3 / LOW | CODE | `backend/orders/refunds.py:191`
**The refund seam's entire concurrency authority is the Order-row lock, and no test can fail if it is deleted: SQLite cannot exercise `select_for_update` at all, and the flow's "race" test resolves contention by sequence — the same outcome a lock-free implementation produces.**

`refunds.py:191` (`Order.objects.select_for_update().get(id=order_id)`) + `:203` (the refund-row locks) are the only things standing between two concurrent ₹700 refunds and a ₹1,400 refund of a ₹1,000 payment. The suite runs on SQLite, where `features.has_select_for_update` is `False`, so the lock compiles to nothing; and `RefundRaceTests` (`tests_refunds.py:637-654`) states its own method — "resolving two attempts in sequence is exactly the interleaving those locks permit" — which is indistinguishable from the no-lock behaviour it is supposed to exclude. Compare the sale commit, which does have mutation-proof pins that read the emitted SQL (`tests_webhooks.py:1719-1757` record locked reads and assert `("id",)`); `refunds.py` has no equivalent anywhere. Removing `select_for_update()` from `refunds.py:191` turns the suite green.

Fix route: **FOLD-INTO-NEXT** — add the `_LockedReadRecorder`-style pin for `issue_refund` (one Order lock, taken before the refund-row read), i.e. the same instrument applied to the sale commit.

### Q03B-09 | P4 / INFO | DOC-ONLY | `backend/orders/refunds.py:197`
**`Refund.Status.PENDING` has no observer, so the docstring's justification for writing the row twice — "a real row under the order's locks while the gateway call is in flight" — describes a state no transaction can ever read.**

The row is created at `:285` inside `:189`'s `atomic()` and updated at `:307` in the same block, so it is never visible to another transaction: a concurrent writer blocks on the Order lock at `:191` and, when it is released, reads the committed *PROCESSED* row. Hence `refunded_total`'s "Only PROCESSED rows count" filter (`models.py:707-714`) defends against a state the writer cannot produce, and `models.py:622-628`'s explanation of the two-write sequence ("so the requested money is a real row under the order's locks while the gateway call is in flight") is unbacked by any reader. No behavioural defect — but this is the sentence that makes the seam *look* like it has an in-flight record, which is exactly what Q03B-01 shows it does not have after a failure. Worth correcting rather than deleting the enum: the honest description is "an attempt marker that only exists if the attempt commits".
