## Findings

### F-01 — P2 · HIGH confidence · CODE · `state.py:49-55` (with `state.py:68-72`, `models.py:512-516,527-529`)

**Claim.** `pending → confirmed` is legal with **no precondition**, so a support operator can confirm an order whose payment is still `pending`; the resulting row has no exit through any customer or admin surface.

**Evidence (reproduced by reading):**
- `ALLOWED_TRANSITIONS["confirmed"] == {"shipped"}`; nothing enters `cancelled` from `confirmed` (`state.py:49-55`).
- The only registered precondition is for `"shipped"` (`models.py:527-529`), so `precondition_failures(order, "confirmed") == []` always.
- `models.py:512-516`: shipping requires `payment_status ∈ {captured, partially_refunded}` → the row cannot ship.
- `refunds.py:240-246`: refunding requires a captured payment → it cannot be refunded.
- `views/payment.py:327`: `if order.status != "pending" … 400 "This order has already been processed"` → the customer's own verify will not capture it.
- Reachable and already exercised: `admin.py:693-694` exposes `mark_confirmed` → `_bulk_set_status(..., "confirmed")` with no payment precondition; the suite builds the resulting state as a fixture (`tests.py:3616-3624`, `{"status": "confirmed", "payment_status": "pending"}`).

**Why it matters.** One routine admin click (confirm before the callback lands) strands the order: unshippable, uncancellable, unrefundable. The only exit left is a later gateway webhook (`webhooks.py:359` accepts it because `transition_allowed("confirmed","confirmed")` self-transitions) — i.e. the path that already fails often enough to need reconciliation.

**Fix.** Register a `confirmed` precondition (`payment_status == captured`, or `payment_method == COD`), or declare an `confirmed → cancelled` edge for `payment_status == pending`. Either is a small table/precondition edit.

**Triage:** NEXT-BUILD.

### F-02 — P2 · MEDIUM confidence · CODE · `models.py:533-542` + `:595-601`

**Claim.** `OrderStatusEvent`'s docstring says the trail is append-only and "no code path can rewrite history", but only `Model.save()` is guarded. The default manager is unguarded, so `OrderStatusEvent.objects.filter(...).update(...)`, `.bulk_update(...)` and `.delete()` rewrite or erase audit rows.

**Evidence.**
- `:595-601` rejects only `self.pk is not None` inside `save()`.
- `ast`: `OrderStatusEvent` has **no** `objects =` assignment — vanilla manager. Contrast `ReturnRequest.objects = ReturnRequestQuerySet.as_manager()` (`:1146`), whose `update`/`bulk_update` refuse a status write (`:1003-1041`), with the docstring `:987-1000` naming exactly these paths as the reason the gate exists.
- Test coverage mirrors the guard rather than the claim: `tests.py:3508 test_events_are_append_only` asserts the `save()` `TypeError` only; no test performs a queryset update on the table.

**Why it matters.** Spec 10.2's transition trail is what reconciliation reads. Immutability that depends on every future author avoiding `.update()` is a convention, not a guarantee — and the same file already contains the pattern that would fix it. P2 rather than P1 because no user-reachable path does it today (all `.update()` calls on the table in the tree are reads or in tests).

**Fix.** Install a manager overriding `update`/`bulk_update`/`delete` (mirroring `ReturnRequestQuerySet`) or use a DB trigger; pin it with a test that asserts the refusal.

**Triage:** NEXT-BUILD.

### F-03 — P3 · HIGH confidence · CODE · `models.py:512-516`

**Claim.** The shipped-edge precondition restates the captured-payment values as literals `("captured", "partially_refunded")` while `state.CAPTURED_MONEY_PAYMENT_STATUSES` (`state.py:262-266`) is the machine-derived answer to that exact question, and the two other gates already read the derived set.

**Evidence.**
- `state.py:239-266`: the set is the BFS closure of `PAYMENT_ALLOWED_TRANSITIONS` from `PAYMENT_CAPTURED`, minus sinks; the comment says restating either half is "what let the cycle-3 audit find the returns gate tracking only `captured`".
- `views/refund.py:274` uses `CAPTURED_MONEY_PAYMENT_STATUSES`; `inventory.py` uses `CAPTURED_SALE_PAYMENT_STATUSES` (`state.py:286`).
- `models.py:514` is the one remaining literal copy — in the gate that decides whether goods leave the warehouse.

**Fix.** `if order.payment_status not in CAPTURED_MONEY_PAYMENT_STATUSES:` — `models.py` already imports six names from `.state`.

### F-04 — P3 · HIGH confidence · CODE · `models.py:335`

**Claim.** `Order.updated_at = auto_now=True` is not maintained on the money paths: those writers pass `update_fields` without it, and Django skips `pre_save` for unlisted fields, so the column keeps its old value and the in-memory instance is not refreshed either.

**Evidence.**
- Django 6.1.1 `base.py:1090-1095` filters `non_pks_non_generated` by `update_fields`; `:1123` then builds values with `f.pre_save(self, False)` over the filtered list.
- Omitting writers: `views/payment.py:550` (`["status","razorpay_payment_id","paid_at"]`), `:559` (`["payment_status"]`), `refunds.py:331` (`["payment_status","refunded_at"]`), `views/checkout.py:848` (`["idempotency_key"]`).
- The repo knows the rule and compensates in exactly one place: `admin.py:651-657` — "on this Django, `save(update_fields=...)` leaves auto_now columns out unless listed".

**Why it matters.** `updated_at` is stale after every capture and every refund — the two events an operator would filter "changed since" on. No test asserts `updated_at` moves on those paths (`grep updated_at` in `orders/tests*.py` finds no assertion).

**Fix.** List `updated_at` in those `update_fields`, or override `Order.save()` to append it whenever `update_fields` is supplied (one place, covers future writers).

**Triage:** FOLD-INTO-NEXT.

### F-05 — P3 · MEDIUM confidence · CODE · `models.py:180-202`

**Claim.** Nothing at the model or database layer enforces the status vocabulary or status↔dimension coherence: `Order` has no `save`/`clean`, the three `choices=` lists are Python-only (no `CheckConstraint`), and the comment at `:183-185` ("the writers keep these in sync … `LEGACY_STATUS_DIMENSIONS` is the mapping") is false for the admin writers, which sync only the fulfilment half.

**Evidence.**
- `ast`: `Order` methods = `__str__, customer_name, recipient, refundable_remaining` (no validator).
- `Meta.constraints` (`:359-393`) = 2 uniqueness + 1 ownership CHECK; no status CHECK.
- `admin.py:531-534`: "Admin never touches `payment_status`", then `:534` writes only `fulfilment_status`; the bulk twin does the same (`:650`), and `cancel_pending` writes only the fulfilment half (`:813`). `LEGACY_STATUS_DIMENSIONS["confirmed"] == ("captured","unfulfilled")` (`state.py:197-203`), so an admin-confirmed row sits outside the declared mapping **by design**.
- Reproducible: `Order.objects.update(status="refunded")` persists a value absent from `STATUS_CHOICES` (char column, no CHECK); same for both dimensions.

**Why it matters.** The mapping is presented as the writers' contract but is really "the writers that touch payment". The next author adding a writer will believe the table. Either the comment or the constraint must move.

**Fix.** Correct the comment, and add `CheckConstraint`s for membership in the three vocabularies (not a status↔dimension CHECK — that would fail the admin's deliberate divergence).

**Triage:** FOLD-INTO-NEXT.

### F-09 — P3 · MEDIUM confidence · CODE · `models.py:466-470`

**Claim.** No layer enforces `subtotal == price * quantity` or `total_amount == Σ subtotals − discount_amount + shipping_amount`. `subtotal` is an independent column with `default=0`, so an `OrderItem` created without it stores `0.00` while the line's money is non-zero.

**Evidence.** `:466-470` — `price`, `quantity`, `subtotal` are three unrelated columns, `subtotal` defaulting to 0; `ast` shows `OrderItem` has only `__str__` (no `save`/`clean`); no constraint in its `Meta` (there is none). The sole writer is `checkout.py:861-876`; no test in `orders/` or `tests/` sums the lines and compares to `total_amount` (searched both trees), so the identity is unguarded and unpinned.

**Why it matters.** The current tree is consistent; the risk is any second writer (data-fix script, future line clone for partial fulfilment) silently creating lines that do not sum to the order total.

**Fix.** Derive `subtotal` in `OrderItem.save()` when it is not supplied, or add `CheckConstraint(subtotal = price * quantity)` (exact for 2-dp decimals on both engines).

**Triage:** FOLD-INTO-NEXT.

### F-10 — P3 · HIGH confidence · CODE · `serializers.py:41-65`

**Claim.** `OrderItemSerializer` marks seven of its nine fields read-only — and leaves `quantity` writable. On a projection whose whole purpose is a frozen purchase record, the one mutable field is the one a client would use to change what they bought.

**Fix.** Add `"quantity"` to `read_only_fields`, and pin the equality (`set(fields) == set(read_only_fields)`) in the existing snapshot test.

## Out-of-scope handoffs (defects that live only in the contract references)

1. **`Order.updated_at` never moves on capture or refund** — `orders/views/payment.py:550` and `:559`, `orders/refunds.py:331` pass `update_fields` without `updated_at` (F-04's model-side half is in scope; these call sites are the fix). The rule is already written at `orders/admin.py:651-657`.
2. **Unquantized, unclamped line math at checkout** — `orders/views/checkout.py:859` `item_subtotal = price * quantity` is not quantized and has no bound while `OrderItem.subtotal`/`Order.total_amount` are `max_digits=10`; a high-priced line times a large quantity overflows the column (`InvalidOperation`/`DataError`) at insert. Related: `views/payment.py:113` `int(order.total_amount * Decimal("100"))` truncates rather than validating.
3. **`OrderAdmin.save_model` transition check is an unlocked read** — `orders/admin.py:490-513` reads `Order.objects.get(pk=obj.pk).status` without `select_for_update`, then writes; the bulk twin deliberately locks (`admin.py:594-599`) and the returns admin path locks, so two concurrent change-form saves can both pass the edge/precondition checks and both append an `OrderStatusEvent`. The docstring at `models.py:1166-1171` claims the admin form holds the row with `select_for_update()` — true for returns, not for orders.
