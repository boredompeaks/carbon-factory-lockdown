## Direct answers to the five questions in the brief

### 1. Does `test_admin_rbac.py` prove the capability matrix for *every* admin class — including the User password channel QC-042 names?

**No, on both counts.**

- **"Every admin class" is a 7-of-17 allowlist.** `store_admins()` (`:86-91`) filters
  `admin.site._registry` by `if model in EXPECTED_MODELS` (`:89`), and `EXPECTED_MODELS`
  (`:40-42`) names seven models. The repo registers **17** store ModelAdmins
  (`@admin.register` in `accounts/admin.py` ×2, `cart/admin.py` ×1, `ops/admin.py` ×1,
  `products/admin.py` ×2, `orders/admin.py` ×6, `shipping/admin.py` ×5) plus Django's own
  `GroupAdmin` (`django/contrib/auth/admin.py:25`). **Ten store admins never enter any pin
  in the file**: `ProductVariant, OrderStatusEvent, Refund, RefundRequest, ReturnRequest,
  ShippingMethod, ShippingRate, Shipment, ShipmentEvent, ShippingProvider`. The module
  docstring's first bullet — "the whole registered store admin surface is role-aware
  (nothing missed)" (`:5`) — and the comment at `:97-99` ("if a future ModelAdmin forgets
  the role-aware base, this equality fails") are false: the one admin that *does* forget
  it, `ProductVariantAdmin(admin.ModelAdmin)` (`products/admin.py:465-470`), is registered
  for a model outside `EXPECTED_MODELS`, so the equality passes. That deferral is
  documented (SPEC-6-08) and separately pinned (`products/test_variant.py:228-233`), so
  the *live* surface is intentional — the defect is that the pin cannot fail for the next
  one. → Q12-01.
- **The password channel is not a matrix kind at all.** `PERMISSION_KINDS` is
  `("view","add","change","delete")` (`:52`), so the file proves only the four model
  permissions. Django's `user_change_password` view is gated on `has_change_permission`
  alone, and no test in the repo posts to `/admin/auth/user/<pk>/password/` (grep for
  `password/` in `backend/tests` returns only `/api/accounts/password-reset/…`). Worse
  than silent: `test_admin_role_keeps_full_function` (`:164-175`) *affirmatively asserts*
  that the `admin` role passes `has_change_permission` on `StoreUserAdmin` — the exact
  boolean QC-042 exploits — and nothing asserts the channel it opens. Tracked as QC-042
  (code) / QC-077 (test) → Q12-10, KNOWN.

### 2. Does `test_mfa.py` exercise replay under concurrency, or only sequentially?

**Only sequentially.** There is no `TransactionTestCase` and no thread in the module
(grep: the only threaded tests in the repo are `products/tests.py:505`,
`tests/test_e2e_concurrency.py`, `tests/test_notification_outbox_worker.py:848`).
Every replay pin is a second request after the first has committed:
`test_same_code_cannot_log_in_twice` (`:749-758`), `:1252-1258` (fresh client),
`:1305-1312` (admin door), `:181-194` / `:1073-1084` / `:1464-1482` (trust boundary).
The pins are still *correct* sequentially — `code` is recomputed, the watermark is read
back from the DB — so they would fail if the watermark comparison were deleted; they
simply cannot see the read–verify–write window. Tracked as QC-043 / Q11-02 / Q30-04
(code) and QC-077 (test) → Q12-09, KNOWN.

### 3. Do the audit tests assert the persisted row (who/what/target), or just that a log call happened?

**Mostly the persisted row — this is the strongest of the three files.**
`test_audit_structured.py` loads the row back (`AuditEvent.objects.get(...)`) and asserts
actor (`:219, :265, :408`), `source` (`:220, :264, :291, :407, :452`), and the target
inside `detail` — `model`, `object_id`, `object_repr` (`:222-223, :266-270, :328-329,
:409-410`) — plus the exact `changes` list (`:224-233, :271-278, :296-299, :411-420,
:455-458`). `test_delete_records_the_surface_and_outlives_the_row` (`:320-331`) even
proves the row survives the target. Two real gaps remain: (a) the trail is never
*failed* — nothing forces `AuditEvent.record` to raise, so the "commits with the mutation
or rolls back with it" claim (`accounts/admin.py:458-460`, `common/audit.py:194-196`) is
unproven for the admin surfaces (the repo's only rollback-together pins are on
`OrderStatusEvent`, in `orders/tests.py`) → Q12-06; (b) the LogEntry half, in
`test_admin_rbac.py`, is asserted by substring only → Q12-05.

### 4. Tautologies and asserts on log strings?

- **One truly vacuous assertion**: the third iteration of the QR exactly-once pin
  (`test_mfa.py:683-689`) reads `getattr(later, "data", "") or later` where `later` is a
  plain `HttpResponse` from `/admin/login/`; `HttpResponse` has no `.data`, so both
  `assertNotIn` calls run against `str(<HttpResponse status_code=200 …>)`, a string that
  cannot contain the artifact. → Q12-04.
- **One structural mirror**: the matrix test recomputes its expectation with the
  production predicate (`user_has_capability(user, model_admin.capability_map[kind])`,
  `:141-143`) while the implementation is that same expression
  (`common/admin.py:178-182, 186-196`). → Q12-02.
- **Asserts on log strings**: `assertIn("shipped", entry.change_message)`
  (`test_admin_rbac.py:665`), `assertIn("cancelled", …)` (`:679`), and
  `assertIn("order cancelled", …)` / `assertIn("Reason: …")` (`:602-603`) are substring
  checks on free text; `action_flag` is never asserted in this file (only
  `test_audit_log.py:74-107` and `test_staff_roles_admin.py:213` do that).
- **Escaping `None`**: `used.discard(None)` (`:115`) plus name-only set-equality
  (`:124-127`) means a *declared* action mapped to `None` — which `get_actions` treats as
  ungated (`common/admin.py:335-339`) — satisfies both "all capability ids come from the
  map" and "every declared action is capability-gated". → Q12-03.

## Axis coverage (all five)

**1. INVARIANTS.** The invariants these files must pin: (a) every ModelAdmin's four
model permissions derive from `CAPABILITY_ROLES` and nothing else — held for the 7 pinned
admins by construction and by the mirror, *not* held as a claim for the other 10
(Q12-01); (b) no role writes the TOTP register and no surface reads its secret — genuinely
pinned (`:236-298`, including the rendered changelist and the 403 on add/delete); (c) a
used TOTP code never verifies again — pinned sequentially only (Q12-09, KNOWN), and the
guard is genuinely exercised (`:181-194` fails if the comparison is removed); (d) every
structured audit value passes one sanitizing path and credential-named fields vanish
entirely rather than redacting — the best-pinned invariant in the flow (`:72-181`,
`:333-359`, including a real `log_mutation` write); (e) the audit row is written by the
same transaction as the effect — unproven (Q12-06); (f) unique single-spend of the trust
marker per browser — well pinned (`:987-1031`, `:1424-1443`).

**2. CORRECTNESS.** No wrong-value/status assertions found: the status codes match the
documented contract (403 for anonymous on JWT-only MFA surfaces, 401 uniform on bootstrap,
400 with `details.totp` for a challenge, 302 for the confirmed role change). Time-
sensitivity is handled honestly and hermetically — `code_after()` derives the next
acceptable counter from the persisted watermark instead of sleeping (`:103-114`), the trust
`grant()` helpers rewind the watermark explicitly and say why (`:850-864`, `:1355-1366`),
and the throttle window is frozen through the throttle's own `timer` hook (`:1695-1704`).
`assertLogs` is used only for the no-secret-in-the-log pin (`:189-195`, `:337-359`), not as
a substitute for asserting the row. One weak spot: `test_the_grant_lasts_the_env_driven_ttl`
asserts a one-minute-wide band around the TTL, which is fine, but `test_zero_days_is_the_kill_switch`
asserts `<= now`, so a negative `MFA_TRUST_DAYS` would also pass.

**3. SAST (as a test concern).** The security pins that exist are mutation-meaningful: the
secret is asserted absent from the changelist, the change page, the login page, `status`,
`setup`, `disable` and the model's `__str__` (`:269-298`, `:397-424`, `:535-538`), and the
sanitizer test reads the real model field names rather than typing them (`:106-115`), so it
cannot drift from the schema. The unmade pin is the credential *channel* (Q12-10) and the
cookie's `Secure` bit (Q12-07).

**4. ARCHITECTURE / SMELLS (test side).** `test_admin_rbac.py` is three concerns in one
file (registry/`ModelAdmin` introspection, live `e2e`-tagged admin UI flows, and an
`AuthHelperTokenBranchTests` block at `:694-703` that belongs to `common/testing.py`); the
`@tag("e2e")` class sits in the same module as the in-process unit pins, so the tag
selection cannot separate them at file granularity. `test_audit_structured.py` imports a
form helper from a sibling test module (Q12-08). Duplication is real but bounded:
`make_role_user` is re-defined verbatim in `test_admin_rbac.py:55-63` and
`test_audit_structured.py:42-50` (and again in `test_staff_roles_admin.py`).

**5. TEST SIDE.** Would these fail if the guard were deleted? — Yes for: the TOTP register
write denial, the secret-exclusion filter, the sanitizer, the trust-marker binding, the
replay comparison (sequentially), the admin-role full-function claim, and the throttle
budget. No for: the locking of the watermark write, the password channel, the `None`
action-capability value, the cookie's `Secure` flag, and the audit rollback. Over-mocking
is absent (the only `mock.patch` targets are `django.core.signing.time.time` for the
signature-expiry case and `ScopedRateThrottle.THROTTLE_RATES` for the throttle
differential, both hermetic and both used to prove a real branch).
