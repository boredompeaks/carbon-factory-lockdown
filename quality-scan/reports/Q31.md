## Direct answers to the brief

**Does the suite drive a failing `pg_dump` (exit 0 + empty file)?**
It drives a *non-zero-exit* `pg_dump` (`returncode=1/2`, `test_backup_db.py:286`, `:305`, `:345`, `:357`) — that class is covered four times. It **never** drives the exit-0-with-a-bad-body class: `BackupTestCase.pg_dump` writes `DUMP_BODY` on **every** invocation, unconditionally, before returning (`:146-149`). So a 0-byte, short, or truncated dump is **structurally unreachable** in this suite. That is exactly the class QC-082 (known, INFRA, Q25) names — and Q31's contribution is *why it stayed green*: the fake cannot express it.

**Same-second collision (QC-081)?**
One test claims it: `test_two_backups_in_the_same_second_do_not_overwrite_each_other` (`:425-434`). It is the weakest possible form — real wall clock, two sequential in-process calls, single assertion `len(self.dumps()) == 2`. It never pins `utc_stamp` (contrast `:447`, which does), never asserts the `-1` disambiguated name, and never asserts the first dump's bytes survived. It is green for the wrong reason if the two calls straddle a second boundary, and blind to the actual check-then-act race by construction. QC-081's mechanism is already CONFIRMED; the *test* is the new observation.

**Truncated dump?**
No postgres truncation test at all. The only truncation-ish coverage is `is_own_dump` ownership (`:637-639`, a 1-byte file is "not ours") — a retention-classification assertion, not a backup-integrity one. The sqlite path has a corrupt-source test (`:461-476`) and it is the one place in the file that uses a **real** `*.partial` glob (`:476`).

**Retention deletion?**
Genuinely well covered — the strongest part of the file. `:502-699` pins newest-N, the shared sqlite/postgres pool, prefix-borrowing files, wrong-width stamps, a directory wearing a dump's name, a hand-taken plain-SQL dump that borrowed the exact scheme, `keep<1`, and the env knob. These tests would survive a mutation of the deletion loop's guards in the right direction (they fail if `is_own_dump` or `STAMP_GLOBS` are widened), and they mostly take **directories**, not mocked mocks. No finding here.

**Does it assert the backup file exists and is nonempty, or only that the command printed?**
Both, on the happy path: `:229` asserts `written.read_bytes() == DUMP_BODY` (15 bytes, so non-empty) and `:226` asserts exactly one file exists; the sqlite test reads rows back (`:412-414`) and asserts the source is byte-identical (`:415`). Error-path tests assert message substrings only (`:299-303`, `:328-343`), which is a defensible message contract. The gap is not "file vs printed" — it is that **nothing asserts the file is *valid***, and the fake cannot produce an invalid one.

**Restore equality beyond counts (QC-185)?**
Nothing in `test_backup_db.py` round-trips a produced `.dump` at all (it cannot — no `pg_restore`). In `test_restore_drill.py` the **only** negative case is `_corrupt_restored_copy`, which deletes one row (`restore_drill.py:261-267`) so the failure is a **count delta**; `_verify` compares `count()` per model (`:280-294`). So the failure mode of a truncated dump — same row count, wrong field values, or missing auto-created M2M — is never simulated. Native QC-107 / QC-185 are known; the *reason they stayed green* is that the single seeded corruption is a count change.

## Backup invariants with NO test

1. A produced dump is **non-empty / correctly signed** — unenforceable with the current fake (QC-082 known).
2. A dump that fails **after** `os.replace` (or a kill mid-`pg_dump`) leaves no misleading file — only the in-process `finally` path is exercised.
3. **Concurrent** same-second runs (QC-081) — sequential only.
4. A **failed** dump does not prune/delete existing good dumps (`:357-370`).
5. Dump **file mode** — `open(partial,"wb")` (`:476`) and `sqlite3.connect(partial)` (`:575`) never `chmod 0600`; the suite chmods only its docker stub (`:944`). A full commerce-DB dump (customer PII) lands under the process umask (0644 on a default `0022` container). No test asserts permissions.
6. **Child-env authority** — `_pg_environment` copies `dict(os.environ)` and overrides only when the config value is truthy (`:527-541`), so an inherited `PGHOST`/`PGDATABASE`/`PGPASSWORD`/`PGSSLMODE` survives when the settings entry is empty: the dump can target a *different* database than the configured one, and `:272-284` cannot see it because the test process exports no `PG*`.
7. **Orphan `.partial` accumulation** — `prune`'s glob needs the exact `.dump`/`.sqlite3` suffix (`:250-256`), so `<stamp>.dump.partial` from a hard kill, and any truncated stamped dump (`is_own_dump` → False), are unreachable by retention forever. No test seeds one.
8. The sqlite dump is a **consistent** snapshot **while a writer is active** — the invariant the online-backup API exists for. Only source-immutability is asserted (`:415`).
9. Assertion of the command's **process exit code** — `:21-23` claims "its exit status and its output" are asserted; only `CommandError` is observed. The `returncode == 1` assertions (`:1029`) belong to `scripts/backup.sh`.
