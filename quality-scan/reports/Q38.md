## The brief's three questions, answered first

1. **Does the file prove the whole loop (request → token → reset → old sessions dead → login with new password)?**
   It proves **request → token → weak-rejected → reset → old *password* rejected → new *password* accepted → link reuse rejected**. It does **not** prove **old sessions dead**: no session is ever created before the reset (`register_and_verify` at `:57` registers and verifies only — `common/testing.py:211-230` never logs in), so the "sessions die with the credential" half of `views.py:773-796` is exercised by nothing in this file. The one session it does create (`:89`) is never used for a request (`:91` is a truthiness check on a value the helper derived from the same response). → Q38-04, Q38-05.
2. **Does it assert the reset token is single-use and expires (QC-085)?**
   Single-use: **yes, but weakly** — `:94-99` re-posts the burnt link and asserts `400`, and never asserts that the password is *unchanged* after that 400. Expiry: **no, nowhere in the repo** — `PASSWORD_RESET_TIMEOUT` is never set or overridden in any test (it appears only in comments and Django's `global_settings`), no test ages a token, and the repo has no `freezegun`. → Q38-02, Q38-03.
3. **Does it assert the old refresh token is blacklisted (QC-086)?**
   **No.** See 1. The sequential pin that exists (`accounts/tests.py:1294-1305`) mints a refresh token with `RefreshToken.for_user(user)` rather than by logging in, so nothing in the repo carries a *login-issued, cookie-borne* refresh token across a reset. That is an extension of Q30:71's known row, and it is where QC-086's race lives. → Q38-04 (KNOWN-adjacent).

## Findings (severity order)

### Q38-01 | P1 / CRITICAL | CODE | `backend/accounts/views.py:665` (with `:636-642`)
**`resend-verification` + `verify-email` hand a staff-disabled account its login back: one boolean (`is_active`) means both "never verified" and "disabled by staff", so the staff off-switch is advisory and the account owner can undo it in two unauthenticated requests.**

`resend_verification` selects `User.objects.filter(email__iexact=email, is_active=False).first()` (`:665`) and mints a **fresh** `default_token_generator` token for whoever matches. `verify_email` then does `if not user.is_active: user.is_active = True; user.save(update_fields=["is_active"])` (`:636-642`). Neither endpoint asks *why* the row is inactive, and there is no second field that could answer: `accounts/models.py` defines only `TOTPDevice` (`:16`) and `Address` (`:70`) — the user model is stock `django.contrib.auth.models.User` — and registration creates the row with `is_active=False` (`accounts/serializers.py:44-48`), the same value staff write when they disable an account (`accounts/admin.py:286-302` exposes `is_active` in the change form, `:308`/`:312` in list display/filter).

So the deactivation control the whole repo documents is reversible by its subject, without a token, a password or staff involvement: `POST /api/accounts/resend-verification/ {"email": <own>}` → read the fresh link from the inbox → `POST /api/accounts/verify-email/ {uid, token}` → `is_active=True` → login succeeds. The `recovery` scope throttles the pair per IP (`:659`, `:622`), which bounds mail volume, not the escalation. It also means a user who was *never* verified and a user *disabled for abuse* are indistinguishable to the login gate.

**Why this is Q38's finding and not Q30's:** this file is where the invariant is written down. `tests/test_e2e_auth_recovery.py:101-128` asserts exactly "an account disabled by staff (`is_active=False`) must never obtain a working login", and pins it for the **reset** path (`:123-126`: password changes, `is_active` stays `False`, login `401`). The sibling path that *does* restore the login — and the one that does so by design rather than by accident — has no test: `accounts/tests.py:316-331` activates a never-verified user, `:345-378` covers bad and cross-user tokens, and no case anywhere disables an account and then presents a verification link. Grep of `docs/vulnerabilities.md` and `docs/audit.md` for `resend|verify-email|deactivat` returns nothing, and V-17 records only the "replay into verify-email is a no-op" case — which is not this: for an inactive row it is not a no-op, it is the write. Not Q30-01 (that is cross-purpose tokens), not Q30's "inactive accounts cannot obtain tokens" (that invariant holds *while* inactive, and is defeated by making the row active again).

Fix route: FIX-NOW. Separate the two states (an `email_verified` field, or refuse `resend_verification` for accounts staff disabled, or have `verify_email` only activate rows with no prior activation and no staff flag) and add the negative test to the e2e file where its sibling already lives. Confidence **H** (mechanism H on source read; the only inference is that the deployment disables via the admin's `is_active`, which `accounts/admin.py:293` shows is the exposed switch). No DB touched.

### Q38-02 | P3 / LOW | CODE (test) | `backend/tests/test_e2e_auth_recovery.py:99`
**The single-use assertion accepts any `400` and never checks the side effect, so a regression that writes the new password *and* returns 400 would pass — the unit test it duplicates asserts the thing the e2e dropped.**

`:94-99` re-posts the used link with `"An0ther-Pass-99!"` and asserts only `status_code == 400`. Two things are missing that `accounts/tests.py:611-618` does assert: the refusal *message* (`:589` pins `"invalid or expired" in res.data["error"]`) and, more importantly, `user.check_password("N3w-Passphrase-99")` still true after the replay (`:617-618`). Without the password check, a `reset_password` that moved `set_password`/`save` above `check_token` (`views.py:759` vs `:773-775`) and then returned the 400 would keep this test green while every burnt link became a live credential-changing one. The chosen password is strong, so the 400 can only come from the link check *today* — the assertion is not wrong, it is non-distinguishing, and it is the weakest assertion in a file whose whole subject is credential recovery.

Fix route: FOLD-INTO-NEXT — assert `"invalid or expired" in res.data["error"]` and `user.refresh_from_db(); user.check_password("Br4nd-N3w-Pass!")`.

### Q38-03 | P3 / LOW | CODE (test) | `backend/tests/test_e2e_auth_recovery.py:55`
**Reset-token expiry has no test in the repository: `PASSWORD_RESET_TIMEOUT` is never overridden, nothing ages a token, and the e2e's "whole loop" therefore proves a 3-day credential window it never measures.**

`:55-99` requests, extracts, rejects a weak password, accepts a strong one and replays — all within one wall-clock instant. The only bound on link lifetime is Django's default, and `config/settings.py:607` mentions it solely in a comment ("Django's own default, 3 days") while never setting it. Repo-wide grep for `PASSWORD_RESET_TIMEOUT` finds only `config/settings.py:607`, two `common/notifications.py` comments/uses (`:394`, `:1153`), `accounts/models.py:325`, the outbox purge command and two outbox-worker tests that reason *about* the comment; the setting is never assigned and never `override_settings`-ed in a test. There is no `freezegun`/`freeze_time` anywhere in `backend/` (grep: zero hits). So "expired link → 400" is pinned only by the same message text as "garbage link → 400" (`accounts/tests.py:345-362` uses `"wrong-token"` and `""`, not an aged token), and the expiry branch of `check_token` is untested in both flows — which matters more than usual because the reset token is the *only* credential in the flow and its window is measured in days.

Fix route: FOLD-INTO-NEXT — `override_settings(PASSWORD_RESET_TIMEOUT=0)` (or a 1-second timeout plus a monkeypatched clock) and assert the same 400, in both `PasswordResetFlowTests` and `PasswordResetTests`.

### Q38-04 | P3 / LOW | CODE (test) | `backend/tests/test_e2e_auth_recovery.py:57`
**No session exists when the password changes, so the file's own title ("password reset end-to-end") omits the half of `reset_password` that Q30-02/QC-086 is about, and the only session-level pin in the repo uses a directly minted token instead of a login.**

`register_and_verify` (`common/testing.py:211-230`) registers and verifies — it does not log in — and the first `api_login` in this class is at `:87`, *after* the reset. `reset_password` (`views.py:773-796`) does three things in one transaction: set the password, blacklist every outstanding refresh token, write the audit row. The e2e pins the first and nothing else; the third is pinned elsewhere (`tests/test_audit_trail.py:435-454`), and the second only by `accounts/tests.py:1294-1305`, which creates its session with `RefreshToken.for_user(user)` rather than by logging in — so no test anywhere proves that a token the login endpoint actually issued (and set in the cookie at `views.py:198-206`) stops working after a reset. That is the exact contract a user experiences ("sign out my other devices"), and it is one `fresh_client()` + one `token/refresh/` replay away:

```
old = self.fresh_client(); old.post("/api/accounts/login/", {...})   # capture refresh cookie
reset ...
old.post("/api/accounts/token/refresh/", {})                          # assert 401 "blacklisted"
```

`assertIn("blacklisted", replay.data["error"])` is already the repo's own idiom for this (`accounts/tests.py:1305`), so the assertion shape exists and is simply not used across a real login. Delta on Q30:71, which named only the *lock* gap: the sequential behaviour is pinned, but never through a login-issued credential.

Fix route: FOLD-INTO-NEXT.

### Q38-05 | P3 / LOW | CODE (test) | `backend/tests/test_e2e_auth_recovery.py:91`
**`assertTrue(access)` is derived from the same response it is checking, and the access token minted at `:89` is never used — the "new credential works" half ends at a truthiness check on `res.data["access"]`.**

`api_login` returns `token = res.data.get("access") if res.status_code == 200 else None` (`common/testing.py:205-209`), so after `assertEqual(res.status_code, 200)` at `:90`, `assertTrue(access)` at `:91` can only fail if the 200 body lacks a non-empty `access` key — it cannot fail because the token is *unusable*. Contrast `:44-49`, where the same shape is immediately followed by `GET /api/orders/` returning 200 with `[]`, which does prove the token authenticates and is scoped to an empty account. The reset flow has no equivalent: nothing between `:89` and the end of the method (`:99`) carries `access` anywhere, so a login that minted a structurally valid but unauthorised token (wrong user in the claim, e.g. a `token_blacklist`/`JWTAuthentication` regression) stays green here. The strong version is already written nine lines up.

Fix route: FOLD-INTO-NEXT — after `:91`, `self.client.get("/api/orders/")` and assert 200, and (the load-bearing half) assert the *identity*: `self.assertEqual(self.client.get("/api/accounts/mfa/status/").status_code, 200)` or any endpoint that names the caller.
