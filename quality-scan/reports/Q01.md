### Q01-01 | P2 | HIGH | CODE | `orders/management/commands/seed_demo.py:47` (also `:75-89`, `:180-192`) | H | NEXT-BUILD

`seed_demo` creates one `is_staff=True` account per staff role — including `admin` and `superadmin`, which hold `staff.manage`/`settings.manage`/`platform.configure` (`common/roles.py:125-131`) — with a static, printed password (`DEMO_PASSWORD = "demo-account"`, `:47`), and has **no test-database guard at all**.

Evidence: `:80-89` loops `STAFF_ROLES` calling `User.objects.create_user(username=f"demo-{role}", password=DEMO_PASSWORD, is_staff=True)` then `u.groups.add(Group(name=role))`; `:180-192` `handle()` dispatches straight to `seed()`/`clean()` with no acknowledgement flag and no environment check. Its sibling `seed_e2e` — added later, for the same class of fixture — refuses without `--i-know-this-is-a-test-db` **and** a second independent check of `settings.DATABASES` (`seed_e2e.py:361-377`), and its module docstring says the test-only credential "must never exist outside this local test DB". `docs/red-team/T1-report.md:81` records that `seed_demo` was requested to be run on the owner's UAT box; the same report records `demo-*` logins answering 401 there, i.e. the command simply had not been run — running it would have created seven role-bearing staff logins, two of them top-tier, on a box that was being attacked over HTTP. The only protection against a privileged-account backdoor here is operator discipline; `seed_e2e` demonstrates the project already decided that is not enough. Pin-adjacent: `backend/tests/test_seed_demo.py` asserts the demo customer can `authenticate()` with the printed password, so the behaviour is deliberate, not accidental — deliberate is not the same as safe.

Escalate to P1 if this command is ever run against a reachable deployment: the credential is in the repo, so the window between run and cleanup is full superadmin takeover.

### Q01-02 | P2 | MEDIUM | CODE | `orders/views/refund.py:86` (also `:164-165`, `:176-177`) | H | NEXT-BUILD

The refund endpoint is the one money surface in this repo that returns `Decimal` objects straight into a `Response`, so its money reaches the wire as JSON **floats**, not the house 2-dp strings.

Evidence:
- `_refund_payload` (`:84-93`) returns `"amount": refund.amount` (a `Decimal`); the response adds `"refunded_total": Refund.refunded_total(...)` and `"refundable_remaining": receipt.order.refundable_remaining` (`:164-165` replay branch, `:176-177` created branch) — also `Decimal`s.
- DRF's renderer encodes `Decimal` as `float`: probe of the installed library —
  `python -B -c "...json.dumps({'refunded_total': Decimal('900.00'), 'amount': Decimal('300.00')}, cls=rest_framework.utils.encoders.JSONEncoder)"` → `{"refunded_total": 900.0, "amount": 300.0}` (Django 6.1.1 / DRF encoders `default()`: `elif isinstance(obj, decimal.Decimal): return float(obj)`).
- `config/settings.py` has no `COERCE_DECIMAL_TO_STRING` override and no custom renderer (grep for `RENDERER|COERCE_DECIMAL|DECIMAL` → no matches), so nothing intercepts it.
- The module docstring states the opposite as fact: "Money stays a Decimal here and the renderer stringifies it, exactly as OrderSerializer does with the order's amounts" (`:80-83`). `OrderSerializer` does **not** rely on the renderer — it uses `MoneyField` → `money_string` (`serializers.py:8-31`), which exists precisely because "DRF's JSON renderer encodes a bare Decimal as a float, dropping the trailing zero (`1234.50` -> `1234.5`) and handing downstream code a binary amount to round".

Consequence: a finance operator reconciling a refund reads `900.0`/`899.98`-shaped binary amounts from this endpoint while every order and listing read returns `"900.00"` strings — the exact drift F-11 was raised for, on the money-out surface. No test can see it (see the out-of-scope handoff on `tests_refunds.py`). Breaks `conventions.md:15` and the `money_string` doctrine.

### Q01-03 | P2 | MEDIUM | CODE | `orders/views/admin.py:180` (gate) with `orders/state.py:68-72`, `orders/models.py:527-529` | H | NEXT-BUILD

`admin_order_fulfill` can move an **unpaid** order `pending -> confirmed` and leave it in a state both exit paths refuse, because preconditions are registered for `shipped` only.

Evidence:
- `ADMIN_FULFILMENT_NEXT` maps `"pending": "confirmed"` (`state.py:68-72`) and `transition_allowed("pending","confirmed")` is true (`ALLOWED_TRANSITIONS`, `:49-55`).
- `precondition_failures(order, target)` is called at `admin.py:197`; the only registered precondition set is `register_transition_preconditions("shipped", ...)` (`models.py:527-529`), so for `target == "confirmed"` the list is empty by construction — `payment_status` is never consulted.
- The write at `:215-217` sets `status="confirmed"` and `fulfilment_status=unfulfilment`, leaving `payment_status="pending"` — the pair `LEGACY_STATUS_DIMENSIONS` declares impossible (`models.py`/`state.py:197-203`: `confirmed -> ("captured","unfulfilled")`).
- From there every operator exit is closed: `admin_order_cancel` refuses (`ALLOWED_TRANSITIONS["confirmed"] == {"shipped"}` → 409 "A paid order cannot be cancelled — issue a refund instead", `admin.py:281-290`), and `issue_refund` refuses because `payment_transition_allowed("pending", "refunded")` is false and `razorpay_payment_id` is empty (`refunds.py:239-254`). `shipped` is blocked by `_require_captured_payment` (`models.py:493-516`). The order is a dead end that reads as "confirmed" (paid) to the customer, and its stock holds stay ACTIVE until the TTL sweep.
- A test pins the first half of this and asserts nothing about the payment dimension: `orders/tests.py:2380` `test_fulfill_advances_pending_to_confirmed_and_audits` checks `status == "confirmed"` and the LogEntry only — a green pin over the defect (the recorded bias trap: green tests hiding a real defect).

This is only correct for a cash-on-delivery order, and checkout cannot create one today (`models.py:204-217`: "No checkout input exists yet"), so every reachable row it affects is prepaid.

### Q01-04 | P2 | MEDIUM | CODE | `orders/management/commands/seed_demo.py:143-144` | H | NEXT-BUILD

`seed_demo` writes two values the state machine does not declare — `status="paid"` and `payment_status="paid"` — and those rows 500 the Django admin change form.

Evidence:
- `state.py:36-42` declares `pending/confirmed/shipped/delivered/cancelled`; `:130-137` declares `pending/authorized/captured/failed/partially_refunded/refunded`. `"paid"` is in neither, and `choices` is not enforced by either engine, so the insert succeeds.
- Crash surface (out of scope, named for the reviewer): `orders/admin.py:494` does a bare `ALLOWED_TRANSITIONS[old]` with `old == "paid"` → `KeyError` → 500 as soon as an operator saves one of these orders from the change form (`transition_allowed("paid", <whatever the select submits>)` is false because `ALLOWED_TRANSITIONS.get("paid", set())` is empty, so line 494 runs); `orders/admin.py:534` `fulfilment_for_status(obj.status)` is a second `KeyError` on the same value.
- The status select cannot even represent the row: the form renders the five declared choices, none matching `"paid"`, so the browser submits `"pending"` and the save is refused/aborts.
- Also unqueryable by the dimension: `payment_for_status`/`fulfilment_for_status` raise `KeyError` on `"paid"` (`state.py:206-213`), so any future caller that maps this row's status crashes.
- Pinned by `backend/tests/test_seed_demo.py:103` (`o.status == "paid" and o.payment_status == "paid"`), so the pin enshrines the defect.

The command's own docstring calls this set "the canonical demo state" / "known-state entry point" — a row outside the machine's vocabulary is the opposite of a known state, and it is the fixture red-team/load runs start from.

### Q01-05 | P2 | MEDIUM | CODE | `orders/views/payment.py:98` and `:306-308` | H | NEXT-BUILD

A non-numeric `order_id` in either payment request body raises an uncaught `ValueError`/`TypeError` → 500 instead of the endpoint's own 400/404.

Evidence: both lookups are `Order.objects.get(id=order_id, ...)` (`:98`) and `Order.objects.select_for_update().get(id=order_id, ...)` (`:306-308`) where `order_id` is attacker-controlled JSON (`:90`, `:298`); only `Order.DoesNotExist` is caught (`:100`, `:309`). Django's `IntegerField.get_prep_value` re-raises the conversion error — probe of installed Django 6.1.1:
`try: return int(value) except (TypeError, ValueError) as e: raise e.__class__("Field '%s' expected a number but got %r." % (self.name, value)) from e`.
So `{"order_id": "abc"}` and `{"order_id": [1]}` are 500s on both endpoints. The sibling malformed-input class was already fixed and documented in this very module (`_object_body`, `:68-80`, "a 500 on both payment endpoints (F7-B1)"), so this is the same defect shape one layer deeper, and it is untested (no `order_id`-shape negative test exists; grep for a non-numeric `order_id` in `orders/tests.py` → none). URL-borne ids are safe (`orders/urls.py:25,32` use `<int:order_id>`), so the body is the only entry.

## 3. Axis notes (what I checked and found clean)

**Correctness.** `_object_body` correctly routes array/scalar/null bodies into the missing-key 400 on both payment views and on the refund seam (QueryDict is a `dict` subclass, so form posts still read). `create_payment`'s intent persistence uses the unique `razorpay_order_id` as the concurrency authority with a bounded 3-attempt loop that re-reads under `select_for_update` and re-raises on exhaustion (`:148-173`) — no check-then-act. `verify_payment`'s "already processed" branch is keyed on both status and `razorpay_payment_id`, and `razorpay_payment_id` is unique, so a replay cannot write twice. Lock acquisition is ordered `Order -> products(ascending id) -> Coupon` in both the view and `commit_order_sale`, so the deadlock the comment describes is actually closed. `refund.py` refuses an over-balance, non-finite, non-numeric or non-positive amount *before* any write, parsing via `Decimal(str(value))` so a JSON number never becomes float money (`refunds.py:260-283`). `_history_page_size` handles `TypeError/ValueError` and clamps both ends (`order.py:35-45`), and both lists sort `("-created_at","-id")` for a total order across pages. No `float`, no timezone-naive comparison, no swallowed exception in the scoped files (the one broad `except Exception` in `refund.py` belongs to the gateway seam and re-raises a typed error).

**SAST.** Every scoped view carries a declarative gate (`IsAuthenticated`, `HasOrdersRead/Fulfill/Cancel`, `HasRefundsCreate`); no inline `request.user.is_staff` in the flow. Ownership is part of every customer lookup (uniform 404 for foreign and unknown alike — no existence oracle). `RefundRequestSerializer` binds `order`/`requester` server-side and marks every staff/timestamp field read-only, so no mass assignment; `items` is a `ListField` of positive ints validated against the addressed order. No raw SQL, no `eval`/`pickle`, no request data in an `ordering=` or a file path except the operator-only `--mapping` CLI arg. Log lines carry order/product/coupon ids, never addresses, phone numbers or card data. No secrets in the scoped code; the credential-bearing code (`settings.RAZORPAY_*`) is read, never written.

**Architecture.** Layering is mostly right: money decisions live in `orders/refunds.py`, the machine in `orders/state.py`, and `orders/views/admin.py` only consumes them. Exceptions worth noting but not filing: `_may_fulfil` (`admin.py:116-139`) is a second authorization layer inside a view rather than a permission class (it uses capabilities, not `is_staff`, and its docstring justifies the two-question split); `orders/views/__init__.py` is a 217-line re-export shim whose `__all__` publishes private helpers and two module objects purely so the test suite's patch targets keep resolving — a test-shaped public surface, documented as such, and the one place a rename would break silently. `_object_body` is duplicated verbatim in `payment.py` and `refund.py` (and in `cart.views`), each copy carrying a paragraph explaining that importing the shared one would create an order-dependent cycle — a real cycle, so duplication is the lesser evil, but it is three copies to keep in step.

**Test side (in-scope file `tests_remint_order_numbers.py`).** Assertions are hand-written literals, not recomputed oracles (`CONFORMING`, `LEGACY_SEQUENTIAL`, `FRESH` at `:29-33`), the title claim is honoured. The dry-run test proves non-mutation by making the generator raise (`:69-73`) rather than by inspecting output alone; the collision-retry test pins `call_count == 2`; the exhausted-retry test pins the *outcome* ("nothing was written") and verifies the whole repair rolls back (`:173-189`); the concurrent-remint test simulates the other writer with a real DB update (`:191-206`); the unique-constraint test pins the database authority rather than a comment (`:208-220`); the import-identity test pins the generator and the attempt bound to `checkout`'s (`:222-228`). Isolation is fine (TestCase, `tempfile.mkdtemp` + `addCleanup(rmtree)`, no clock or cache dependence). Weaknesses: Q01-11 (a guard pinned only by direct call) and Q01-10 (the mapping write's failure mode untested). Missing cases in this file: no `--mapping` I/O failure, no assertion that the reported count matches the rows actually written, no pin that `legacy_rows()` is pk-ordered (the command's output order depends on it).

**Invariants with no test at all anywhere I could find:** I3 (a post-capture 409 refunds or reconciles — only `tests.py:1498` documents the gap by name), the wire-level money shape of the refund response (I1 on this endpoint), and Q01-05/Q01-03's payment-dimension consequences (both pinned only up to the point where the defect begins).
