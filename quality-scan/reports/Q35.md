## Findings

### Q35-01 | P2 HIGH | CODE | `expire_reservations.py:77,86,98-99` — the ledger row describes the snapshot, not the flipped set

`_expire_stale` builds `rows = by_product[product_id]` from the **pre-transaction
snapshot** (`:61-66`), runs the conditional UPDATE (`:79-83`) which may flip only a
**subset**, then gates the ledger write on mere truthiness (`if flipped:`, `:85`) and
passes the whole snapshot list:

```python
79  flipped = StockReservation.objects.filter(
80      pk__in=[row["id"] for row in rows], status=ACTIVE, expires_at__lte=now,
83  ).update(status=StockReservation.Status.EXPIRED)
84  released += flipped
85  if flipped:
86      self._record_release(product, rows)      # <-- rows, not the flipped ids
```

`_record_release` then writes `refs` and `units` from **every** snapshot row
(`:98-99`), so a hold that the UPDATE refused (re-armed by a checkout retry, or
released/converted by a concurrent writer in the window) is still named in the note
and still counted in the unit total. The ledger row is the [R-12.9] *requirement*,
so this is the audit record overstating what happened: "orders #12, #13: 5 unit(s)
back to available-to-sell" when only #12's units ever left the pool.

Precondition (fully reachable, and the exact shape the existing race test builds):
two lapsed holds on the **same** product, one of them re-armed between snapshot and
flip. `tests/test_expire_reservations.py:161-205` builds that race on **two
different products** (`raced` / `clean`), so `flipped` for the raced product is 0
and the ledger row is never written for it — the assertion
`StockMovement.objects.count() == 1` passes for a reason that does not test the
note. Same product + one surviving row → `flipped == 1` → row written naming the
survivor.

Second defect in the same row: `note` is truncated to 200 chars (`:105-109`) but
`units` keeps summing **all** snapshot rows (`:99`), so on a product with ~25+
holds the note cites a truncated subset of order ids against a total that covers
the untruncated set — internally inconsistent even when every row did flip.

Fix shape: capture `flipped_ids = set(...update()...)` is not available from
`.update()`; use `pk__in` + a returned-rows UPDATE (e.g. `filter(...).values_list`
before/after under the product lock, or re-read the rows that are now EXPIRED and
`updated_at >= t0` — simplest correct: re-select `status=EXPIRED AND pk__in=ids`
after the UPDATE and build `refs`/`units` from *that* result set, inside the same
atomic block).

Axis 1 invariant broken: "the movement row IS the audit record" — the row must
describe the mutation that occurred, not the candidates read before it.
Test that would not catch it: all of `tests/test_expire_reservations.py` (see
Q35-10).

### Q35-02 | P2 MEDIUM | CODE | `views.py:93-94` vs `:96-101` — the `?ordering=` branch is not a total order

```python
93  if ordering in allowed_ordering:
94      products_data = products_data.order_by(ordering)     # single, non-unique field
```

`price`, `name` and `created_at` are all non-unique, and none of the six whitelisted
values is a unique field. The `-id` tiebreaker exists only in the `else` branch
(`:101`), and the comment at `:96-101` claims totality ("identical requests always
partition the catalogue into identical pages") for the default branch only. So a
catalogue with two products at the same price served as `/?ordering=price&page=1`
then `page=2` has an **arbitrary** tie order on each page: the same row can appear
on both pages, and a row can appear on neither. That is the F-12/V-20 defect
reopened on the branch F-12 did not cover — a new mechanism, not a re-report.

Frontend impact: the storefront price/name sort buttons can silently drop or
duplicate catalogue items between pages. No error surface.

Fix: `order_by(ordering, "id")` (or `"-id"`) for every whitelisted value.

Test side: `tests.py:164-183` exercises `-price`/`price` over exactly three
products with three **distinct** prices and a `-name`/`name` sort over distinct
names — no tied sort key is ever created, so the guard (`-id`) could be deleted
from the default branch and `test_ordering_by_price_and_name` would still pass.
`tests.py:255-273` pins the tiebreak only for the default branch.

### Q35-03 | P2 MEDIUM | CODE | `expire_reservations.py:61-83` — unbounded snapshot, one transaction, one `pk__in`

Three bounds are missing:

1. `stale = list(...)` (`:61-66`) reads **every** lapsed hold into memory with no
   `.limit()`/`iterator()` chunking. A backlog is read in one query and held as a
   Python list.
2. All of it executes inside **one** `transaction.atomic()` (`:75-87`), holding a
   `select_for_update` row lock on every affected product for the whole sweep.
   Products are exactly the rows `commit_order_sale` locks
   (`orders/inventory.py:152-157`) — so a large sweep parks checkout traffic
   behind it for the sweep's full duration. There is no `nowait`/`skip_locked`
   (`:78`), so waiters block indefinitely rather than failing fast.
3. `pk__in=[row["id"] for row in rows]` (`:80`) puts the **entire** per-product id
   list into one statement. `StockReservation` is unique on `(order, product)`
   (`models.py:691-695`), so one popular product can legitimately accumulate tens
   of thousands of lapsed holds. **Source-read reasoning, not measured:** both
   engines cap bind parameters (PostgreSQL's extended protocol 16-bit param count
   = 65535; SQLite `SQLITE_MAX_VARIABLE_NUMBER` 32766 / 999 on older builds), and
   Django does not chunk `__in` lists — past the cap the command raises instead of
   sweeping. Confidence M for the exact ceiling, H that no cap/batch exists.

Amplifier: no self-overlap guard (brief question). A sweep longer than the beat
period (`settings.py:783-792`) starts a second instance; both walk products in the
same ascending order (so no deadlock), but the second blocks on the first's locks
for minutes and the two together hold product locks roughly twice as long.

Fix shape: `--limit`/`BATCH_SIZE` (e.g. 500 ids per transaction), per-batch atomic
commits, and a duplicate-run guard (advisory lock or a "sweep in progress" row).

### Q35-04 | P2 MEDIUM | CODE | `views.py:261-282` — DELETE has no referential guard: it silently destroys the stock ledger and strands pending orders

```python
261  elif request.method == "DELETE":
262      with transaction.atomic():
268          log_api_action(request, product, DELETION, "Deleted via API.")
273          log_mutation(... CATALOGUE_DELETED ...)
280          product.delete()
```

`products.delete()` fires two cascades that the view never inspects:

- `StockMovement.product` is `on_delete=models.CASCADE`
  (`products/models.py:473-477`) — the hard delete **erases every SALE /
  RESTOCK / CORRECTION row for that product**, i.e. the [6.5.17] audit ledger for
  its entire sales history, while the `AuditEvent` this view writes survives and
  still describes only the deletion.
- `OrderItem.product` is `on_delete=models.SET_NULL, null=True`
  (`orders/models.py:443`) — every historical line loses its product, and any
  *pending* order containing the product becomes permanently unsellable:
  `commit_order_sale` re-reads items, finds `product is None` for the line and
  raises `StockUnavailable(..., available=0)` (`orders/inventory.py:174-181`) —
  the customer paid, and the capture can never commit on either writer.
- `StockReservation.product` is CASCADE (`models.py:647-651`) — in-flight holds
  vanish instead of being released.

No 409, no confirmation, no "delist instead" redirect. A staff `products.write`
holder with one DELETE request erases the ledger. The code's stated rationale
(`models.py:66-69`, "destroying history is what `delete` is for") covers the
*product* row, not the movement ledger that other flows are required to keep.

Fix shape: refuse (409) when `product.stock_movements.exists()` or a pending
`OrderItem` references it, and steer to the delist path (`is_active=False`, the
`products.publish` admin action) — which the MERCHANT-DELIST design already owns.

Confidence M: the cascade is measured from source, the "intended" reading rests on
the model comment.

### Q35-05 | P3 LOW | CODE | `views.py:324,361` — a non-integer `product_id` is a 500, and a float silently retargets

```python
324  product_id = body.get("product_id")
341  if not isinstance(delta, int) or isinstance(delta, bool): (delta IS guarded)
360  try:
361      product = products.objects.get(id=product_id)
362  except products.DoesNotExist:
```

`_object_body` (`:294-307`) guarantees a dict, so `.get` is safe — but the value is
never type-checked, unlike `delta` (`:341`), which is guarded for exactly this
class of input. `id="abc"` (or `id=[1]`, or `id={"a":1}`) reaches
`Field.get_prep_value` → `int()` → **ValueError**, which `except DoesNotExist` does
not catch → unhandled 500 on a staff endpoint whose every other validation branch
returns 400. `id=1.9` is worse in the quiet direction: `int(1.9) == 1`, so the
adjustment lands on product 1 while the caller named something else.

Reachable only behind `HasInventoryAdjust`, so no privilege boundary is crossed;
the blast radius is a 500 + a wrong-target write.

### Q35-06 | P3 LOW | CODE | `views.py:327` — `note` is unvalidated: Postgres 500 / silent on SQLite

```python
327  note = body.get("note", "")
```

Every other body key is checked (`:329-358`); `note` is passed straight into
`StockMovement.note`, which is `CharField(max_length=200)` (`models.py:481`).
A 5,000-character note (or a dict, coerced by `get_prep_value`) raises
`DataError`/`StringDataTruncation` on PostgreSQL — a 500 — while SQLite stores it
unbounded, so the failure is engine-shaped and invisible to a SQLite-only test run.
Note also round-trips into the response (`:383`).

Contrast: the sweep truncates its own note with `[:200]` (`expire_reservations.py:109`),
so the two ledger writers enforce different contracts for the same column.

### Q35-07 | P3 LOW | CODE | `expire_reservations.py:78` — one vanished product aborts the whole sweep

The snapshot is read **outside** the transaction (`:61-66`); `:78` then does
`products.objects.select_for_update().get(pk=product_id)` with no `DoesNotExist`
handling. A product deleted between snapshot and lock makes the command raise
inside `transaction.atomic()` (`:75`), which rolls back **every flip already made
in this run** — so one bad row in the batch un-does the releases for every product
before it, and the cron/beat run ends with a traceback and zero net progress. The
command's own `handle` (`:37-45`) has no per-product isolation.

Fix shape: skip the product id (`filter(...).first()` / catch `DoesNotExist`), or
commit per product rather than per run.

### Q35-08 | P3 LOW | CODE | `views.py:374` — the response re-queries instead of returning the movement it created

```python
368      product.adjust_stock(request.user, delta, reason, note)
374      movement = product.stock_movements.first()
```

`adjust_stock` commits its own atomic block (`models.py:185`) and returns `None`,
releasing the product lock; `.first()` then reads again. Between the commit and
this read a second adjustment on the same product can lock, insert and commit, so
the response can report *another* operator's `delta`/`stock_after`/`note` as the
result of *this* request. `.first()` also relies on `StockMovement.Meta.ordering =
("-created_at",)` (`models.py:492`) with no pk tiebreak.

Same root cause as Q35-01's family (report from a re-read rather than from the
write), one layer up. Fix: have `adjust_stock` return the created movement.

### Q35-09 | P3 LOW | DOC-ONLY | `views.py:211-215` vs `serializers.py:14-25` — the documented relist workflow does not exist on this surface

The comment justifies serving delisted rows to PUT/PATCH/DELETE:

> "…and 'delist → fix the price → relist' is the natural staff workflow — hiding the
> row from its own edit path would force a relist just to change a number."

`ProductSerializer.fields` (`serializers.py:14-25`) contains no `is_active`, so
**this API cannot delist or relist anything**; both are Django-admin actions gated
by a different capability (`delist_products`/`relist_products`, `products.publish`,
`tests/test_admin_rbac.py:360-370`). The reachable workflow is "fix the price
(here) → relist (in admin)", and the write gate here is `products.write`, not the
`products.publish` that owns the visibility decision. The read-inclusivity itself
is defensible and the 404-on-GET path (`:216-219`) is correct; the *reason given*
describes a capability the flow does not have, which is how a future reader will
conclude the API is the delist surface.

Also note the naming smell the whole file shares: the model class is lowercase
`products` and is imported beside the module of the same name (`views.py:20`), so
`products.objects` and `products` (module) differ only by attribute.
