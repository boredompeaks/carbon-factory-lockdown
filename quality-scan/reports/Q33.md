## Verdict up front

This is an unusually strong test module — 130 `assertEqual` against hand-written literals (prices,
`2499.00`, totals `2548.00/5098.00/5097.00`, pincodes, tracking numbers) rather than values recomputed
from the command's own tables; 0 `res.data`, exactly 1 wire assertion via `res.json()`; no skips, no
xfails, no shared class fixtures (`CredentialEnvMixin` is env mock only, each test seeds its own DB via
TestCase rollback); the DB guard IS pinned hard and would fail loudly if deleted. The defects are in the
*seeded state the tests certify*, not in assertion style: rows the command does not own, a reset that
leaves the audit trail lying, and one advertised "usable" object (the coupon) that is only
field-checked.

## Findings

**Q33-01 | P2 MEDIUM | CODE | seed_e2e.py:704**
`clean()` deletes `User.objects.filter(username=SUPERADMIN_USERNAME)` unconditionally. `Order.user` is
`on_delete=CASCADE` (models.py:127-133), so every order owned by `superadmin` that the command did *not*
create is destroyed. The command documents the opposite (seed_e2e.py:36-37, "deletes only the rows this
command owns"); the customer account got exactly that guard (708: `orders__isnull=True`) and exactly one
test (tests_seed_e2e.py:516-536). The superadmin mirror is absent from both code and tests. Reachability:
the seeded superadmin is the account the walk is performed in, and `is_superuser` bypasses admin RBAC
(common/admin.py:174-182), so the admin order-add form is reachable; any order created there is silent
cleanup collateral. Evidence: models.py:129 CASCADE; no `orders__isnull` on 704. Fix: filter 704 the way
708 is filtered, and add the mirrored test.

**Q33-02 | P3 LOW | CODE | seed_e2e.py:685-694**
Deleting seeded products/coupons/methods mutates foreign rows that the suite asserts "survive untouched":
`OrderItem.product` is SET_NULL (models.py:443), `Order.coupon` is SET_NULL (models.py:219),
`CartItem.product` is CASCADE (cart/models.py:85). Walk a storefront checkout with `marj` in the basket,
then `--cleanup`: the customer's order line loses its product FK and any cart line for `marj` disappears.
`test_cleanup_removes_only_the_seeded_rows` (469-514) only asserts foreign rows *exist*, never that their
columns are intact, and its foreign rows never reference a seeded product/coupon/method — so the boundary
is asserted against a fixture shaped to miss the failure.

**Q33-03 | P3 LOW | TEST | tests_seed_e2e.py:147-155**
The coupon assertions are metadata-only: `discount_type`, `discount_value`, `active`, `valid_from <= now`,
`valid_until > now`. `minimum_order_amount`, `usage_limit` and `used_count` are never asserted (all three
are seeded, seed_e2e.py:496-503) and the coupon is never *applied* — `/api/orders/apply-coupon/` exists
(orders/urls.py:49) and is never called by this module. A coupon seeded with `usage_limit=0`, an exhausted
`used_count`, or `minimum_order_amount=Decimal("999999")` keeps every assertion green while being
unusable — i.e. the one thing an owner signs in to do with SAVE10 is untested.

**Q33-04 | P2 MEDIUM | CODE | seed_e2e.py:574-608, 616-624**
The documented "re-running DOES reset the seeded statuses" has no trail half. `_seed_orders` /
`_seed_shipments` rewrite the rows' status through `update_or_create` but never delete the
`OrderStatusEvent` / `ShipmentEvent` rows the walk wrote, so after a re-seed the order row reads
`confirmed` while its own audit trail still says `confirmed→shipped`. `test_lifecycle_scenario_is_idempotent`
(626-651) is the test that exists for this: it deliberately walks a parcel to `DISPATCHED`, re-runs, and
asserts the parcel is back to `LABEL_CREATED` (651) — and never looks at the trail, so it certifies a clean
reset that also leaves the history contradicting the row. Adjacent and untested: seeded orders carry no
`TRIGGER_ORDER_CREATE` `OrderStatusEvent` although checkout writes one (checkout.py:831-836), so the
command's own claim that "a seed row no writer could have produced would make the D-01 admin walk refuse"
(570-573) is false for the audit dimension. The only event assertion in the file is the ShipmentEvent one
(261) — from the fresh-seed path only.

**Q33-05 | P3 LOW | TEST | tests_seed_e2e.py:263-269**
The advertised purpose — "the summary a human uses to sign in and open the admin" (module docstring 5-7) —
is asserted as substrings of stdout: `/admin/orders/order/`, `/admin/shipping/shipment/`, and the
credential lines. `reverse()` does guarantee the route resolves, but nothing GETs the printed URL, so a
change-form or changelist that 500s over a seeded row (an out-of-vocabulary status, a missing required
field, a broken `OrderStatusEvent` inline) leaves the suite green. Session-level sign-in *is* covered
(125-130 storefront, 320-336 admin), so the gap is precisely the page that renders the seeded data.

**Q33-06 | P3 LOW | TEST | tests_seed_e2e.py:25, 125-130**
The module subclasses `django.test.TestCase` rather than `common.testing.ApiTestCase`, so `ApiSettings`
(dummy Razorpay keys, MD5 hasher, locmem mail, temp MEDIA_ROOT) and the per-test `cache.clear()` never
apply. Its one API call is a `POST /api/accounts/storefront/login/`, which inherits `throttle_scope = "auth"`
(accounts/views.py:122, 10/min — settings.py:1287) keyed for an anonymous caller on IP. The counter lives
in the process/redis cache: `ApiTestCase` clears it at the start of each of *its* tests, so a preceding
test that spent the budget leaves it set when a plain-`TestCase` test runs — this assertion can flip
`200` → `429` on test order alone (Confidence M on the flake, H on the harness deviation). Practical
consequence: the only end-to-end login assertion in the flow is the one test not running under the house
harness.

**Q33-07 | P2 MEDIUM | CODE | seed_demo.py:143-144 (pinned by tests/test_seed_demo.py:103, 213)**
Asked directly: does any test pin a row whose status is outside the declared vocabulary? **Yes.**
`tests/test_seed_demo.py:103` asserts `o.status == "paid" and o.payment_status == "paid"`, and the cleanup
fixture reuses `"paid"` at 213. `"paid"` appears in neither `STATUS_CHOICES` (state.py:36-42) nor
`PAYMENT_STATUS_CHOICES` (state.py:130-137); `ALLOWED_TRANSITIONS.get("paid")` is `{}`, so the machine has
no edge out of the row on every surface, and `LEGACY_STATUS_DIMENSIONS["paid"]` (state.py:197-203) raises
`KeyError` for any reader that calls `payment_for_status` on it. The demo seed is the starting state for
the red-team (T1) and load (T2) programs, so this is the dataset the load/red-team numbers are measured
against. The test is the aggravating factor: it freezes a value no writer can produce. By contrast this
flow's own module is clean — every status it pins (`confirmed`, `pending`, `delivered`) is in the
vocabulary, and it asserts the *mapped* dimension literals (`captured`/`pending`/`fulfilled`, 210, 220,
226-227) rather than re-deriving them, which is what makes a change to `LEGACY_STATUS_DIMENSIONS` fail.

**Q33-08 | P4 INFO | TEST | seed_e2e.py:396-410**
The seed creates no role-scoped staff user: the superadmin joins no `Group` (`sync_role_groups`,
common/roles.py:143), and `RoleAwareModelAdmin._holds_capability` short-circuits on `is_superuser`
(common/admin.py:170-176), so the entire advertised admin walk runs with RBAC bypassed. `seed_demo`
does the opposite (one user per role, seed_demo.py:80-89, asserted at test_seed_demo.py:74-85). No test in
this module asserts any `Group` for any seeded account. Not a defect of the account (superuser bypass is
documented and intended), but the E2E walk cannot demonstrate a role-gated admin session and a regression
in `CAPABILITY_ROLES` would not be caught from this seed.

**Q33-09 | P3 LOW | TEST | tests_seed_e2e.py:406-416**
`assertEqual(generator.call_count, 4)` couples one test to three independent things: the retry budget, the
number of seeded orders (3), and the failure position of the side-effect list. Adding a fourth seed row —
a change the command invites — breaks this test while retry behaviour is untouched. The same test also
crams the exhaustion half (418-433) into the same method with cleanup-plus-manual-delete setup noise.

**Q33-10 | P3 LOW | CODE | seed_e2e.py:352-353 (pinned by tests_seed_e2e.py:805-808, 810-824)**
`_database_is_a_test_db()` returns `True` on `settings.DEBUG` alone, and the suite certifies that arm
(`test_debug_mode_is_an_accepted_condition` asserts a run succeeds with `DEBUG=True`). For a guard whose
stated job is refusing a "production-shaped" database, `DEBUG=True` is the exact accidental-production
case; the two other arms (sqlite engine, localhost host) are equally unconditional, so a local production
Postgres passes. The tests are honest about what the code does — which is why deleting the whole check
fails loudly (781-794 would raise nothing) while *weakening* it to `DEBUG or sqlite` would not.

## Direct answers to the brief's questions

- **Seeded state the command advertises?** Partly. Ownership/roles: the orders belong to `superadmin`,
  not to the storefront `customer` — `order_list` is scoped `user=request.user` (orders/views/order.py:52),
  so the field-login customer sees an empty order history; no test asserts the customer owns anything, and
  the only pinned owner is `superadmin` (190-193, 355-358). Staff roles: none are seeded. Coupon: field
  metadata only (Q33-03). Statuses: correct vocabulary and correct mapped dimensions (unlike seed_demo).
- **Row outside the declared vocabulary?** Yes, but in `tests/test_seed_demo.py:103` — the file under this
  flow is clean (Q33-07).
- **Rendered output or `res.data`?** Neither trap: 0 `res.data`, one `res.json()` (130) on a plain Django
  client, i.e. the rendered body. The remaining 129 assertions are ORM reads through literal-pinned
  expectations — the right shape for a seeding command.
- **Execution order / shared fixtures?** No shared class fixtures and no `setUpTestData`; every test seeds
  through the command in its own TestCase transaction. The one order-dependent surface is the un-cleared
  DRF throttle cache (Q33-06).
- **Is the non-test-DB guard exercised?** Yes, and it is the best-covered invariant in the file: flag
  refusal (772-779), production-shaped refusal with `User.objects.count() == 0` proof (781-794), plus
  three acceptance arms. Delete the guard → those tests fail.
- **Would deleting the guard or changing a seeded password keep tests green?** No for both: the guard
  deletion fails 772-794; a password change fails `check_password` + `authenticate` +
  `assertIn(f"superadmin: superadmin / {SUPERADMIN_PASSWORD}", out)` (263). The values are hand-written
  literals, not imported from the command's constants, so they cannot agree with a wrong constant.

## Seed invariants with NO test

keys has no lock and no IntegrityError retry, unlike `_ensure_order_number`).
