## Findings (severity order)

### Q37-01 | P3 / LOW | CODE | `backend/cart/management/commands/prune_carts.py:64`
**The prune is all-or-nothing: one unbounded `DELETE` over an unindexed predicate, with no `--limit`, no chunking and no supporting index — and a statement timeout makes it never converge.**

`prune_carts.py:49-54` builds `Cart.objects.filter(user__isnull=True, order__isnull=True, items__isnull=True, updated_at__lt=cutoff)` and `:64` hands the whole set to `stale.delete()` in a single statement. There is no `--limit`/`--batch-size` argument (`:30-41` defines only `--days` and `--dry-run`), so the transaction length is a function of how long the janitor has been off. `Cart.Meta` (`cart/models.py:67-79`) declares only the `unique_active_cart_per_user` constraint and `cart/migrations/0001_initial.py:29` creates `updated_at` with no `db_index`, so the predicate is a full table scan filtered on three NULL tests plus a range — no index can be used for any of the four terms as written.

Consequence, from the statement shape rather than from a measurement: a large first run holds a write transaction over the whole match set, and if the deployment's `statement_timeout`/lock timeout fires the transaction rolls back and **nothing** is pruned — the next scheduled run repeats the identical attempt. The command is single-shot by design, so it has no way to make progress across runs. Bound it (`--limit N` looped by the operator) or make the criterion sargable first. Not the same mechanism as Q02-07 (which is that nothing schedules the command at all).

Fix route: FOLD-INTO-NEXT. Confidence **M** (statement shape H; the timeout-convergence argument is inference, no DB touched).

### Q37-02 | P3 / LOW | CODE | `backend/cart/management/commands/prune_carts.py:45`
**`--days 0` is accepted and makes the age guard a no-op: `updated_at__lt=now` matches every row, so one run deletes every live empty guest cart on the site.**

The only validation is `if days < 0: raise CommandError` (`:45-46`); `0` passes, `cutoff = timezone.now() - timedelta(days=0)` (`:48`) is "now", and no row can have `updated_at >= now`. The surviving predicate is then exactly "empty, orderless, anonymous" — which is the normal state of *every* guest cart between boot and the first add, and the resting state of a guest who removed their last line. One `PRUNE_DAYS=0` cron misconfiguration, or an operator reading `--days` as "retention above which to keep", empties the whole guest population in a single unbatched statement (Q37-01). `--days` is documented as a *minimum age* (`:28-36`), so `0` should be refused with the same `CommandError` as a negative: `days <= 0`, or a floor of 1. Tests pin `-1` (`tests_merge.py:252-254`) and never `0`.

Fix route: FOLD-INTO-NEXT. Confidence **H**.

### Q37-03 | P3 / LOW | CODE | `backend/cart/views.py:82`
**A JSON number that overflows to infinity (`{"product_id": 1e400}` / `{"quantity": 1e400}`) escapes every guard as an uncaught `OverflowError` — a 500 on both public cart write paths.**

`views.py:82` `products.objects.get(id=product_id)` is wrapped in `except (products.DoesNotExist, ValueError, TypeError)` (`:84`) and `:103` `quantity = int(quantity)` in `except (ValueError, TypeError)` (`:105`); `:178-184` (PATCH) repeats the second shape. `json.loads('{"q": 1e400}')` is `inf` (probed) — `1e400` is an ordinary JSON number literal, so DRF's JSON parser never sees it as a constant and `STRICT_JSON` does not reject it (DRF's `JSONParser.parse` only routes `Infinity`/`NaN`/`-Infinity` through `parse_constant`, `rest_framework/parsers.py:63-68`). `int(inf)` raises `OverflowError` (probed), which neither clause catches, and Django does not catch it either: `IntegerField.to_python`/`get_prep_value` catch only `(TypeError, ValueError)` (source read, Django 6.1.1), so `:82` raises out of the ORM lookup as well. Result: `OverflowError` → 500 on `POST /api/cart/` and on `PATCH /api/cart/<id>/`, unauthenticated, no credential needed.

This is the crash half of the coercion defect; Q02-03 covers the truncation half (`2.9` → `2`, `true` → `1`) and is not duplicated here. The `:82` path is new — Q02-03 cites only `:103`/`:177`.

Fix route: FOLD-INTO-NEXT — `except (ValueError, TypeError, OverflowError)` (and reject floats rather than truncating).

### Q37-04 | P3 / LOW | CODE | `backend/cart/management/commands/prune_carts.py:64`
**The janitor deletes `Cart` rows with no lock and no coordination with the request paths, so a cart deleted between `resolve_cart` and the write turns three unguarded sites into uncaught 500s.**

`stale.delete()` takes no `select_for_update` and the request paths take none either. The add path resolves the cart (`views.py:64` → `services.py:38`/`:52`) and then inserts a `CartItem` against that in-memory `cart` (`views.py:125-127`) with no transaction; if the row went away in between, the insert violates `CartItem.cart`'s NOT NULL FK and raises `IntegrityError`, which nothing catches. The coupon paths have the same TOCTOU one layer down: `Cart.objects.select_for_update().get(pk=cart.pk)` (`views.py:239`, `:267`) raises `Cart.DoesNotExist` if the row is gone, and `Cart.DoesNotExist` is not in any `except` in this module. The prune is one of only two deleters of a cart row (the other is `services.py:128`/`:141` in the merge, which holds locks), so this is the unguarded half of a two-writer pair.

Reachability: needs a row that is simultaneously empty, 30+ days stale, and being written — rare at the default 30 days, but `--days 0` (Q37-02) promotes *every live empty guest cart* into the match set on every run, which is what turns a theoretical seam into a scheduled one. `resolve_cart`'s `get_or_create` (`services.py:52`) is the correct shape for this problem and is not used by the mutation sites.

Fix route: NEXT-BUILD (catch `IntegrityError`/`DoesNotExist` and re-resolve, or serialize the janitor against the write paths). Confidence **M** (mechanism H; the interleaving is reasoned, not exercised).

### Q37-05 | P3 / LOW | CODE | `backend/cart/management/commands/prune_carts.py:55`
**The figure the command prints is a pre-count from a separate query, not the number of rows deleted — and the comment that justifies preferring it rests on a cascade that the filter makes impossible.**

`matched = stale.count()` (`:55`) and `stale.delete()` (`:64`) are two independent statements outside any transaction (the delete is atomic by itself, the pair is not), and Django's `QuerySet.delete()` re-evaluates its own query rather than consuming the earlier count — so a cart that gains a line between the two statements drops out of the delete and the printed `Deleted {matched}` (`:67-69`) overstates. The comment at `:65-66` says the matched count is printed "not the ORM's cascade-inclusive delete count", but the predicate guarantees `items__isnull=True`, so there is nothing to cascade and the ORM total would have been the accurate figure. `conventions.md:49-52` holds printed numbers to "a number is a claim until a command produced it"; this one is produced, but it is not the number the sentence claims.

Fix route: FOLD-INTO-NEXT (print `len(deleted)` from the ORM's `(total, per_model)` tuple, or count inside one transaction).

### Q37-07 | P4 / INFO | CODE | `backend/cart/views.py:67`
**Every cart response serializes the cart through `CartSerializer` with no `prefetch_related`/`select_related`, so the boot GET costs `1 + 1 + n` queries and each line re-fetches its product.**

`views.py:67`, `:140`, `:202`, `:211`, `:243`, `:270` all build `CartSerializer(cart)` directly. `CartSerializer.items` is a plain `CartItemSerializer(many=True)` (`serializers.py:22`) over the reverse manager and `CartItemSerializer.product` is a nested `ProductSerializer` (`serializers.py:9`, flat per `products/serializers.py:6-14`), so each line costs one product query, plus one for the coupon traversal (`serializers.py:39-43`). This is the SPA's per-page-load call (the header badge) and the throttle deliberately does not bound it (Q02-04), so the cost lands on the one unthrottled public read in the flow. Not filed by Q02. Fix is local: `Cart.objects.select_related("coupon").prefetch_related(Prefetch("items", queryset=CartItem.objects.select_related("product")))` behind a `_cart_payload(cart)` helper, which also removes the six-way duplication of the response shape.
